# 品达物流 TMS — 完整开发计划（执行总纲）

> **定位**：给**执行者（你 + Claude Code）**照做的动手顺序，不是给老板看的排期。
> **事实输入**：《项目现状基线_代码与服务器实测.md》（2026-10-07 实测）+《需求文档v2》v2.4 + 各任务卡。
> **与甘特区别**：《整体项目排期总览甘特》是多团队并行的理想节奏；本计划按**单人全栈 / Vibe Coding**实际，以"**纵向切片、每片可跑可测、最快看到页面**"重排。
> **铁律**：技术栈不升级、不引新中间件；容器内中间件一律 `192.168.20.130`（禁 127.0.0.1 / 192.168.1.80）；每阶段走 CI/CD 自动构建部署。

---

## 一、现状决定的打法

- **已就绪（不用重做）**：8 中间件 + 数据卷 + 容器自启动 + Gitea Actions CI/CD + 14 微服务后端主干（订单/调度/在途/签收/基础数据）。
- **要新做**：① 管理端 P0 六大业务页（最急）；② 移动三端 uni-app（从零）；③ 需求新增的 P1/P2 后端表与接口。
- **打法**：**后端先补"页面要用到的"接口和数据 → 管理端纵向切片逐页打通 → 端到端造数联调 → 再铺移动端 → 最后 P1/P2 深化与上线收口**。每完成一片即提交、CI 自动部署、可在页面验证。

## 三、各阶段任务清单

### M0 基线锁定（0.5 天）
- [ ] `git status` 核对，把需求文档（37 文件）+ 现状基线 + 本计划一次性提交并 `git push gitea master:master`。
- [ ] 确认 24 容器 Up、Nacos 14 服务注册、CI 上一轮构建跑完（load 回落）。
- [ ] 定分支/提交规范（对应《ClaudeCode开发纪律与红线》）。
- **验收**：仓库为最新基线，触发一次 CI 全绿。

### M1 后端 P0 数据与接口（3–5 天）
- [ ] 执行 OPS-0：建 `pd_notify_template`、`pd_notify_record`、`pd_transport_alert`（+ `pd_alert_sop`）DDL。
- [ ] 把三端/新接口按模板注册进 `pd_auth.pd_auth_resource` 并绑角色（`docs/sql/pd_auth_resource_注册模板_阻断C.sql`、阻断 C 闭环脚本）。
- [ ] 跑种子/造数脚本（`docs/sql/种子数据初始化_FR00.sql`、testdata），确认账号统一 123456 可登录。
- [ ] 补齐六页所需查询接口（缺哪个补哪个，Feign/aggregation 组装）。
- **验收**：每个接口经网关 `/api` 带 token 可 curl 返回数据。

### M2 管理端 P0 六页（8–12 天，纵向切片，一页一闭环）
> 顺序：**订单管理 → 调度一张图 → 在途监控 → 车辆/司机档案 → 统一告警中心 → 通知中心**；每片：加 api js → 建页 → 接数据 → 提交 CI → 页面验证。
- [ ] 引入 vue-baidu-map-3x，配百度 GL ak（占位，BD-09 零转换）。
- [ ] 六页按《管理端UI规范与页面模板》六类模板实现（主色 `#2B6CFF`）。
- [ ] dashboard 大屏由硬编码改为接 `api/Dashboard.js` 真实数据。
- [ ] 旧 `pinda/*` 42 页：保留可复用的（用户/机构/字典/权限），其余下线/隐藏。
- **验收**：六页可查询、筛选、看详情、地图/轨迹/告警可交互；《管理端UI规范》DoD 全过。

### M3 端到端联调（2–3 天）
- [ ] 按《链路测试用例与造数脚本》造 ≥10 条覆盖全链路订单。
- [ ] 跑 TC-01~11：下单→计费→调度→取件→干线→派件→签收→回单→异常→告警→结算口径。
- [ ] 记录并修复阻断问题，回归验证。
- **验收**：核心链路用例全过，页面能完整演示一单到底。

### M4 移动三端（15–20 天）
- [ ] 建 `pinda-uni-app`（uni-app Vue3+Vite+uview-plus+Pinia），先做**公共层**（request/user/coord 坐标转换/api）。
- [ ] **司机端**（11 页，对应《司机端任务卡》）：登录/任务/到站/装卸/签收/POD 上传（走 `/api/web-driver/attachment/upload`）。
- [ ] **快递员端**（10 页）：取派任务、扫码、投递确认（合规 FR-30）。
- [ ] **客户小程序**（10 页）：下单、轨迹、地址簿、支付（mock 兜底）；小程序侧腾讯地图 GCJ-02。
- **验收**：三端核心流程在真机/模拟器可用，接口与管理端共用同一套后端。

### M5 P1 业务深化（15–20 天，按依赖接力）
- [ ] **OPS**：围栏与自动流转、ETA、运营看板、成本分摊、绩效（OPS-1~5）。
- [ ] **FIN**：运费审计、对账单、司机工资、账期、利润（FIN-1~5，含 FA-1~4）。
- [ ] **DSP**：VRP 升级、外协运力池、抢派双模、承运商门户/KPI/黑名单（DSP-1~3）。
- [ ] **IoT**：JT/T 808 终端接入、冷链温控、视频、能源（IOT-1~3，缺设备先 mock）。
- **验收**：各任务卡 P1 项交付，数据口径与《数据字典与枚举口径》一致。

### M6 上线收口（10–15 天）

- [ ] 合规闸口：M1 硬闸口 FR-30/31/36 复核；等保、资质（持牌通道、无二清）。

## 四、依赖顺序（关键路径）

```
M0 基线锁定
   └─> M1 后端数据/接口（通知告警表·资源注册·造数）
          └─> M2 管理端六页（订单→调度→在途→档案→告警→通知）
                 └─> M3 端到端联调（10 单 / TC-01~11）
                        ├─> M4 移动三端（公共层→司机→快递员→客户）
                        └─> M5 P1 深化（OPS→FIN→DSP→IoT）
                                      └─> M6 上线收口（P0 差距→合规→可商用）
```
- 每个 M 内部"纵向切片、小片提交"，避免攒大批量；每片都经 CI 部署后在真实页面验证。

## 五、完成定义（DoD）与纪律

**每片/每阶段 DoD**：
1. 代码提交并 push gitea，CI 构建部署绿灯；
2. 新接口已注册 `pd_auth_resource` 并授权，经网关可访问；
3. 页面/接口在 `192.168.20.130` 实测通过（非仅本地）；
4. 涉及数据口径与数据字典一致；涉及 UI 与 UI 规范一致；
5. 有验证记录，失败项已记录不隐瞒。

**红线（详见《ClaudeCode开发纪律与红线》）**：不硬编码生产 IP/密码到代码（走环境变量/Nacos）；不新增中间件、不升级主框架；软删除/审计字段遵循统一约定；支付资金走持牌机构。
