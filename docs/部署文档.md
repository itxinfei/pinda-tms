# 品达TMS 中间件部署文档（Ubuntu 24.04）

本文档说明如何在一台 Ubuntu Server 24.04 (amd64) 虚拟机上部署品达TMS所需的全部中间件与数据库。中间件以 Docker 容器方式运行；Java 微服务同样容器化，由 `deploy/apps/docker-compose.app.yml` 编排（本文早期版本写的“微服务在宿主机运行”已不适用）。由于中间件供宿主机上的 CI 与各服务共同访问，地址统一使用宿主机 IP，容器之间不依赖容器网络。

> **本节以下所有参数、镜像与挂载路径，已于 2026-10-06 对 192.168.20.130 实机 `docker inspect` 核对。** 该机器上曾长期存在文档与实际漂移（镜像换代、挂载缺失），核对结果见“二、统一规划”的挂载实况表。

## 一、架构总览

|---|---|---|---|---|

```bash

export DB_PASS=<你的 MySQL root 口令>   # 本机实值放在 /data/deploy/middleware/.env（不入库）

```

> **配置 group 与注册 group 是两件事。** 审计全部 `bootstrap*.yml` 后确认：**每个服务的 `spring.cloud.nacos.config.group` 都是 `pinda-tms`**，group 写在带 profile 的文件里（`bootstrap-prod.yml` 等），只看 `bootstrap.yml` 会误判成“没设置、走 DEFAULT_GROUP”。服务注册同理全部落在 `pinda-tms` 组（实测 `groupName=pinda-tms` 返回 14 个）。
>
> 因此 Nacos 里 `DEFAULT_GROUP` 下的那 17 条同名配置**没有任何服务在读**，属于历史残留副本——改它不会产生任何效果，是排障时的真实陷阱（本次就给一个配置补丁打到了 `DEFAULT_GROUP` 而白跑一轮）。确认保留价值后再删；删前先看第八节，Seata 的 TC 现在**必须**注册在 `DEFAULT_GROUP`，那是另一回事，别一起清掉。

### 2.1 挂载与持久化实况

下表是 2026-10-06 对每个容器 `docker inspect .Mounts` 的实测结果，**不要凭“数据都在 /data”这个印象操作容器**：

| 服务 | 宿主机路径 | 容器内路径 | 数据体量 | 状态 |
|---|---|---|---|---|
| mysql57 | `/data/mysql` | `/var/lib/mysql` | 185M | 正常 bind |
| redis | `/data/redis` | `/data` | 20K | 正常 bind（AOF） |
| nacos | `/data/nacos` | `/home/nacos/logs` | 71M | **只挂了日志** |
| nacos 配置库 | 无 | `/home/nacos/data`（内嵌 Derby） | 3.9M | **留在容器可写层** |
| kafka | 无 | `/bitnami/kafka` | 6.4M | **无任何卷，删容器即永久丢失** |
| rabbitmq | 匿名卷 `825aeae…` | `/var/lib/rabbitmq` | **453M** | 不在 /data、无名字、文档外 |
| zookeeper | 3 个匿名卷 | `/data`、`/datalog`、`/logs` | 124K | 同上 |
| gitea | `/data/gitea` | `/data` | 266M | 见 gitea compose |
| CI Maven 仓库 | `/data/m2` | `/root/.m2` | 256M | 由 act_runner 注入构建容器 |
| CI 工作区 | `/data/projects`、`/data/runner` | — | 15M | runner 状态 |
| seata | `/data/seata/config` | 宿主机直接读取 | 12K | systemd 服务 |

由此得出两条可操作的结论：

1. **按 `/data` 做的备份会漏掉约 460M 状态**——RabbitMQ 453M 与 ZK 124K 在匿名卷里，Kafka 6.4M 与 Nacos 配置 3.9M 在容器可写层。备份必须显式覆盖这四处（用 `docker cp` 从容器路径取，它会穿过卷）。
2. **`docker rm` 的后果因服务而异**：MySQL/Redis 安全；ZK/RabbitMQ 的卷会变成孤儿留在 `/var/lib/docker/volumes/`，新容器不会复用，需手工找回；Kafka/Nacos 直接归零且无法找回。

- 启动顺序：Docker → MySQL（建库导数据）→ Redis → Nacos（建命名空间、推送配置）→ Zookeeper → Kafka → RabbitMQ → Seata。

### 2.2 宿主机基线（磁盘与内存参数）

**根分区。** Ubuntu Server 24.04 的Installer 默认只把 LVM 卷组的 **50%** 分给根逻辑卷（装机选“使用整个磁盘 + LVM”时尤其如此）。本机 100G 盘上曾出现 `sda3` 是 98G PV、根 LV 却只有 49G、`VFree` 常年 49G 的情况，磁盘满其实是空间没分配而不是不够用。补齐是两条在线命令，无需卸载或重启：

```bash
sudo lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv
```

> 只能做大不能做小：ext4 缩容要卸载且有风险，所以剩余空间一旦并入根卷就别指望再拆出来。若要给 `/data` 单独建卷，应在装机阶段就规划好。

**内存与 IO 参数。** 已固化在 `/etc/sysctl.d/99-pinda-memory.conf`（文件名排在 `99-sysctl.conf` 之后才会覆盖生效），四项及理由：

```
vm.overcommit_memory = 1          # Redis 开 AOF，重写要 fork；启发式模式下 fork 可能失败导致写入报错
vm.swappiness = 10                # 默认 60 会提前换出 JVM 匿名页，回来就是 GC 停顿尖刺
vm.dirty_background_ratio = 2     # 单盘 IO 接近饱和时收紧脏页窗口，降低周期性写停顿
vm.dirty_ratio = 5
```

加载并核对（只加载本文件，不动其它网络参数）：

```bash
sudo sysctl -p /etc/sysctl.d/99-pinda-memory.conf
sysctl vm.overcommit_memory vm.swappiness vm.dirty_background_ratio vm.dirty_ratio
```

**JVM 堆外参数。** 15G 内存跑 15 个容器化服务 + 6 个中间件，实际占内存的是堆外而不是 `-Xmx`：实测 pd-gateway `-Xmx256m` 却常驻 626M、210 个线程（Java 8 默认 `Xss=1m`，光线程栈就 ~210M）。所以 `JAVA_OPTS` 除堆大小外还要带 `-XX:MaxMetaspaceSize`、`-XX:MaxDirectMemorySize`、`-XX:+HeapDumpOnOutOfMemoryError`，否则进程被 OOM 杀掉时拿不到任何现场。注意 `deploy/apps/docker-compose.app.yml` 用的是 `x-jvm-core` / `x-jvm-small` 两个锚点，改这两行即覆盖全部 15 个服务。

### 2.3 构建残留清理（三层）

镜像是**本地 build、不推 registry**，tag 用 git 短提交号，所以每部署一次就给每个服务多加一个 tag，旧 tag 变成"有父镜像引用但无人引用"的层，`docker image prune` 都清不掉。实测 22 小时堆出 191 个 tag、34.9GB，根盘写到 74%。act_runner v0.6.1 又没有 `[gc]` 段（配置文件里根本没有这个 key），所以清理只能自己搭，共三层：

| 层 | 位置 | 触发 | 作用 |
| --- | --- | --- | --- |
| ① 构建后即清 | `deploy/ci/cleanup-images.sh`，由 `.gitea/workflows/deploy.yml` 末尾的"清理构建残留"步骤调用（`if: always()`） | 每次 push 部署 | 每个 `pinda/pd-*` 仓库只保留最近 5 个 tag；回收悬空镜像；封顶 BuildKit 缓存 |
| ② 每日兜底 | 宿主机 `/usr/local/bin/pinda-image-cleanup.sh` + root crontab `40 4 * * *`，日志 `/var/log/pinda-image-cleanup.log` | 每天 04:40 | 与 git 无关，流水线挂了/脚本没提交也照样堆不起来 |
| ③ 参数层 | `/etc/docker/daemon.json` 的 `log-opts.max-size=100m`、`builder.gc.policy` | 构建/写日志时自动 | 防容器日志和 BuildKit 缓存无限增长 |

脚本的三条安全约束（改动时别去掉）：

```bash
KEEP=5 DRY_RUN=1 bash deploy/ci/cleanup-images.sh   # 预演，只打印不动手
```

1. **只碰 `pinda/pd-*`**，中间件镜像（mysql/redis/nacos/bitnami…）不在扫描范围内；
2. **正在用的 tag 双保险保护**——既比对运行中容器的 `Config.Image`，也比对其镜像 ID（`--format` 里带点的标签键会返回 `<no value>`，只查一个来源会漏）；
3. 排序用 `docker images --format '{{.Tag}}|{{.CreatedAt}}' | sort -t'|' -k2 -r`，**不能用 `--sort`**（该版本不支持，会静默输出空列表，结果就是"处理 0 个"却以为已经清理过）。

> **BuildKit 缓存的容量封顶在这台机器上不生效**（实测）：`docker builder prune -f --max-used-space 2GB` 与字节写法 `--max-used-space 2000000000` 都只回 `Total: 0B`，缓存一分不掉；`--keep-storage` 同样无效。真正生效的是**按时间**回收：`docker builder prune -f --filter "until=1h"` 实测清掉 1.488GB（3.685GB → 2.197GB）。所以 ①② 里用的是 `BUILDER_KEEP_AGE`（默认 72h）。要做**容量**封顶只能开 `daemon.json` 的 `builder.gc.policy`——那需要重启 dockerd（整栈含 MySQL/Nacos 中断一次），目前未上机。

**核对是否真的在堆盘：**

```bash
docker system df                 # Images/Build Cache 两行是主要嫌疑
docker images 'pinda/pd-*' | wc -l
df -h / | tail -1
```

### 2.4 虚拟机恢复会打挂对外服务（已装自愈）

本机是 VMware 虚拟机。guest 被挂起再恢复后，宿主网络会按接口 `ifdown/ifup` 重配一遍（open-vm-tools 13.x 带的 `/etc/vmware-tools/scripts/vmware/network` 干这事，同时 VMware Tools 会把 guest 时钟同步回宿主，于是 journal 里出现十几小时的时钟跳变），**docker 网桥被拆了重连，但网桥上的网关 IP 是 dockerd 直接刷上去的、不属于任何网络配置文件，没人补回来**。后果：宿主机路由表里再没有 `172.19~172.22.0.0/16`，所有 `-p` 发布的端口（前端 8080、网关 8760、Gitea 3000、MySQL 3306）一律 TCP 连得上但无响应，而**容器之间照常通信**（同一网桥上二层转发不需要网关），所以 compose 健康检查全绿、看起来一切正常。

三层处理：

```bash
# ① 已经停用 resume 时的网络重配脚本（原件在同目录 network.orig-pinda）
#    /etc/vmware-tools/scripts/vmware/network  -> exit 0
# ② 自愈守护：每 1 分钟比对 docker 声明的网关与网桥实际地址，缺就补
systemctl status pinda-bridge-fix.timer
journalctl -u pinda-bridge-fix.service --no-pager -n 10
# ③ 手动应急（脚本在仓库里，也可 ssh 上去直接跑）
bash /usr/local/bin/pinda-bridge-fix.sh          # 实修
DRY_RUN=1 bash /usr/local/bin/pinda-bridge-fix.sh # 只报告
```

> 判这类故障**不要先看防火墙**：分三层各测一次就定位清楚了——容器内自问自答（`docker exec <c> curl 127.0.0.1:<port>`，通了说明进程活着）、容器互访（`/dev/tcp` 通了说明桥接二层正常）、宿主直连容器 IP（不通说明宿主没有进容器子网的路由）。另外，容器内 `/dev/tcp/127.0.0.1:<port>` 这种探针天生看不见宿主↔容器这一段，`deploy/ci/deploy-check.sh` 第 3 节专门补了这个检查。

还有一条与它同源、当前仍在生效的缺陷：ufw 的 `INPUT` 默认 DROP 且原本**没有任何一条针对 `docker0`/`br-*` 的放行**，所以跑在宿主机上的进程（如 `seata-server` 连 `192.168.20.130:3306`）拿不到容器回包。已在线补了 `-A ufw-before-input -i br-+ -j ACCEPT` 与 `-i docker0 -j ACCEPT`，并写进 `/etc/ufw/before.rules`（用 `iptables-restore --test` 验过语法；改这个文件前留了 `before.rules.pinda-bak-<日期>` 备份）。**改完不要贸然 `ufw reload`**，先在线加规则、确认新的 SSH 连接还能建再持久化。

顺带：`br_netfilter` 目前没加载（`/proc/sys/net/bridge/` 不存在），它是 Docker 的官方前置条件。因为加载它会让桥接流量进入 iptables，所以先在 `before.rules` 里加好 `ufw-before-forward` 的桥放行，再加载——这两步连同 `daemon.json`（容器默认 `nofile=65535`、BuildKit 自动 GC）打包在 `deploy/ci/apply-docker-window.sh` 里，需要 1-2 分钟整栈中断，等窗口执行；脚本带 60 秒观察窗，dockerd 起不来会自动用备份回滚。

### 2.5 :80 与 :8080 是同一个前端（曾经不是）

这台机上有两个入口访问管理后台，历史上它们**跑的是两份不同的产物**：`:8080` 是 CI 构建的 `pd-admin-ui` 容器，`:80` 是 Ubuntu 自带 nginx 直出的宿主静态目录 `/var/www/pinda`（手工拷贝、**CI 完全不碰**）。实测两份 index.html 引用的 JS 哈希都不同（`app.b0a4bcd1.js` vs `app.1f7dadf8.js`），也就是说从 `http://192.168.20.130` 打开时看到的是过期副本——这类"改了没生效/菜单空"的现象不一定是浏览器缓存，先确认自己走的是哪个入口。

现在 `:80` 改成纯反代到容器，静态与 `/api` 都由容器里那份 nginx 负责，单一真源：

```bash
bash deploy/nginx/install-host-80.sh   # 配置在 deploy/nginx/ 下，可重复执行
# 核对：两个入口的 app.*.js 哈希必须一致
curl -s http://192.168.20.130/     | grep -oE "static/js/app\.[a-z0-9]+\.js"
curl -s http://192.168.20.130:8080/ | grep -oE "static/js/app\.[a-z0-9]+\.js"
```

> 两个坑：① `conf.d` 目录**只 include `*.conf`**，websocket 的 `map $http_upgrade $connection_upgrade` 若起别的后缀（如 `.map`）根本不会被加载，`nginx -t` 直接报 `unknown "connection_upgrade" variable`；② 改完必须 `nginx -t` 通过再 `reload`，不要先挪走 `/var/www/pinda` 再改配置，否则中间会出现"静态站已没了、新配置又没生效"的空窗。
>
> CORS 白名单在网关侧（`-Dcors.allowed.origins`），`http://192.168.20.130`（无端口，即 :80）与 `http://192.168.20.130:8080` 两条都在里面，实测两个入口的预检与 GET 都回 `Access-Control-Allow-Origin`。

### 2.6 流水线 30 分钟超时（红过的真实原因）

`/data/runner/config.yaml` 的 `runner.timeout` 曾被写成 `30m`，而完整一次构建（Maven 全部模块 + 15 个镜像 + 前端 npm）实测要 35 分钟以上。超时时 act_runner 报的**不是超时**，而是去 job 容器取退出码文件失败的假象错误：

```
Get "http://docker.sock/.../containers/<id>/archive?path=/var/run/act/workflow/pathcmd.txt": context deadline exceeded
```

看到它在"构建 14 个微服务镜像"步骤中途挂掉、而日志里 Maven 明明 `✅ Success`、镜像也建成了一批，就要怀疑作业被整体掐掉，先查 `timeout` 再看代码。现已调回 `2h`（改完需 `systemctl restart act-runner`，空闲时做）。

## 三、安装 Docker

```bash
# 1) 前置依赖
sudo apt-get update
sudo apt-get install -y ca-certificates curl gnupg

# 2) Docker 官方 GPG 密钥
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo tee /etc/apt/keyrings/docker.asc >/dev/null
sudo chmod a+r /etc/apt/keyrings/docker.asc

# 3) 添加 APT 源（自动识别代号 noble）
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" | sudo tee /etc/apt/sources.list.d/docker.list >/dev/null

# 4) 安装（国内访问慢可把 download.docker.com 换成 mirrors.aliyun.com/docker-ce）
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# 5) 镜像加速 + 容器日志轮转
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json >/dev/null <<'EOF'
{
  "registry-mirrors": [
    "https://docker.1ms.run",
    "https://docker.1panel.live",
    "https://docker.m.daocloud.io"
  ],
  "log-driver": "json-file",
  "log-opts": { "max-size": "100m" }
}
EOF

# 6) 启动并开机自启
sudo systemctl enable --now docker
docker --version

# 7) 当前用户免 sudo（执行后重新登录，或 newgrp docker 生效）
sudo usermod -aG docker $USER

# 持久化目录
sudo mkdir -p /data/mysql /data/redis /data/nacos /data/seata \
             /data/nacos-data /data/zookeeper/data /data/zookeeper/datalog \
             /data/kafka /data/rabbitmq /data/gitea /data/m2 /data/projects /data/runner
```

### 4.4 Seata AT 回滚表

**7 个业务库都要建 `undo_log`，不能只建 pd_dispatch。** 各服务普遍开了 `enable-auto-data-source-proxy: true`，只要某个库的数据源被纳入全局事务分支，它的库就必须有这张表，否则回滚日志写入直接失败。早期文档只给了 `pd_dispatch`，其余 6 库是 2026-10-06 补齐的。

已存在 `pd_dispatch.undo_log` 时，用 `LIKE` 从它复制最稳（逐列与索引结构保证一致，不必手写 DDL）：

```bash
docker exec -i mysql57 mysql -uroot -p${DB_PASS} <<'SQL'
CREATE TABLE IF NOT EXISTS pd_dispatch.undo_log LIKE pd_dispatch.undo_log; -- 占位, 已存在则跳过
CREATE TABLE IF NOT EXISTS pd_aggregation.undo_log LIKE pd_dispatch.undo_log;
CREATE TABLE IF NOT EXISTS pd_auth.undo_log        LIKE pd_dispatch.undo_log;
CREATE TABLE IF NOT EXISTS pd_base.undo_log        LIKE pd_dispatch.undo_log;
CREATE TABLE IF NOT EXISTS pd_oms.undo_log         LIKE pd_dispatch.undo_log;
CREATE TABLE IF NOT EXISTS pd_users.undo_log       LIKE pd_dispatch.undo_log;
CREATE TABLE IF NOT EXISTS pd_work.undo_log        LIKE pd_dispatch.undo_log;
SQL
```

全新环境没有可复制的来源时，用项目实际采用的结构（与现网 `SHOW CREATE TABLE` 逐字一致：无 `id` 自增主键、`DATETIME(6)`、唯一键 `ux_undo_log`）：

```sql
CREATE TABLE IF NOT EXISTS `undo_log` (
  `branch_id` BIGINT NOT NULL, `xid` VARCHAR(128) NOT NULL, `context` VARCHAR(128) NOT NULL,
  `rollback_info` LONGBLOB NOT NULL, `log_status` INT NOT NULL,
  `log_created` DATETIME(6) NOT NULL, `log_modified` DATETIME(6) NOT NULL,
  UNIQUE KEY `ux_undo_log` (`xid`,`branch_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='AT undo table';
```

验证（应覆盖 7 个 `pd_` 库；另有历史库 `pinda_tms`）：

```bash

  "SELECT table_schema FROM information_schema.tables WHERE table_name='undo_log' ORDER BY 1;"
```

### 7.1 Zookeeper 3.5 + Kafka 2.6（bitnami）

```bash
docker run -d --name zookeeper \
  -p 2181:2181 \
  -v /data/zookeeper/data:/data \

docker run -d --name kafka \
  -p 9092:9092 \
  -v /data/kafka:/bitnami/kafka \
  -e KAFKA_CFG_ZOOKEEPER_CONNECT=${HOST}:2181 \
  -e KAFKA_CFG_LISTENERS=PLAINTEXT://:9092 \
  -e KAFKA_CFG_ADVERTISED_LISTENERS=PLAINTEXT://${HOST}:9092 \
  -e ALLOW_PLAINTEXT_LISTENER=yes \
  -e KAFKA_HEAP_OPTS="-Xms256m -Xmx512m" \
  --restart=unless-stopped \
  bitnami/kafka:2.6.0 /opt/bitnami/scripts/kafka/run.sh

docker exec kafka /opt/bitnami/kafka/bin/kafka-topics.sh --create --if-not-exists \
  --bootstrap-server ${HOST}:9092 --replication-factor 1 --partitions 3 \
  --topic tms_order_location
```

要点，逐条都是实机踩过的：

- **`KAFKA_ADVERTISED_LISTENERS` 必须是宿主机 IP**，否则客户端拿到容器内地址会连不上。
- **bitnami 版用 `KAFKA_CFG_*` 前缀**，与旧文档里 `wurstmeister` 的 `KAFKA_*` 不通用；bitnami 的 `KAFKA_LISTENERS` 写法是 `PLAINTEXT://:9092`（不含 `0.0.0.0`），旧写法在 bitnami 下会被忽略。
- **Kafka 与 ZK 必须显式挂卷。** 在 2026-10-06 之前，实机的 Kafka 容器一个卷都没有，`__consumer_offsets` 与 `tms_order_location` 全在容器可写层，`docker rm kafka` 就没了；ZK 则是镜像自带 `VOLUME` 声明产生的**匿名卷**，数据在但没名字、不在 `/data`，重建容器后新卷是空的、旧卷变孤儿。
- `KAFKA_HEAP_OPTS` 显式压到 512m，是为了能安全配 1g 容器内存上限；bitnami 默认 1024m 堆配上 1g 上限，堆写满就会被 cgroup OOM 杀掉。
- 挂 `/data/kafka` 后目录属主要 `1001:1001`（bitnami 以该 uid 运行），ZK 的目录属主 `1000:1000`。

### 7.2 RabbitMQ 3.8

```bash
docker run -d --name rabbitmq \
  -p 5672:5672 -p 15672:15672 \
  --hostname rabbitmq \
  -v /data/rabbitmq:/var/lib/rabbitmq \
  -e RABBITMQ_DEFAULT_USER=pinda \
```

## 八、部署 Seata Server（可选）

配置来源 `/opt/seata/seata-server-1.4.2/conf/registry.conf`，注册与配置都走 Nacos：

```

  nacos { serverAddr = "192.168.20.130:8848" namespace = "1cb93ce4-dc0e-4730-b759-d35fd7ed93c3" group = "SEATA_GROUP" } }
```

Nacos 中新建配置：命名空间 pinda，Group=`SEATA_GROUP`，Data ID=`service.vgroupMapping.pinda-tms-group`，内容 `default`。

 systemd 单元 `/etc/systemd/system/seata-server.service`：

```ini

Environment=JAVA_HOME=/usr/lib/jvm/java-11-openjdk-amd64
WorkingDirectory=/opt/seata/seata-server-1.4.2
```

要点：

- `-m file` 是**文件存储模式**，事务会话落在 `/opt/seata/seata-server-1.4.2/sessionStore`（宿主机磁盘，不在容器层，所以没有丢数据的风险）。要改成 redis/db 模式需同步改 `file.conf` 与 `registry.conf`。

#### ⚠️ TC 必须注册到 `DEFAULT_GROUP`，不是 `SEATA_GROUP`

**这是全项目最隐蔽的一个坑，2026-10-06 定位并修复。** 症状是各服务持续刷（约 12 条/分钟/服务）：

```
i.s.c.r.netty.NettyClientChannelManager : no available service 'default' found, ...
```

客户端连不上 TC，`@GlobalTransactional` 实际不生效，但服务本身启动正常、接口也不报错，所以极容易被当成“Seata 没用到”而长期忽略。

根因是**两版本的 naming group 约定不一致**：

- 客户端 `seata-spring-boot-starter` **1.2.0** 查询服务实例时用的 group 固定是 `DEFAULT_GROUP`（`seata.registry.nacos.group` 只作用于 **config** 读取，不作用于 naming 查询——这是 1.2.0 的行为，不是配置写错）；
- 服务端 1.4.2 的 `registry.conf` 出厂把 `group` 写成 `SEATA_GROUP`。

两边错开，永远查不到。判据直接看客户端日志的 Nacos 订阅行：

```
[LISTENER] adding DEFAULT_GROUP@@seata-server with default to listeners
```

修法只改 TC 一侧的 `registry.nacos.group`，**不需要重建任何服务镜像**：

```hocon
registry {
  type = "nacos"
  nacos {
    serverAddr = "192.168.20.130:8848"
    namespace = "1cb93ce4-dc0e-4730-b759-d35fd7ed93c3"
    cluster = "default"
    group = "DEFAULT_GROUP"     # 必须与客户端 naming 查询一致
  }
}
config {
  type = "nacos"
  nacos {
    # config 段保持 SEATA_GROUP：vgroupMapping 等配置就存在这个组下，客户端读得到
    serverAddr = "192.168.20.130:8848"
    namespace = "1cb93ce4-dc0e-4730-b759-d35fd7ed93c3"
    group = "SEATA_GROUP"
  }
}
```

改完 `systemctl restart seata-server`，约 30 秒内各服务应出现成功注册的正面证据（没有这行就不要宣称修好）：

```
io.seata.core.rpc.netty.RmRpcClient : register RM success. server version:1.4.2
io.seata.core.rpc.netty.TmRpcClient : register TM success. server version:1.4.2
```

要点与边界：

- **registry 段和 config 段的 group 现在故意不同**，不要“顺手统一”，改了会立刻退回找不到 TC 的状态。
- 验证要用上面的 `register RM/TM success`，不能只看“报错消失了”——`no available service` 里的 `'default'` 是 **cluster 名**（来自 `vgroupMapping`），不是服务名，容易被误读成“客户端在找名为 default 的服务”从而改错方向。
- 排查过程中试错过的两条死路，别再走：给客户端配置加 `application: seata-server`（1.2.0 不识别该键，且它本来就在查 `seata-server`）；把 TC 的 `application` 改成 `default` 并挪到 public 命名空间（同时改错两个变量）。
- 客户端 1.2.0 + 服务端 1.4.2 这个组合现在功能可用，可长期维持；若将来把客户端升到 1.4.x，则命名 group 会跟随 `seata.registry.nacos.group`，届时需把 TC 的 `registry.nacos.group` 改回 `SEATA_GROUP` 并同步配置，否则又会错开。
- AT 模式还要求每个参与事务的库都有 `undo_log` 表；当前实测存在于 `pd_dispatch` 与 `pinda_tms`。

> 原始 `registry.conf` 备份留在服务器 `/root/registry.conf.pre-grp-exp`，确认稳定后可删除。

> 不用 Seata 时：在各服务配置中设置 `seata.enabled=false`、`seata.service.enable-degrade=true`，可先不启动。

## 十一、部署微服务时的注意事项

微服务已容器化，由 `deploy/apps/docker-compose.app.yml` 编排（14 个 Spring Boot 服务 + `pd-admin-ui`），镜像 tag 取 git 短提交号：

```bash
TAG=<短提交号> docker compose -f deploy/apps/docker-compose.app.yml up -d --remove-orphans
```

两个必须显式注入的地址，原因都是**容器内 `127.0.0.1` 指向容器自身**：

- Nacos：`NACOS_IP` / `NACOS_PORT` / `NACOS_ID` 由 compose 的 `x-nacos-env` 锚点注入，命名空间必须与 `bootstrap` 里写死的 `1cb93ce4…` 一致。
- Redis：`SPRING_REDIS_HOST`、`J2CACHE_LETTUCE_HOSTS`、`REDIS_HOST` 三个都要指到宿主机 IP。j2cache 走的是自己的 lettuce 配置，不吃 `spring.redis.*`，只设前者会出现“Spring 能连、j2cache 回落 127.0.0.1”的半通状态。

各服务 `bootstrap-<profile>.yml` 默认 Nacos 账号为 `pinda/pinda`，但 Nacos 默认账号是 `nacos/nacos`。启动前导出环境变量统一（无需在 Nacos 额外建用户）：

```bash
export NACOS_USERNAME=nacos NACOS_PASSWORD=nacos
# Nacos 地址已在配置中默认指向 192.168.20.130，如需改：
# export NACOS_SERVER_ADDR=192.168.20.130:8848
```

## 十二、常用运维命令

中间件已收敛到 `deploy/middleware/docker-compose.infra.yml`（裸 `docker run` 时代留下的编排缺失是本次排查的主因之一）：

```bash
docker compose -f deploy/middleware/docker-compose.infra.yml up -d          # 全量对齐
docker compose -f deploy/middleware/docker-compose.infra.yml up -d kafka    # 只重建单个服务
docker compose -f deploy/middleware/docker-compose.infra.yml config --quiet # 改完先验语法
bash deploy/middleware/migrate-data.sh status                               # 看现状，不改东西
```

临时排障仍可用 docker 直查：

```bash
docker ps
docker logs -f nacos
docker restart mysql57
```

> **`docker rm` 前必须看第二节的挂载表。** 早先这里写的是 `docker rm -f mysql57 redis nacos kafka zookeeper rabbitmq seata-server   # 数据仍在 /data`——那句注释是错的，按它操作会丢数据：MySQL/Redis 安全；**Kafka 的数据在容器可写层，删了就永久消失**；Nacos 配置库同样在容器层；ZK/RabbitMQ 的卷会变孤儿留在 `/var/lib/docker/volumes/`，新容器不复用、需手工找回。另外 `seata-server` 不是容器，`docker rm -f` 对它只会报 No such container——用 `systemctl`。
>
> 单个容器重建的正确顺序是：`migrate-data.sh <服务>`（复制数据到 `/data` 并删旧容器）→ `docker compose up -d <服务>` → 验证 → 再下一个。

## 十三、常见问题

| 现象 | 原因与处理 |
|---|---|
| `docker pull` 超时 / TLS handshake | 更换 `/etc/docker/daemon.json` 加速器后 `sudo systemctl restart docker` |
| `permission denied ... docker.sock` | `newgrp docker` / 重新登录，或临时加 sudo |
| 服务报 `NacosException / wait server ready` | Nacos 未就绪；确认 `NACOS_SERVER_ADDR` 与 8848 可通 |
| `get config from nacos error` / 空配置 | 命名空间/分组/dataId 未对齐；按 6.3 重新导入（注意 `scripts/push-nacos-config.sh` 并不存在于本仓库） |
| 报表不存在 (`Table ... doesn't exist`) | 服务连错库；核对“微服务→库映射”，数据源 URL 库名是否正确 |
| Kafka 连不上、超时 | `KAFKA_ADVERTISED_LISTENERS` 必须是宿主机 IP |
| MyBatis `Invalid bound statement` | mapper-locations：业务服务为 `/mapper/**`，pd-auth 为 `/mapper_authority/**` |
| RabbitMQ 资源/账号失败 | 管理界面确认 pinda 与 .env 里的口令；队列由 pd-dispatch 自动声明 |
| Seata 事务失败 / 服务刷 `no available service 'default' found` | 先看第八节的 naming group 坑：TC 必须注册在 `DEFAULT_GROUP`。用 `register RM/TM success` 确认连通，`'default'` 是 cluster 名不是服务名；另核对 `vgroupMapping` 与参与库的 `undo_log` 表 |
| 服务报 `Too many open files`，但看着像内存泄漏 | 容器 `nofile` 软限默认只有 **1024**（`docker inspect -f '{{range .Mounts}}'` 查不出来，要在容器内看 `ulimit -n`）。长连接的 pd-gateway / pd-netty 最先中招；`deploy/middleware/docker-compose.infra.yml` 里的 `x-ulimits` 已统一提到 65535，应用侧 compose 同样要加 |
| MySQL `Too many connections` / Druid 取连接超时 | 8 个带数据源的服务各自 Druid `max-active=50`（合计 400），超过出厂的 `max_connections=151`。平时 `Threads_connected` 只有 41（8×5 的 initial-size）看着没事，一压就爆。已把服务端调到 500；更省内存的做法是把 Druid `max-active` 降到 20 |
| 服务莫名变慢、GC 停顿尖刺，但内存没满 | 检查是否发生了 swap 换入换出。本机已设 `vm.swappiness=10`，避免 JVM 匿名页被提前换出；swap 与数据在同一块虚拟盘上，一旦开始换页会同时拖垮 IO |
| 构建/服务偶发卡住几十秒 | 单盘 IO 已接近饱和（实测 `sda` `%util` 99.8%、`w_await` 67ms）。MySQL 缓冲池已从 128M 提到 1G 以减少读落盘；根治要加第二块盘，把 `/data` 或 Docker 数据目录迁过去 |
