## 一、项目定位与目标用户

### 1.1 项目定位

> **品达物流 TMS 是一套面向"自营 / 加盟运输管理"的运输管理系统（Transportation Management System）。**

它管理的是**货物从寄件到签收的全过程**：寄件下单 → 上门取件 → 干线运输 → 末端派送 → 电子签收 → 结算对账。

**必须厘清的边界**（本项目**不是**什么）：

| 不是 | 说明 |
|---|---|
| ❌ 快递网络系统 | 不对接顺丰/中通/圆通等外部厂商 API（无 EDI/X12 对接） |
| ❌ 网络货运平台 | 不做运力撮合交易、不做税务套利、不涉及"网络货运"资质 |
| ❌ WMS 仓储系统 | 仓储（库存/上架/拣货）非本期范围，仅预留边界 |
| ✅ **运输管理 TMS** | 管理自己的/加盟的车队、司机、网点、线路、客户 |

### 1.2 目标用户与核心诉求

| 角色 | 载体 | 核心诉求 | 关键指标 |
|---|---|---|---|
| **平台管理员** | 管理端 Web（升级目标 Vue3） | 看得见全局、控得住风险 | 时效达成率、异常闭环率 |
| **调度员** | 管理端 Web | 派单派车要快、空驶要少 | 空驶率、调度时长、线路匹配率 |
| **司机** | App（uni-app） | 今天干什么、跑哪条线 | 任务完成率、里程、油耗 |
| **快递员** | App（uni-app） | 单量、绩效、少扯皮 | 单量、投递合规率 |
| **客户** | 小程序 | 我的货到哪了、运费多少 | 查单成功率、投诉率 |
| **财务/结算** | 管理端 Web | 算得清、对得上 | 对账差异率、结算周期 |

### 1.3 业务模式前提（决定功能取舍）

- 本项目是**自营/加盟运输管理**，运力来源有自有车与外协车；
- 因此**需要"外协运力池 + 抢派双模"**（自有车优先、不够时外协补）；
- 但**不做**面向社会的运力交易撮合平台（无保证金/无抽佣/无双向评价体系）。

### 3.2 cortex-tms — 架构与领域设计参考

> 来源：GitHub `cortex-tms/cortex-tms`；Spring Boot + **DDD 领域驱动** + 微服务

| 维度 | cortex-tms 设计思路 |
|---|---|
| **架构哲学** | "**核心流程闭环，扩展灵活**"——内置从订单到结算的主干流程，预留扩展点 |
| **服务拆分** | order-service（订单与状态流转）/ dispatch-service（调度算法）等按领域拆 |
| **调度算法** | 当前按车辆空闲状态 + 粗略位置派单，**算法引擎可替换**为更智能的实现 |
| **通知机制** | 默认站内信 + 邮件，**预留短信/企微/钉钉集成点** |
| **基础数据要义** | "很多实施失败的项目，问题都出在基础数据没整理好"——车辆要区分**自有/外协/临时**，客户要区分**月结/现结**与计价方式（按票/按吨/按方） |

> 💡 **其可借鉴点**：
> - **运力类型维度**（自有/外协/临时）——本项目外协运力池的基础
> - **客户计价方式维度**（按票/按吨/按方）——本项目运费规则的输入
> - **调度算法可替换**——本项目 DFS 路径规划的演进方向（预留 VRP 接口）

## 四、目标与成功指标

### 4.1 项目目标

| 层级 | 目标 |
|---|---|
| **业务目标** | 让运输全过程**可视、可控、可结算**，降低空驶与差错 |
| **产品目标** | 四端（管理/司机/快递员/客户）形成**完整业务闭环** |
| **合规目标** | 满足 2026 物流合规要求（投递确认、北斗监控、数据安全），**避免上线即处罚** |

### 4.2 成功指标（可衡量）

| 指标 | 口径 | 目标值 | 备注 |
|---|---|---|---|
| 状态机一致性 | 跨端状态不一致的工单数 | **0** | 依赖双向同步桥打通 |
| 调度响应时长 | 订单创建→生成运输任务 | ≤ **5 分钟**（自动调度） | 待建 |
| 空驶率 | 空载里程 ÷ 总里程 | 下降 **10%**（相对基线） | 依赖成本看板先上线 |
| 查单成功率 | 客户查轨迹成功率 | ≥ **99%** | 当前无 orderId 查询，需改造 |

> ⚠️ **里程碑定义**：M0 = 需求与基线锁定（即本需求文档 v2.4 发布，环境实测基线已就绪）；M1–M6 = 详见《产品差距与商业化升级路线图.html》。上述指标需在 **M0 阶段锁定基线值**（当前无业务数据，需先跑通下单→调度流程产生样本），否则无法验收。

## 六、核心业务流程设计

### 6.1 主流程（12 状态，代码已实现）

```
①客户下单          ②取件              ③干线运输              ④末端派送         ⑤签收
客户小程序    →   快递员/网点    →   司机运输           →   快递员派送    →   客户签收
pd_order            pd_task_           pd_task_transport    pd_task_pickup_   RECEIVED
status=23000        pickup_dispatch    status 5级          dispatch
                                                                              ↓
                    23000 待取件 →（上门取件：23001 已取件 / 网点自寄：23002 网点自寄 → 23003 网点入库）
                    → 23004 待装车 → 23005 运输中 → 23006 网点出库 → 23007 待派送 → 23008 派送中
                    → 23009 已签收 / 23010 拒收 / 23011 已取消
                    （2026-10-08 业务功能审查回写：补全网点自寄路径 23002/23003，与数据字典 §一对齐）
```

**状态机约束**：状态变更必须走 `StateTransitionValidator` + 条件更新（`eq(status=期望值)` 做 CAS 防并发），**禁止**裸 `setStatus()`。

**订单取消业务规则（2026-10-08 用户业务拍板：Q-6）**：
- **可取消阶段**：待取件（23000）状态下客户可自助取消，取消后全额退款（按原支付渠道退回）。
- **不可取消阶段**：已取件（23001）及之后的所有状态（含网点自寄/入库、待装车、运输中、网点出库、待派送、派送中）均不可自助取消——货物已在物流链路中，取消需走异常/退回流程，不走订单取消状态机。
- **取消触发方**：客户小程序自助取消（限待取件阶段）；管理员管理端可在任何阶段发起取消（走人工审核，非自助）。
- **取消后退款**：待取件取消 → 自动全额退款；管理员人工取消 → 按实际发生费用扣除后退款（人工核定）。

## 十四、产品差距与商业化升级路线图

> 本节为产品战略视角补充，完整版见 **《产品差距与商业化升级路线图》（`../产品差距与商业化升级路线图.html`）**。

### 14.1 当前定位与核心结论

品达 TMS 当前本质是一个**教学/演示级脚手架**：业务领域建模完整度（12 级状态机、调度 5 阶段、DFS、Drools）在同类开源中属中上，但离"生产可用"和"商业产品"仍有**代际差距**。若用于学习/内部演示/小范围自用，现状已合格；若要商业化，需系统性补齐。

### 14.2 十维度能力成熟度（摘要）

| 维度 | 本项目 | 生产级 | 商业 SaaS | 差距 |
|---|---|---|---|---|
| 业务建模完整性 | 4.0 | 4.5 | 5.0 | 无差距 |
| 架构/技术栈现代性 | 2.0 | 4.0 | 4.5 | 🔴 A 级 |
| 可观测性/监控 | 0.5 | 4.0 | 4.5 | 🔴 A 级 |
| 高可用/弹性 | 1.0 | 4.0 | 5.0 | 🔴 A 级 |
| 安全合规 | 1.5 | 4.0 | 4.5 | 🟠 B 级（当前决策暂不处理） |
| 移动端/IoT | 2.0 | 3.5 | 5.0 | 🟠 B 级 |
| DevOps/自动化 | 2.0 | 4.0 | 4.5 | 🟡 C 级 |
| 数据智能/算法 | 1.5 | 3.5 | 5.0 | 🟠 B 级 |
| 测试质量 | 0.5 | 3.5 | 4.0 | 🔴 A 级 |
| 多租户/SaaS | 0.0 | 3.0 | 5.0 | 🔴 A 级（商业化最大短板） |

**A 级硬伤**：架构停更（JDK8/Zuul1.x，无 Sentinel）、可观测性为零、高可用单点、测试护栏缺失。

### 14.3 三期演进路线（与本文 FR 映射）

| 阶段 | 时间 | 目标 | 对应本文功能 | 退出标准 |
|---|---|---|---|---|
| **一期·地基** | 0–3 月 | 从"能跑"到"敢上线" | **FR-30/31/36 合规硬闸口** + FR-32~35 合规 P1 + 安全/可观测/高可用/测试护栏 | 压测达标、监控告警闭环、P0 安全清零 |
| **二期·产品力** | 3–9 月 | 从"可用"到"好用" | FR-10~15 三端 + FR-40~48 + 财务结算 FR-50~52 + 北斗/视频 FR-58/59（2026-10-08 二轮审查回写：FR-10~15 三端、FR-40~48、FR-50~52 财务已前移至 P0（W1–W8），本节为原始二期规划，仅作远期参考；依据 BA-17） | 移动端日活验证、调度提效、结算对账通过 |
| **三期·商业化** | 9–18 月 | 从"单系统"到"平台" | 多租户 SaaS（本文未覆盖，需立项）+ BI 驾驶舱 + 生态对接 | 多租户生产验证、首批付费客户 |

> ⚠️ **本文 §5 功能清单（FR-xx）主要覆盖一期/二期范围**；多租户 SaaS、BI 驾驶舱、生态对接（ETC/油卡/保险/支付）属三期，需单独立项，不在当前 MVP/P1/P2 内。

### 14.4 商业化升级的组织与风险

- **团队**：建议后端 3–5 / 前端移动 2–3 / 数据算法 1–2 / SRE 1–2 / 测试 1–2，产品 1–2。
- **关键风险**：技术栈锁定（JDK8/停更组件）需渐进式升级；安全漏洞上线前必须重评；无测试护栏致回归风险，一期即补。
