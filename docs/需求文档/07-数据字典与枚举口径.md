# 数据字典与枚举口径（跨端唯一真源）

> **日期**：2026-10-06
> **来源**：从源码 `pd-service-api` 的 16 个枚举类**逐条提取真实取值**（非推测；计数口径 = `grep -rl "public enum" pd-service-api --include=*.java` 去 target 后实测 16）
> **用途**：三端 + 管理端 + 后端**共用同一套口径**，避免"同一个状态各端理解不同"导致的跨端 bug
> **价值**：状态值是本项目跨端 bug 的第一高发点（前端写死 23005、后端返回 23006、测试按 6 理解…），本表是唯一裁决依据

---

## 〇、使用规则（先读，否则本表会被用错）

| 规则 | 说明 |
|---|---|
| **① 禁止在前端硬编码数字状态** | 一律用后端返回的 `code`，中文名只用于**展示**。前端写 `status == 23005` 是 bug 源头 |
| **② 本表是唯一口径** | 文档、代码注释、数据库取值**冲突时以本表为准**（本表由源码提取） |
| **③ 新增枚举必须回写本表** | 后端加状态而本表未更新 → 视为未完成（DoD 卡点） |
| **④ 状态流转必须走校验器** | `StateTransitionValidator` 已实现且在用，**禁止绕过**（详见 §7） |
| **⑤ 中文名仅供展示** | 枚举第二个参数是**英文名**（如 `IN_TRANSIT`），中文对照取自 `OrderDTO` 注释，**两者都要以本表为准** |

## 一、订单状态 `Order.status`（12 级，核心中的核心）

> 源码：`pd-service-api/pd-service-oms-domain/.../enums/OrderStatus.java`
> ⚠️ 枚举类里只有英文名，**中文对照取自 `OrderDTO.java:144` 注释**（已交叉核对）

| code | 枚举名 | 中文含义 | 客户视图档位（7 档） | 阶段 |
|---|---|---|---|---|
| 23000 | `PENDING` | 待取件 | ① 待取件 | 下单后 |
| 23001 | `PICKED_UP` | 已取件 | ② 已取件待发货 | 取件 |
| 23002 | `OUTLETS_SINCE_SENT` | 网点自寄 | ② 已取件待发货 | 网点 |
| 23003 | `OUTLETS_WAREHOUSE` | 网点入库 | ② 已取件待发货 | 网点 |
| 23004 | `FOR_LOADING` | 待装车 | ② 已取件待发货 | 装车 |
| 23005 | `IN_TRANSIT` | **运输中** | ③ 运输中 | 干线 |
| 23006 | `OUTLETS_EX_WAREHOUSE` | 网点出库（名实见下方注释） | ③ 运输中 | 网点 |
| 23007 | `TO_BE_DISPATCHED` | 待派送 | ④ 派送中 | 末端 |
| 23008 | `DISPATCHING` | **派送中** | ④ 派送中 | 末端 |
| 23009 | `RECEIVED` | 已签收 | ⑤ 已签收 | 终态 |
| 23010 | `REJECTION` | 拒收 | ⑥ 已拒收 | 异常终态 |
| 23011 | `CANCELLED` | 已取消 | ⑦ 已取消 | 异常终态 |

### 🚨 发现的代码注释笔误
`OrderDTO.java:144` 注释末尾写的是 **`230011`为已取消** —— **多了一个 0**。
✅ 正确值是 **`23011`**（见 `OrderStatus.CANCELLED`）。
**引用该注释时务必纠正**，否则会造出永不命中的状态判断。

### ⚠️ 23006 `OUTLETS_EX_WAREHOUSE` 名实注释（易误解）
枚举名与字面含义是"网点出库"，但它**不是网点操作员手动做出库产生的**：在状态机联动中由**司机干线到达/交付**触发——`pd-web-driver CargoController#finish`（`CargoController.java:652`）在司机 `PUT /business/cargo/finish` 时把订单置为 23006（`TaskTransportServiceImpl.java:434` 同口径）。
真实语义是"**干线货物已送达目的网点，进入末端派送前置**"（介于 23005 运输中 与 23007 待派送之间）。因此客户视图仍归入 **③ 运输中** 档，不要因名字带"出库"就归到派送档。

### 客户视图 7 档映射（客户端展示用，2026-10-09 拍板）
客户不关心 12 个细分状态，只看 7 档（拒收、取消各单列一档；与《01-业务需求全景》§四映射表一致）：

| 客户档位 | 覆盖的 code |
|---|---|
| ① 待取件 | 23000 |
| ② 已取件待发货 | 23001、23002、23003、23004 |
| ③ 运输中 | 23005、23006 |
| ④ 派送中 | 23007、23008 |
| ⑤ 已签收 | 23009 |
| ⑥ 已拒收 | 23010 |
| ⑦ 已取消 | 23011 |

> ⚠️ **映射必须查表实现，严禁区间判断**。写成 `status >= 23001 && status <= 23004` 是错的——一旦中间插入新状态就会漏。
> 建议后端在 DTO 里直接多返回一个 `customerStatus` 字段，由后端统一映射，前端不做区间判断。

## 七、状态机约束（枚举之外的强制规则）

### 7.1 校验器已实现，**禁止重写**

`StateTransitionValidator`（pd-work）已实现并在用：

| 调用方 | 行号 |
|---|---|
| `TaskTransportServiceImpl` | 243 / 287 / 331 |
| `TransportOrderServiceImpl` | 74 / 84 |

- 已覆盖：订单 12 级 + 运单双维度 + 运输任务 5 级。
- **真实缺口是"跨端同步桥"**（如司机发车未联动 `Order` 23005），**不是校验器本身**。
- ❌ 严禁新建/重写状态机；✅ 缺什么补什么。

### 7.2 状态更新必须带条件（防并发覆盖）

`TaskTransport.depart/arrive/deliver` 用 `LambdaUpdateWrapper + eq(status=期望值)` 做条件更新（**状态机守卫 / CAS**），全项目**无 `@Version` 乐观锁**。

> ⚠️ 新增状态变更接口时**必须沿用条件更新**，不要直接 `setStatus()`——否则并发下会状态错乱。

## 十、枚举使用规范（DoD 卡点）

开发/评审时逐条检查：

- [ ] 前端**未硬编码**任何状态数字（`status == 23005` ❌）
- [ ] 状态展示**中文名**来自统一映射表，非前端自造
- [ ] 客户视图 **7 档**（§一映射表）由**查表**实现，非区间判断
- [ ] 新增状态时：改枚举 → **回写本表** → 更新状态机校验 → 通知三端
- [ ] 状态变更接口**带条件更新**（`eq(status=期望)`），非裸 `setStatus`
- [ ] 跨端对接时按**枚举类**区分 `CONFIRM`（司机作业=改派 / 运输任务=待确认）
