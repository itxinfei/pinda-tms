# 多端数据打通与统一领域模型（客户 / 快递员 / 司机 三端共享数据源）

> 本文档是三端（客户小程序、快递员端、司机端）任务卡的**前置架构契约**。
> Claude Code 在实现任意一端的任意页面前，必须先读本文档。
> 违反本文档"硬性契约（§6）"的改动一律视为 bug，无论单端功能是否跑通。

---

## 0. 为什么必须有这份文档（用户硬要求）

用户原话："几个用户端数据必须是通的"。

含义：**客户下单 → 快递员取派 → 司机运输，整条链路共享同一份业务数据**，而不是各端各建一套、各自缓存副本。三端看到的是同一批记录的**不同投影（projection）**，不是三份独立数据。

调研成熟产品（顺丰"青龙"、京东物流、菜鸟、满帮、G7、货拉拉）得出的共同做法，全部指向同一原则：

1. **单一数据源（Single Source of Truth）**：订单/运单/运输任务只有一份主记录，各端只读投影。
2. **统一 ID**：订单号即运单号即查询主键，一个订单可拆多包裹/多运单，靠稳定 ID 串联。
3. **统一状态机**：状态 + 子状态 + 原因码，由**状态表/状态机集中驱动**，严禁散落的 `if/else` 与直接 `setStatus`。
4. **事件总线**：状态变更发事件（本项目已有 Kafka/RabbitMQ + `OrderConfirmedEvent`），各端订阅刷新。
5. **实时同步**：WebSocket / MQTT 秒级推送；轨迹走专用通道（本项目已由 `pd-netty` + Kafka 承接）。

本项目**链路主键已经存在**，但**状态桥与轨迹查询入口有断点**（见 §4、§5）。本文档把它们补成可执行的契约。

## 1. 现状核对：真实实体与关联链路（基于代码，非设计）

以下实体与字段均来自 `pd-oms` / `pd-work` / `pd-netty` 实测代码，是"单一数据源"的物理落地。

### 1.1 实体清单

| 实体（表） | 模块 | 角色 | 关键字段 |
|---|---|---|---|
| `Order` (pd_order) | pd-oms | **客户订单主记录**，客户/快递员可见状态的载体 | `id`(订单号/运单号)、`memberId`、`paymentMethod`、`paymentStatus`、`amount`、`status`(23000–23011)、收/发件人信息 |
| `OrderCargo` (pd_order_cargo) | pd-oms | 货物明细 | `orderId`、`tranOrderId`(运单id)、`goodsTypeId`、`weight`、`volume` |
| `TransportOrder` (pd_transport_order) | pd-work | 调度生成的运单 | `id`、`orderId`(外键→Order) |
| `TransportOrderTask` (pd_transport_order_task) | pd-work | 运单↔运输任务关联 | `transportOrderId`、`transportTaskId` |
| `TaskTransport` (pd_task_transport) | pd-work | **司机运输任务主记录**，司机可见状态的载体 | `id`、`truckId`、`status`(1–5)、计划/实际发车·到达·提货·交付时间、经纬度 |
| `DriverJob` (pd_driver_job) | pd-work | 司机作业记录 | `id`、`driverId`、`taskTransportId`(外键→TaskTransport)、`status`(1–5) |
| `LocationRecord` (pd_truck_location) | pd-netty | GPS 轨迹明细 | `businessId`(车辆/快递员id)、`transportTaskId`、`type`(truck/courier)、`lng`、`lat`、`currentTime` |

> 单号说明：`Order.id` 由 `CodeGenerate` 生成 8 位编码，**同时充当客户查询用的"运单号"**。没有独立 `trackingNo` 字段——客户凭 `Order.id` 查全程。

### 1.2 关联链路图（单一数据源的物理串联）

```
客户 Order.id (运单号)
   │  orderId
   ▼
TransportOrder (运单)
   │  transportOrderId
   ▼
TransportOrderTask ── transportTaskId ──▶ TaskTransport.id (司机运输任务)
   │                                         │ taskTransportId
   ▼                                         ▼
OrderCargo (货物)                        DriverJob (司机作业)
                                           │
                                           ▼
                                      LocationRecord.transportTaskId (轨迹)
                                      LocationRecord.businessId (车辆/快递员 id)

客户可见状态  = Order.status        (12 级: 23000~23011)
司机可见状态  = TaskTransport.status (5 级: 1~5)  ↔ DriverJob.status
快递员操作对象 = Order (取件/派送阶段) + OrderCargo + POD
```

**结论**：三端在物理上已经指向同一批记录，链路主键完整。问题不在"有没有"，而在"状态怎么互相同步"和"客户怎么查到自己的轨迹"——见 §4、§5。

## 2. 三端投影模型（同一份数据，不同可见性）

| 端 | 读取的主记录 | 写操作 | 可见状态范围 |
|---|---|---|---|
| **客户端**（客户小程序） | `Order`（仅本人 `memberId`）、`OrderCargo`、`LocationRecord`（经 §5 解析） | 下单、支付、评价、查件 | `Order.status` 全 12 级（映射为客户 3~4 档视图，见 §4.3） |
| **快递员端** | `Order`（取件 23000–23003、派送 23007–23009）、`OrderCargo`、本人 `LocationRecord` | 取件确认、POD 电子签收、异常上报、派送 | 取件/派送阶段状态 + POD |
| **司机端** | `TaskTransport`/`DriverJob`（`driverId`=本人）、`LocationRecord`（本人 `businessId`） | 发车/到达/交付、轨迹上报、异常 | `TaskTransport.status` 1–5 + 轨迹 |

**铁律**：任何一端**不得**维护本端私有的"订单状态副本"。所有状态以 `Order.status` / `TaskTransport.status` 为准，前端只做展示映射。

## 3. 状态机打通契约（核心）

### 3.1 两套状态机必须可互相推导

| 业务阶段 | 客户/快递员可见 `Order.status` | 司机可见 `TaskTransport.status` / `DriverJob.status` | 状态变更触发方 |
|---|---|---|---|
| 下单·待取件 | 23000 待取件 | （尚无运输任务） | 客户下单 |
| 已揽收 | 23001 已取件 | — | 快递员取件 |
| 网点自寄/入库 | 23002 / 23003 | — | 网点 |
| 干线待发/运输中 | 23004 待装车 → **23005 运输中** | **2 进行中（在途）** | **司机发车 depart** |
| 到达终端网点 | **23006 网点出库** | **4 已完成（交付）** | 司机交付 deliver |
| 到达待确认 | 23006（不变） | **3 待确认（司机到达 arrive）** | 司机到达 arrive |
| 末端待派/派送中 | 23007 待派送 → 23008 派送中 | —（转入快递员域） | 快递员派送 |
| 已签收 | **23009 已签收** | — | 快递员妥投 `delivered` |
| 拒收 | 23010 拒收 | — | 快递员 |
| 取消 | 23011 已取消 | 5 已取消 | 任一端（需权限） |

### 3.2 现状核对（已核实，勿重复造轮子）

✅ **状态机校验器已存在且已被调用**：`pd-work` 的 **`StateTransitionValidator`**（`com.itheima.pinda.state`，2026-07-01）已完整实现四张流转图——订单 12 级、运单 `status`、运单 `schedulingStatus`（**双维度分离，避免 code 冲突**）、运输任务 5 级，并提供 `validateXxxTransition()` 与 `getAllowedNextXxxStatuses()`。
已被以下位置**实际调用**：
- `TaskTransportServiceImpl` 第 243 / 287 / 331 行（depart / arrive / deliver 三处均校验）
- `TransportOrderServiceImpl` 第 74 / 84 行（运单 status + schedulingStatus）
- `OrderServiceImpl` 注释明确"与 pd-work 的 StateTransitionValidator 保持一致"

❌ **真正的缺口是「双向同步桥」，不是「校验器」**：
- 司机**发车**（`TaskTransport`→2 进行中）时，**未联动把 `Order.status` 置为 23005 运输中**——客户看不到"运输中"。
- 司机**交付**时虽通过 Feign 回写了 `TransportOrder`(4) 与 `Order`(23006 网点出库)（411–435 行），但同步逻辑**散落在 service 方法内**，新增节点（如派送中/已签收）易漏改。
- 即：**自身状态有校验 ✅，跨端联动同步缺失 ❌**。

**结论：不要新建状态机，也不要替换 `StateTransitionValidator`。要补的是"状态变更 → 联动对方状态"的同步桥。**

### 3.3 修正方案（给 Claude Code 的强制要求）

1. **复用现有一切，只补同步桥**：**严禁新建/重写状态机**——`StateTransitionValidator` 已完备且已被调用。所有状态跃迁继续用它做校验；要新增的是**状态变更后的跨端联动同步逻辑**（收口到一个同步组件，禁止散落 `feign.updateById(status)`）。**落点（✅ 已定案）**：`pd-work` 新建 `StateSyncService`（`state/sync` 包），统一承接"司机 depart→Order 23005、司机 deliver→Order 23006、快递员 delivered→Order 23009"等联动；`pd-oms`/`pd-web-courier` 通过 Feign 调用它，或由 `pd-work` 状态机在跃迁后主动调 `pd-oms`（`OrderApi`）更新。**失败补偿**：联动写失败发 MQ 事件（复用 `OrderEventMQListener` 通道），由消费端重试 + 管理端告警；MVP 阶段允许客户端轮询 ≤15s 兜底（契约 C5），不要求强一致。
2. **双向同步**：任一端触发状态跃迁，状态机负责把**另一侧**对应状态一并算出并落库（如司机 depart → 同时把 `Order` 置 23005；司机 deliver → `Order` 置 23006；快递员 delivered → `Order` 置 23009）。
3. **状态白名单**：必须经 `StateTransitionValidator` 白名单校验（允许 23004→23005，禁止 23000→23009），非法跃迁拒绝并记录。
   （❗措辞修正：是**白名单单向校验**，不是"可逆"——不支持逆向跃迁/回滚）
4. **原因码**：异常/拒收/改派必须带 `reasonCode`，便于溯源（参考调研中的 GS1/承运商原因码）。

## 4. 轨迹打通契约（核心）

### 4.1 现状断点

`pd-netty` 的轨迹接口（实测）：

- `GET /trace/replay?businessId=&type=` → 按 **businessId（车辆/快递员 id）** 查完整轨迹
- `GET /trace/latest?businessId=&type=` → 按 **businessId** 查最新点
- `POST /trace/page` → 支持 `transportTaskId` 过滤（但 /latest、/replay 不支持）

**断点**：客户想看"我的包裹到哪了"，手里只有 `Order.id`（运单号），**没有 truckId**。`/trace/latest`、`/replay` 不接受 `orderId` 或 `transportTaskId`，导致**客户端无法查询自己订单的轨迹**。链路在查询入口断掉。

### 4.2 打通契约（强制）

1. **客户查轨迹必须凭 `orderId`**：新增/改造一个客户侧轨迹查询入口，后端按 `Order.id → TransportOrder.orderId → TransportOrderTask.transportTaskId → LocationRecord.transportTaskId` 解析出轨迹，返回给客户。**严禁要求客户提供 truckId。**
2. **`/trace/latest`、`/trace/replay` 增加 `transportTaskId` 入参**（`LocationRecord` 已有该字段，无需改表），支持按运输任务查轨迹。
3. **司机/快递员查轨迹**仍按本人 `businessId` + `type` 查（不变）。
4. 轨迹数据三端同源：客户看到的轨迹 = 司机上报的轨迹 = `LocationRecord` 表，不得各端另存副本。

### 4.3 客户状态档位映射表（Order.status → 客户视图）

客户小程序**只展示 4 档视图**，底层仍是 `Order.status` 12 级（单一数据源，前端不私存副本，符合 C1）。

| 客户档位 | 客户可见文案 | 映射的 Order.status（12 级） | 阶段说明 |
|---|---|---|---|
| 1 · 待取件 | 已下单，等待揽收 | `23000` 待取件 | 客户下单后、快递员揽收前 |
| 2 · 运输中 | 已揽收，干线运输 | `23001` 已取件 / `23002` 网点自寄 / `23003` 入库 / `23004` 待装车 / `23005` 运输中 / `23006` 网点出库 | 揽收 → 到达终端网点 |
| 3 · 派送中 | 快件派送中 | `23007` 待派送 / `23008` 派送中 | 转入快递员域 |
| 4 · 已完成 | 已签收 | `23009` 已签收 | 终态（成功） |
| 4 · 异常 | 已拒收 / 已取消 | `23010` 拒收 / `23011` 已取消 | 终态（异常/取消分支） |

**映射实现要求**：
- 前端/BFF 用**纯查表**（按 `status` 码 `switch`）映射档位，**禁止**用区间判断或字符串匹配；
- 新增 12 级状态时**必须同步更新本表**（否则客户视图缺档）；
- 司机侧 `TaskTransport.status`（5 级 1~5）与快递员侧阶段映射见各自任务卡，本表仅描述客户视图；
- 状态文案可随 UI 规范本地化，但**档位与状态码绑定关系不可变**。

## 5. 实时同步方案（不引入新中间件）

遵守「**不引入新中间件**」硬约束、**复用现有能力**（⚠️ 2026-10-08 订正：原文此处写"不升级技术栈"，该口径已于同日**全栈升级决策废止**——现为"按升级基线（JDK21/SB3.3）迁移，但**不引入路线图里的新中间件**"）：

| 同步内容 | 机制（现有栈内） | 说明 |
|---|---|---|
| 状态变更推送 | Kafka / RabbitMQ 事件（已有 `OrderConfirmedEvent`/`OrderEventMQListener`）+ 各端**轮询兜底** | 状态变更发事件，三端订阅刷新；MVP 阶段用轮询（如客户每 10~15s 拉一次 `Order.status`）即可，不强制 WebSocket |
| 轨迹实时 | `pd-netty`（Netty + Kafka）已承接 GPS 上报；前端读 `/trace/latest` 轮询或 WebSocket 推 | 轨迹通道已具备，无需新中间件 |
| 可选增强 | **Spring WebSocket**（属 Spring Boot 现有依赖，非新中间件） | 若要做秒级状态推送，用 Spring WebSocket；不引 MQTT/新消息队列 |

**禁止**：为"实时"引入 MQTT、Redis Pub/Sub 等当前技术栈之外的新组件。

## 6. 硬性契约（Claude Code 红线，违反即 bug）

> C1 **单一数据源**：任何端不得维护独立的状态副本；前端状态永远来自 `Order.status` / `TaskTransport.status`。
>
> C2 **统一状态机**：所有状态跃迁必须经由集中状态机/流转服务，禁止在业务方法里散落 `setStatus` / `feign.updateById(status)` 绕过校验。
>
> C3 **双向同步**：`Order.status` 与 `TaskTransport.status` 必须可互相推导；司机 depart 必须同步 `Order`→23005 运输中，司机 deliver 必须同步 `Order`→23006，快递员 delivered 必须同步 `Order`→23009。
>
> C4 **客户轨迹可用订单号查**：客户查轨迹只凭 `Order.id`，后端解析到 `transportTaskId`；`/trace` 接口必须支持 `transportTaskId` 入参。严禁前端要求客户传入 truckId。
>
> C5 **终态一致**：司机交付 / 快递员签收后，客户端必须在**秒级（轮询 ≤15s）**内看到对应终态与轨迹更新。
>
> C6 **不引新中间件**：实时同步只用 Kafka/RabbitMQ/Netty/轮询/Spring WebSocket，不引 MQTT 等栈外组件。

## 7. P0-1 状态桥修复任务 PRD 必选模块（2026-10-07 补入）

> 本节把 P0-1 任务（状态机断点 1 修复 + 客户按 `Order.id` 查轨迹端点）按 PRD 标准补全 5 个必选模块 + 合规模块，与 §3.3 修正方案、§4.2 打通契约配套使用。任务整体工作量 0.5-1 人日（W1 内完成），依据《02-优先级总览.md》P0-1 行 + 《_需求审查归档/文档与代码一致性核查报告.md》§三 偏差 7 + 本文件 D-03/D-04/D-02/D-17。

### 7.1 需求背景与目标用户

#### 7.1.1 触发源与量化痛点

`TaskTransportServiceImpl.depart()` 现状（2026-10-05 源码实测，见《_需求审查归档/文档与代码一致性核查报告》§三 偏差 7）：第 243 行起校验 `TaskTransport` 状态 1→2 通过后，仅更新 `pd_task_transport.status=2` 与 `actualDepartureTime`，**未通过 Feign 回写 `pd_oms.pd_order.status=23005 运输中`**。同样，`/trace/latest`、`/trace/replay` 只接受 `businessId`（车辆/快递员 id），客户凭订单号查轨迹无解。由此产生 3 项可量化痛点：

| 痛点 | 当前表现 | 业务影响 | 量化口径 |
|---|---|---|---|
| 客户看不到"运输中"档位 | 司机发车后，客户小程序仍停留在"已取件"（对应 `Order.status=23001`），最长持续到交付才跳到"网点出库" | 客户误以为包裹滞留，客服咨询量上升 | 客户小程序状态滞后率 = 100%（发车后 1 小时内查件仍看不到运输中） |
| 客户凭订单号查轨迹无解 | 客户手里只有 `Order.id`（运单号），无 `truckId`/`transportTaskId`；`/trace/*` 不接受 `orderId` | 客户无法自助查"包裹到哪了"，电话问询占比高 | 月度客户咨询中"车到哪了/包裹到哪了"类占比 ≥40% |
| 状态联动散落在 service 方法 | 仅 deliver 环节回写运单（4）与订单（23006），depart/arrive 不写；新增节点易漏改 | 跨端联动靠人工记忆，状态机校验已有但同步桥缺失 | 跨端联动节点覆盖率 = 1/4（仅 deliver，depart/arrive/courier-delivered 三处缺口） |

行业对标（顺丰"青龙"、京东物流）：订单状态变更与司机执行动作秒级联动，客户凭运单号可全程可视化。

#### 7.1.2 目标用户与角色权限矩阵

| 角色 | 触发动作 | 可见状态范围 | 可执行操作 | 不可执行 |
|---|---|---|---|---|
| 客户 | 查件（凭 `Order.id`） | 本人订单 `Order.status` 全 12 级 → 4 档视图（§4.3） | 输入订单号查状态 + 查轨迹 | 看到他人订单 |
| 司机 | 发车 depart | 本人 `TaskTransport.status` 1→2 | 触发状态跃迁 + 联动写 `Order.status=23005` | 跳过状态机校验 |
| 快递员 | 派送 delivered | `Order.status` 23007→23009 | 触发状态跃迁 + 联动写 `Order.status=23009`（走 §3.3 同步桥） | — |
| 调度员（内部） | 监控状态联动 | 全部订单状态 | 查询状态联动日志 + 异常补偿记录 | 修改状态（绕过状态机） |

> **数据隔离实现**：客户查轨迹只凭 `Order.id`，后端按 `Order.memberId = 当前 JWT userid` 鉴权（网关 `TokenContextFilter` 注入 `userid`）；司机/快递员只触发本人 `TaskTransport`/`DriverJob` 的状态跃迁，Feign 调用入参带 `driverId`/`courierId` 校验。

#### 7.1.3 核心使用场景

| # | 场景 | 角色 | 触发条件 | 系统响应 |
|---|---|---|---|---|
| 1 | 司机发车联动 | 司机 | 司机在司机端 App 点"发车" | depart 接口校验状态机 → `TaskTransport.status=2` + 联动 `Order.status=23005` → 客户秒级看到"运输中" |
| 2 | 客户凭订单号查轨迹 | 客户 | 客户在小程序输入 `Order.id` 查件 | 后端解析 `Order.id → TransportOrder.orderId → TransportOrderTask.transportTaskId → LocationRecord.transportTaskId` → 返回轨迹 |
| 3 | 司机交付联动 | 司机 | 司机在司机端点"已交付" | deliver 接口校验状态机 → `TaskTransport.status=4` + 联动 `Order.status=23006` + 异常补偿记录 |

#### 7.2.3 实现要点

- **StateSyncService 落点**（§3.3 已定案）：`pd-work` 新建 `state/sync` 包，统一承接 depart/arrive/deliver/courier-delivered 四处联动；`TaskTransportServiceImpl` 在原 depart/arrive/deliver 方法内调 StateSyncService，不直接写 `feign.updateById(status)`。
- **状态机校验**：所有跃迁经 `StateTransitionValidator.validateXxxTransition()` 白名单校验（§3.2 已存在）；非法跃迁（如 23000→23009）拒绝并记 WARN 日志。
- **Feign 调用顺序**：`TaskTransport.status` 先落库（本地事务）→ 再 Feign 调 `OrderApi.updateStatus()`；Feign 失败不回滚本地事务（允许短暂不一致），由 MQ 消费端重试最终一致。
- **MQ 事件兜底**：Feign 调用失败 → 发 Kafka 事件（复用 `OrderEventMQListener` 通道）→ 消费端按 `orderId + targetStatus` 幂等重试 3 次（间隔 5s/30s/2min）；3 次仍失败入告警中心（依赖 P0-5）。
- **客户端轮询兜底**（契约 C5）：客户小程序每 15s 轮询 `Order.status`，联动失败时客户最迟 15s 看到正确状态；不强制 WebSocket。
- **轨迹查询入口**：pd-netty 的 `GpsTraceController.latest/replay` 增加 `transportTaskId` 入参（可选，与 `businessId` 二选一）；pd-web-customer 新建 `OrderTraceController`，先按 `orderId` 关联查 `TransportOrderTask.transportTaskId`，再调 pd-netty 的 `/trace/latest?transportTaskId=`。
- **客户鉴权**：pd-web-customer 的 `OrderTraceController` 入口校验 `Order.memberId = JWT.userid`，非本人订单返回 403（用 `token` 头 D-16，不复用管理端 `Authorization: bearer`）。
- **网关路由**：依赖 §5.1 已修复的 Nacos 路由 `/web-customer/**`，无需新增路由（D-17 已定案）。

## 9. 调研参考（成熟产品做法来源）

- 顺丰"青龙"/"丰智云"、京东物流"与图"/"超脑"：以订单为主线、数据中台统一口径、全链路可视化。

- 通用架构范式（CEP Tracking / 订单跟踪系统）：事件总线 + 数据中台 + 状态机引擎 + WebSocket 实时同步；OrderID/PackageID/TrackingID 三级唯一标识；状态映射层解耦第三方。

> 本项目不对接任何外部厂商 API（见《开发规范与需求规格说明书》红线），上述仅借鉴其**多端数据一致的内部架构范式**，不涉及外部集成。
