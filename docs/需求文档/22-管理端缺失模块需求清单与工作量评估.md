# 管理端缺失模块需求清单与工作量评估

> 结论：dictionary / dictionaryItem 可直接开发；application 需先明确用途

---

## 一、问题定性

| 模块 | 前端页面 | 前端 API | 后端 Controller | 建表脚本 | 资源表注册 |
|---|---|---|---|---|---|
| 数据字典 dictionary | ✅ 3 个组件 | ✅ 4 方法 | ❌ 0 | ❌ 无 | ❌ 未注册 |
| 字典项 dictionaryItem | ✅ 2 个组件 | ✅ 4 方法 | ❌ 0 | ❌ 无 | ❌ 未注册 |
| 应用管理 application | ✅ 2 个组件 | ✅ 4 方法 | ❌ 0 | ❌ 无 | ❌ 未注册 |

**本质**：这是**未开发完的半成品**，不是权限问题。前端按完整模块写好了页面和调用，后端从未实现对应接口。

**当前用户可见表现**：菜单能进、页面能打开，但一发起请求就404（网关先判"未知请求"返 401，补注册后转为 404）。

## 二、逐模块需求清单

### 2.1 数据字典 dictionary（可直接开发）

**前端反推字段**（来自 `views/pinda/base/dict/Edit.vue`）：

| 字段 | 类型 | 校验 | 说明 |
|---|---|---|---|
| code | varchar | 必填、唯一 | 字典编码 |
| name | varchar | 必填 | 字典名称 |
| describe | varchar | 选填 | 描述 |
| status | bit | 必填 | 状态 true/false |

**需交付**：
1. 建表 SQL：`pd_auth_dictionary`（含 `id/name/code/describe_/status` + Entity 公共字段）
2. 实体 + Save/Update/Page DTO
3. Controller 4 接口：`GET /dictionary/page`、`POST /dictionary`、`PUT /dictionary`、`DELETE /dictionary`
4. 注册资源进 `pd_auth_resource` + 授权 role_id=100

**工作量**：约 0.5 天（纯标准 CRUD，无业务逻辑）

### 2.2 字典项 dictionaryItem（可直接开发）

**前端反推字段**（来自 `DictionaryItemEdit.vue`）：

| 字段 | 类型 | 校验 | 说明 |
|---|---|---|---|
| dictionaryId | bigint | 必填 | 所属字典 ID（外键关联 dictionary.id） |
| code | varchar | 必填 | 字典项编码，同字典内唯一 |
| name | varchar | 必填 | 字典项名称 |
| describe | varchar | 选填 | 描述 |
| sortValue | int | 选填 | 排序值 |
| status | bit | 必填 | 状态 |

**需交付**：同2.1，另加：
- `pd_auth_dictionary_item` 建表 SQL
- **级联规则**：口径见 §五 R-01（字典下存在字典项时禁止删除，不做级联删除）

**工作量**：约 0.5 天

### 2.3 应用管理 application（⚠️ 需先明确用途）

**前端反推字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| name | varchar | 应用名称 |
| appKey | varchar | 应用密钥对标识 |
| appSecret | varchar | **应用密钥（敏感）** |
| appType | 枚举 | 应用类型（前端用 `.code` 访问，说明是枚举对象） |
| website | varchar | 官网地址 |
| icon | varchar | 应用图标 |
| className | varchar | **实现类全限定名** |
| status | bit | 状态 |

**必须先澄清的 3 个问题**：

| 编号 | 问题 | 为什么必须先问清 |
|---|---|---|
| Q-01 | `appSecret` 明文存库还是加密存？ | 若为开放平台调用凭据，明文存储是安全缺陷；若仅作展示，需限制查询接口返回 |
| Q-02 | `className` 指向哪个包/用途？ | 字段名暗示"按类名反射加载"，若无明确目标类，属于过度设计或残留字段 |
| Q-03 | `appType` 枚举有哪些取值？ | 前端用 `application.appType.code` 访问，需与后端枚举定义对齐，否则取值乱|

**结论**：Q-01~Q-03 已随 P1-21 排期收口，处置口径见 §五。

**预估工作量**：澄清后约 1 人天（含密钥加密存储 + appKey 自动生成 + 反射调用的安全约束）

## 四、风险登记册

| 编号 | 风险 | 类别 | 概率 | 影响 | 等级 | 应对 |
|---|---|---|---|---|---|---|
| R-01 | 删除字典时是否级联删除字典项，前端无此逻辑，后端需定义 | 需求风险 | 中 | 中 | 中 | 开发前与产品确认；建议"字典下有字典项时禁止删除并提示" |
| R-02 | application 的 appSecret 明文泄露 | 安全风险 | 高 | 高 | **高** | 若做，必须加密存储且查询接口脱敏返回 |
| R-03 | className 反射加载引入远程代码执行风险 | 安全风险 | 中 | 高 | **高** | 未明确用途前不做；若做必须白名单校验 |
| R-04 | 新增接口未注册资源导致 401 复发 | 技术风险 | 中 | 中 | 中 | 已有完整注册流程与 SQL 脚本，可复用 |
| R-05 | 字典编码被业务代码硬编码依赖 | 数据风险 | 中 | 中 | 中 | 上线前先排查现有代码是否引用字典项编码 |

## 五、待决策项处置口径

> 下表由原待拍板项收口而来，均已并入《02-优先级总览.md》**P1-21（数据字典 + 应用管理 CRUD，2.5–3 人天，落点 `pd-auth`）**，作为 P1-21 开工时必须遵守的设计约束：

| 原编号 | 事项 | P1-21 内的处置口径 |
|---|---|---|
| 原第 5 项 | dictionary 与 application 是否一起做 | ✅ 已闭合：合并为 P1-21 一个抓手，一次交付 |
| R-01 | 删除字典时字典项如何处理 | 按风险登记册建议执行：**字典下存在字典项时禁止删除并提示**，不做级联删除（避免误删被业务引用的字典项）；P1-21 设计评审确认 |
| Q-01 / R-02 | appSecret 是否加密存储 | **必须加密存储**，查询接口脱敏返回，禁止明文落库 |
| Q-02 / R-03 | className 字段实际用途 | 本期**不做反射加载**（YAGNI + RCE 风险），字段保留仅作记录；若无真实消费方，P1-21 评审时决定是否删除 |
| Q-03 | appType 枚举取值 | 以后端 `pd-auth-entity` 既有枚举为准对齐，经 `/authority/application/*` 契约读取；禁止前端自定义取值 |

> ⚠️ 上表为 P1-21 开工前设计约束（沿用 §四风险登记册的应对建议）；若设计评审时业务方另有口径，以评审结论为准。
