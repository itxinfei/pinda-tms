## P-03：快递员异常上报，标 P0 还是 P1？

### 背景与证据

| 侧 | 记的是什么 |
|---|---|
| **需求侧标 P0** | SRS §7.3「页面清单（首期 P0）」快递员行含"异常上报"；第 9 章「阶段2：快递员端 + POD + 异常（P0，约 1 周）」；附录 A 配送执行 `P0+P1`；上游调研文档也写 `[P0] 异常上报` |
| **执行侧对不上** | 《优先级总览》**P0-2b 验收项**只写"取派件 + POD 电子签收 + 蓝牙打印"，**不含异常上报**；《快递员端任务卡》**C-1~C-10 没有异常上报页**；该卡 C-5「边界说明」反而把"破损上报入口"推给 **P1-11** |
| **后端不缺** | SRS §6.10 域现状记"✅ 快递员异常上报入口 API 已实现"（`pd-web-courier` 已有）→ **缺的是前端页面，不是后端接口** |

**结论**：这是个"需求侧标了P0、但执行侧没有对应页面项"的典型断裂。若不拍板，按 P0 施工会无处落地，实际会滑到 W9-W12。

### 选项

| | **① 升为真 P0** | **② 降为 P1** |
|---|---|---|
| 做什么 | 把异常上报入口补进 **P0-2b 验收项**，并在《快递员端任务卡》新增一页 | 把 SRS 三处 P0 标注改为 P1，随 P1-11（W9-W12）交付 |
| 好处 | 贴合"异常早报"业务价值（破损/拒收越晚上报损失越大）；与需求侧现有标注一致 | 不动P0 范围，P0 工期可控；三端P0 更聚焦 |
| 代价 | P0 工期 +1~2 人日（1 页+ 联调） | 需求侧三处要改标注；异常上报延后，异常发现/告警闭环（属P0-5）会与逆向理赔（P1-11）拉得更远 |
| 与既有定案的关系 | 与 P0-5 统一告警中心相邻但不冲突 | 与 P1-11 逆向/异常流规格天然同批 |

### 我的建议：**② 降为 P1**

理由：**P0-5（统一告警中心）已经在 P0 里承担"异常发现与告警闭环"**，快递员端上报页面属于"异常录入的UI 入口"，与后端告警闭环是两件事。按业务价值排序，等告警中心落地后再补上报入口更稳。

**但这取决于你的业务判断**：如果破损/拒收的早期上报对你们是强需求（减少损失），就该选 ①。

## P-04：菜单显示用后端下发还是前端静态直出？

### 背景与证据

| 侧 | 记的是什么 |
|---|---|
| **前端现状（2026-10-06 重构后）** | 菜单/路由改为**前端静态直出** —— 守卫直接取 `src/router/menu.js` 的 `staticMenu`，**不再调后端 `getRouter`**；开发测试环境不按角色过滤、固定全量；**新增页必须手工登记否则无入口** |
| **规范文档现状** | 《管理端Vue3升级专项实施规范》§5.4 与《管理端UI规范》§3.1 仍写"动态路由**由后端 `getRouter` 下发**、`filterAsyncRouter` 映射" |
| **冲突性质** | 两者**互斥**。且 `D-32` 换 `vue3-element-admin` 基座（基座自带路由/权限示例）会把这个问题推到台前 |

**共同事实（两条都不影响）**：`pd_auth_resource`（383 条）只决定**网关放行**，不决定菜单显示。

### 选项

| | **① 恢复后端动态下发** | **② 维持前端静态直出** |
|---|---|---|
| 做什么 | 恢复 `getRouter` 下发 + RBAC 过滤 | 保持 `staticMenu` |
| 要改什么 | 删前端 `menu.js` 的 `staticMenu` 直出；改《任务卡》§〇 第 6 条与新页DoD | **回写改**《实施规范》§5.4 与《UI规范》§3.1 两处口径，并明确"生产环境按角色 RBAC 何时做" |
| 好处 | 菜单随角色动态下发，与 RBAC 一致；新增页不用手工登记 | 前端简单、开发快、不依赖后端菜单接口 |
| 代价 | 依赖后端 `getRouter` 稳定返回；前端要改 | ⚠️ **菜单不按角色过滤**——生产环境若多角色，菜单显示与权限不匹配（是安全/体验隐患）；新增页必须手工登记，漏登记就没入口 |

### 我的建议：**① 恢复后端动态下发**

理由：
1. **多角色是本项目既定事实**（管理端有系统管理员/调度/财务/运营等角色，SYS-01~06 就是 RBAC）。静态全量菜单意味着"所有登录用户都看到全部菜单"——调度看到财务菜单、司机看到管理员菜单，与 §6.14 的角色权限设计直接矛盾。
2. `D-32` 换基座（vue3-element-admin）**自带路由/权限示例**，本来就该走后端下发。
3. 规范文档原本就是 ① 的口径，改文档比改架构代价小。

**但要注意成本**：这是前端工作量（`D-32` 专项内），且要确认后端 `getRouter` 在基座改造后能稳定工作。
