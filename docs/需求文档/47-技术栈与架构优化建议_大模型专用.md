#### 1.2.1 MQ 选型定案（2026-10-09 参考神领物流后拍板）

**参考对象**：神领物流（黑马程序员培训项目，面向成千上万学习者的成熟 TMS 项目）

**神领物流技术栈特点**：
- 19 个微服务 + 1 个网关
- 前端管理端 vue2，移动三端 uniapp + vue3


**理由**：
1. **参考成熟项目**：神领物流作为面向学习者的 TMS 项目，只用 RabbitMQ 就够了
3. **学习成本低**：学习者只要学一套 MQ
4. **中小场景够用**：100-500 辆车，RabbitMQ 完全扛得住
5. **迁移成本低**：轨迹数据迁到 RabbitMQ，大概 1 天工作量

**迁移要点**：
- 用 routingKey = truckId/driverId 保证同一辆车的轨迹串行消费，不会乱序
- 死信队列 + 重试机制，保证消息不丢
- 订单领域事件继续走 RabbitMQ，不用改

#### 1.2.2 实测证据与落地闸口（2026-10-09 补，支撑 §1.2.1 定案；与上文"参考神领物流"是两个独立依据，二者都要保留）

§1.2.1 的理由是"对标成熟项目"。本节补另一条**与本仓库代码绑定**的依据——它比对标更硬，也正是本方案风险最低的原因：

| 实测项 | 证据（`file:line`） | 结论 |
|---|---|---|
| RabbitMQ 消费端 | `pd-dispatch/.../OrderEventMQListener.java:59/87/134` + `pd-oms/.../SettlementDeliveredListener.java:57` | 订单事件 + **结算单生成**在用，是活链路 |
| RabbitMQ 拓扑 | `pd-dispatch/config/rabbitmq/RabbitMQConfig.java:28-76` | topic exchange + routingKey=eventType + 3 队列 + DLQ + 发布重试 3×2s，**原生具备**扇出/死信/重试 |


**⚠️ 定案文本里两条未经核实的说法（不删原文，此处标注）**：
1. "**轨迹迁 RabbitMQ 大概 1 天工作量**"——未实测。真实工作量取决于下面闸口 ①②，尤其"每车一串列"若做成 per-truck queue，100–500 辆车即 100–500 个队列的声明/清理策略要设计。
2. "**routingKey = truckId/driverId 保证串行消费**"——RabbitMQ 的串行保证粒度是**队列**不是 routingKey：同一 routingKey 只有在**绑定到同一队列且该队列只有 1 个消费者**时才串行。原文写法可用，但须按此语义改写，否则实现者会误以为 routingKey 天然保序。

- **② 保序与乱序兜底口径写进 SRS**：同车轨迹串行消费的约束（或改为"按 `gpsTime` UPSERT 取最新"的幂等写）必须固化为验收项，否则迁移后出现"轨迹倒挂"这类难查问题。

### 4.2 四端 CI/CD 部署要求（D-50 定案）

> **强制要求**：所有四个端的 Web/H5 版本都必须通过 CI/CD 自动构建并部署到 Docker 容器中运行，不允许手动部署。

| 端 | 构建产物 | 部署方式 | 容器端口 | CI/CD 触发 |
|---|---|---|---|---|
| **管理端**（vue3-element-admin） | 静态文件（dist） | Nginx Docker 容器 | 80/443 | push 到 main 分支自动触发 |
| **司机端 H5**（uni-app） | 静态文件（dist/build/h5） | Nginx Docker 容器 | 8081 | push 到 main 分支自动触发 |
| **快递员端 H5**（uni-app） | 静态文件（dist/build/h5） | Nginx Docker 容器 | 8082 | push 到 main 分支自动触发 |
| **客户端 H5**（uni-app） | 静态文件（dist/build/h5） | Nginx Docker 容器 | 8083 | push 到 main 分支自动触发 |

**CI/CD 流程要求**：
1. **代码提交**：开发者 push 代码到 Gitea
2. **自动构建**：Gitea Actions 自动执行构建脚本（pnpm install → build）
3. **镜像打包**：构建完成后自动打包成 Docker 镜像（基于 nginx:alpine）
4. **镜像推送**：推送到本地 Docker Registry（或直接加载到服务器）
5. **容器重启**：SSH 到服务器，停止旧容器，启动新容器
6. **健康检查**：容器启动后自动检查是否正常运行

**APP 端发布方式**：
- 司机端/快递员端 APP：通过 HBuilderX 云打包或本地打包，生成 APK/IPA 后手动分发
- 客户端小程序：通过微信开发者工具上传，提交审核后发布
