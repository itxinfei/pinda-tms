# 60-技术栈评估与演进路线

> **用途**：技术栈现状评估（对照行业同类产品）、后期新增技术栈路线（P0/P1/P2）、预留项决策（Seata / Flowable / 新徽章）、工程优化点清单。写技术选型 / 新增依赖 / 演进规划前先读。
> **日期**：2026-10-12（基于同类产品实测调研：联云科技 TMS / oTMS / 唯智 vTradEx / 运匠 Logwire / 2026 运输管理系统发展报告）

---

## 0. 结论速览（AI 可据此直接执行）

1. **技术栈不推倒重来**：现有底座（微服务 + Drools + Netty + uni-app 三端 + CI/CD）已覆盖行业产品约 70% 功能骨架，处于同类第一梯队。
2. **最大商业缺口**：财务结算闭环（BMS 计费/对账/核销/开票）与实时轨迹链路（流处理+时序存储+推送）——列为 **P0**。
3. **Seata 不引入（保持已移除）**：场景无强一致硬需求，AT 模式全局锁/脏写/SQL 约束代价与调度批量写冲突；跨服务一致性用"本地消息表 + RabbitMQ 可靠消息 + 消费幂等 + XXL-Job 定时对账"。预留触发条件：出现财务强一致场景时评估 **TCC（强一致）/ Saga（长链路）**，**不用 AT**。
4. **Flowable 预留（需求已变，暂不开发）**：2026-10-12 用户确认"需求变了，暂时预留，后期再增加"；徽章保留，不上路线图，不做任何开发。
5. **新徽章全部为预留方向**（Debezium / Doris / JimuReport / 快递100 / Spring AI），不在本期实现，不新增依赖；引入前按《59》整合新栈三步走。
6. **最优先 3 件工程项（零新增技术栈）**：① MySQL 定时备份+恢复演练 ② 跨服务事务/幂等方案定案 ③ 部署页中间件 3/6 healthy 排查。

## 4. 分布式事务决策（Seata 用/不用）

> **结论：不引入 Seata，保持"已移除"状态；列为预留，触发条件见 §4.3。**

### 4.1 兼容性事实（已核实）
- Seata 2.3.0（2025-03 推荐）/2.5.0 支持 Spring Boot 3.x；SCA 2025.1.0.0 官方对应 **Seata 2.5.0**（本项目 SCA 2025.0.0.0 对应 2.4.x 可用）。**不是兼容问题，是代价问题。**

### 4.2 不引入的理由
1. **场景无强一致硬需求**：订单→调度→任务链路是状态机驱动，天然"短时不一致可接受"，用最终一致性即可。
2. **AT 模式代价与调度批量写冲突**（多个独立来源验证）：
   - 全局锁（TC 侧 lock_table）：跨网络拿锁，高并发热点 TPS 骤降、连接池打爆
   - 脏写/脏读：非 Seata 链路的数据修改、报表统计可读到未全局提交数据（与 Doris 经营分析规划冲突）
   - SQL 硬约束：业务表必须单列主键、禁 `INSERT ON DUPLICATE KEY UPDATE`/`REPLACE INTO`/多表关联更新
   - 运维 +1：需部署 TC server（第 9 个中间件）
3. **已有更好底座**：RabbitMQ + XXL-Job + 幂等（订单取消防重已落地）——最终一致性三件套齐全。

### 4.3 主方案与触发条件
**主方案（现在就用，零新增组件）**：
```
订单状态变更(本地事务) → 同事务写本地消息表 + 发 RabbitMQ → 下游服务幂等消费(业务号唯一键) → 本地状态推进
XXL-Job 定时扫描消息表(重发失败消息) + 两端状态对账补偿
```
**触发条件（出现才评估 Seata）**：
| 触发场景 | 届时选型 | 说明 |
|---|---|---|
| 财务结算/支付对账（一分钱不能错） | **TCC** | 强一致业务，AT 不适合核心交易 |
| 超长链路（多式联运多段协作） | **Saga** | 长事务 + 状态机补偿 |
| 一般联动（当前订单/任务） | 不用 Seata | 本地消息表 + 幂等足够 |

## 5. 新增徽章衔接（2026-10-12 用户新增，全部为**预留**）

| 徽章 | 定位 | 衔接/注意 | 状态 |

| Doris | OLAP 分析库 | 承接经营分析/大屏；**与 ES 分工：Doris=聚合分析，ES=检索**；初期可先 MySQL 汇总表过渡 | 预留 |

| JimuReport | 可视化报表 | SQL 数据集 + Doris（MySQL 协议兼容）；商用前确认许可证边界 | 预留 |

| Spring AI | 大模型集成 | P1 LLM 辅助承接；配向量库（pgvector/Redis 向量）；key 进 Nacos 配置 | 预留 |

## 6. 工程优化点清单（零新增技术栈，按优先级）

### P0（立即做，风险最高）
1. **MySQL 定时备份 + 恢复演练**（mysqldump/xtrabackup）——单库承载全部业务，目前无备份机制
2. **跨服务事务/幂等方案定案**（按 §4.3 主方案落地，覆盖订单取消防重推广到派单/回调）
3. **部署页中间件 3/6 healthy 排查** + 宿主 nginx `/deploy.html` 404 修复
4. **修复 swagger-ui 401**：`/v3/api-docs` 加白名单（springdoc 已有，被 TokenAuthInterceptor 拦截）

### P1（近期 1~2 月）
- 数据：历史订单/轨迹冷热分离（分区+归档）、慢 SQL 治理（Druid 监控+索引审计）
- 缓存：热点订单缓存 + 双删/CDC 订阅，防击穿/雪崩
- 质量：JUnit5 + Testcontainers + MockMvc 单测体系；CI 加 checkstyle/spotless
- 安全：敏感数据加密存储+脱敏展示、审计日志（登录/派单/改价）、接口防刷限流
- 运维：日志集中（Loki/EFK）、容器自愈（restart + 健康探针 + 资源上限）、镜像 tag 语义化

### P2（随业务演进）
- 读写分离（主从+多数据源）、契约测试/接口版本管理、文件上传安全（MinIO）、灰度/回滚（nginx 蓝绿）、热部署、前端 TS 严格模式/ESLint 统一

### 上线前补课清单（2026-10-13 CI/CD 合规审计追加，真实用户/公网上线前必须完成）

> 对照大厂（阿里云效/Aone 体系）通行 CI/CD 纪律，以下三项当前按 CLAUDE.md §5.2 dev 定调豁免，但属结构性硬缺口，上线前必须补齐：

1. **测试门禁**：`build-check.yml` / `deploy-backend.yml` 全程 `-Dmaven.test.skip=true`，CI 只保证"可编译"不保证"可用"。上线前 CI 门禁必须 = 编译 + 单测（JUnit5+Testcontainers，接 §6-P1 质量项）+ 规约扫描（P3C/checkstyle），全绿才可部署。
2. **中央制品库（Harbor/Registry）**：当前镜像 build 在部署机本地 docker daemon，tag 不出机器——部署机一挂制品历史全丢，且 `deploy-fe.sh` 时间戳 tag 不可回溯 commit。上线前：CI 构建推中央 Registry、部署机只 pull；镜像 tag 一律绑定 commit SHA（不可变标识），禁纯时间戳 tag。
3. **灰度/分批发布**：当前 `deploy-backend.yml` 一把切选中服务。上线前至少实现分批发布（基础服务批→业务批→网关最后批）+ 每批观察窗口 + 回滚演练留痕；单机 compose 架构以"批次+健康观察窗口"近似灰度，多机化后升级真灰度/蓝绿（接 §6-P2 灰度项）。
