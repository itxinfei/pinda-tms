# 品达 TMS 开源产品化路线图

> **文档定位**：把品达 TMS 从"demo 项目"做成"开源可商用产品"的完整路线图。
> **生成日期**：2026-10-08
> **商业模式**：源码开放（Apache 2.0 核心）+ 商用授权 + 二开/部署/技术支持服务
> **客户画像**：B（外包公司/接项目开发者，拿源码当模板）+ C（大学生/学习者）
> **时间路径**：A——先花 2-3 周把技术栈升到现代标准，再做业务功能

---

## 〇、产品定位一句话

```
品达 TMS = 开源版物流运输管理系统（Carrier TMS）
         = 中小企业自营车队/区域 3PL 可直接部署
         = 外包开发者可二次开发接物流项目
         = 你（作者）卖二开服务、部署支持、商业版高级功能
```

**架构拆分（2026-10-08 用户拍板）**：拆成两个独立项目
```
项目 A：pinda-cloud-authority（权限中心）
├── pd-auth-server（认证 + RBAC：用户/角色/菜单/日志）
├── pd-gateway（统一网关）
└── pd-admin-ui-vue3（vue3-element-admin 前端）

项目 B：pinda-tms（物流业务系统）
├── pd-base / pd-oms / pd-dispatch / pd-work / pd-user / pd-aggregation / pd-netty
└── 业务前端（管理端业务页 + 移动三端 uni-app）
```

**为什么拆**：
1. 权限中心独立，可以给别的项目复用
2. 物流业务系统更纯粹，只关心业务
3. 开源时拆成两个仓库，用户按需下载
4. 降低复杂度，好部署好运维

**对标开源项目**：RuoYi（后台管理脚手架）、JeecgBoot（低代码平台）、pig（微服务脚手架）、mall（电商系统）——它们都是"开源核心 + 服务收费"模式。

## 一、为什么必须先升技术栈（B/C 客户视角）

| B 客户（外包开发者）看到 pom.xml | C 客户（学习者）看到 README |
|---|---|
| JDK 1.8 + Spring Boot 2.2.5（2020年）→ "这项目五年没更新了吧？" | star < 100 + 技术栈老 → "不看了" |
| Spring Boot 3 + JDK 21 + Vue3 + Vite → "现代栈，拿这个给客户做项目有面子" | badge 全绿 + 在线 demo + 视频 → "收藏先" |
| Zuul 1.x（Netflix 已停更）→ "网关都不换，架构有问题" | ECharts 5 + 百度地图 → "UI 不错" |

**结论**：技术栈不是给你自己用的，是给"下载源码的开发者"看的。现代栈 = 信任感 = star 数 = 二开订单。

## 二、阶段 1：技术栈现代化（2-3 周，约 20-25 人日）

### 2.1 后端技术栈（最终选型）

| 层 | 现状 | 目标 | 变更说明 |
|---|---|---|---|
| JDK | 1.8 | **21 LTS**（Temurin） | Dockerfile 换 `eclipse-temurin:21-jdk` |
| Spring Boot | 2.2.5.RELEASE | **3.3.x** | 强制 jakarta.*，OpenRewrite 自动迁移 |
| Spring Cloud | Hoxton.SR3 | **2023.0.x** | 对齐 Boot 3 |
| Spring Cloud Alibaba | 2.2.1.RELEASE | **2023.0.x** | 对应 Nacos 2.x 客户端 |
| 网关 | Zuul 1.x (Netflix) | **Spring Cloud Gateway** | **必换**——Zuul 1.x 不兼容 Boot 3；Gateway 是响应式，编程模型不同但更现代 |
| ORM | MyBatis Plus 3.3.0 | **3.5.x** | jakarta 版本 |
| 连接池 | Druid 1.1.22 | **1.2.23** | jakarta 版本 |
| 鉴权 | Shiro 1.4.0 | **Shiro 2.0.x** | jakarta 版本，API 有小变 |
| 规则引擎 | Drools 6.5.0.Final | **Drools 8.x** | **大坑**——7+ API 完全重写，运费规则要重新写 DSL |
| API 文档 | springfox-swagger 2.9.2 | **springdoc-openapi 2.x** | springfox 已停更，不支持 Boot 3 |
| JSON | FastJSON 1.2.x | **FastJSON2** | 包名 `com.alibaba.fastjson2`，API 基本兼容 |
| 分布式事务 | Seata 1.2.0 | **Seata 2.x** | 对齐 Spring Cloud 2023 |
| 定时任务 | Quartz（既有） | **Quartz 2.3.x** | 不变，升级客户端版本 |
| 轨迹通道 | Netty（既有） | **Netty 4.1.x** | 不变，升级版本号 |
| 消息队列 | Kafka 2.6 / RabbitMQ 3.8 | 客户端升新版 | 服务端升级见 §2.3 |

### 2.2 前端技术栈（最终选型）

**管理端基座：vue3-element-admin（有来开源）**
- 地址：https://gitee.com/youlaitech/vue3-element-admin
- 选型理由：
  1. **一套生态管四端**：管理端 Vue3 + 移动端 uni-app，正好对应管理端 + 移动三端
  2. 国内开源，Gitee 有镜像，克隆方便
  3. 代码结构清晰，适合外包二开赚钱
  4. 自带代码生成器，业务页批量生成快
  5. 文档全，学习者容易上手

| 端 | 现状 | 目标 |
|---|---|---|
| 管理端 | Vue2.6 + Element UI 2.12 + Vue CLI 3 + node-sass | **vue3-element-admin 基座**：Vue 3.4 + Element Plus + Vite 5 + Pinia + TypeScript |
| 移动端（三端） | 未建 | **uni-app（有来开源配套）**：Vue3 + Vite + uview-plus + Pinia |
| 图表 | ECharts 4.2 | **ECharts 5.x** |
| 地图 | 百度地图 JS API GL（D-12 已定） | 不变 |

**UI 设计原则（调研 10+ TMS 产品总结）**：
1. Dashboard 大盘：4 个核心 KPI 一眼看到（今日运单 / 在途 / 异常 / 准时率）
2. 地图+表格分栏：左侧地图轨迹，右侧数据列表，调度员必备
3. 状态时间线：颜色编码（绿=正常 / 黄=预警 / 红=异常）

## 四、双授权商业模式落地

### 4.1 授权结构

```
┌─────────────────────────────────────────┐
│  核心开源版（Apache 2.0）                │
│  - 所有运输业务功能（订单/调度/轨迹/结算） │
│  - 三端（司机/快递员/客户小程序）          │
│  - 管理端（业务页+系统管理）             │
│  - 免费商用，但需保留版权声明             │
│  - 你不提供技术支持（除非买服务包）        │
├─────────────────────────────────────────┤
│  商业授权版（闭源模块，单独收费）          │
│  - 多租户 SaaS 版                        │
│  - 企业微信/钉钉/飞书集成                │
│  - 高级 BI 报表/控制塔大屏               │
│  - 客户门户开放 API                      │
│  - 工作流引擎（审批流/异常处理流）        │
│  - 工单系统/客服系统                      │
│  收费模式：License 年费 + 定制开发         │
├─────────────────────────────────────────┤
│  服务包（你卖的）                         │
│  - 部署服务（远程帮客户装）：3000-5000 元/次 │
│  - 二开定制：按人天 800-1500 元/人天     │
│  - 技术支持：年费 5000-20000 元/年       │
│  - 培训：按次收费                         │
└─────────────────────────────────────────┘
```

### 4.2 LICENSE 文件怎么写

- **仓库根目录 LICENSE**：Apache 2.0 全文
- **仓库根目录 COMMERCIAL-LICENSE.md**：商业授权条款（哪些功能需要授权、价格、联系方式）
- **每个开源文件头部**：Apache 2.0 版权声明（`Copyright 2026 Pinda TMS Authors`）
- **商业版模块**：放在 `pinda-tms-proprietary/` 目录，单独 LICENSE（保留所有权利）

### 4.3 B 客户（外包开发者）转化路径

```

```

## 六、关键风险与避坑

| 风险 | 影响 | 避坑 |
|---|---|---|
| **Drools 6.5 → 8.x API 大改** | 运费规则重写 2-3 天 | 先在测试模块验证 Drools 8 DSL，再迁移全量规则；保留旧规则参考 |
| **Zuul 1.x → Gateway 编程模型重写** | 网关配置重写 2-3 天 | Gateway 路由配置可以从 Zuul yml 半自动转换；过滤器逻辑要重写（pre/post/error） |
| **Shiro 2.0 jakarta 版本 API 变化** | 鉴权过滤器要调 | Shiro 2.0 文档较全，按官方迁移指南走 |
| **Spring Cloud Alibaba 2023 对应 Nacos 2.x** | Nacos 客户端包名变化 | Nacos 1.4 → 2.x 服务端也要升，配置导出导入 |
| **OpenRewrite 迁移不干净** | 872 个文件手工调 1-2 天 | OpenRewrite 跑一遍后，全局搜 `javax.` 确认清零 |
| **阶段 1 超时** | 影响阶段 2 业务开发 | 严格按 2-3 周控，遇到 Drools/Gateway 大坑不要追求完美，先跑通再优化 |
