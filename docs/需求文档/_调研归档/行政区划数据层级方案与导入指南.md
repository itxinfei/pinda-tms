**实施中发现的坑（已在脚本中修正）**：
1. **GitHub 直连不通**（HTTP 000）→ 改用 **jsDelivr 镜像** `cdn.jsdelivr.net/gh/...`，成功
2. **`short_name` 尾部带 `0D`（CR）** —— 源 JSON 为 CRLF 换行，导入后需 `TRIM(TRAILING CHAR(13) FROM ...)`，三库均已清理
3. **根节点 `parent_id=0` 需转 NULL** —— 否则前端/MyBatis 判断根节点会误判
4. **`first` 列被误填中文名** —— 首次 CSV 把 `name` 当占位列写进了 `first`，已用pypinyin 重算覆盖
5. **`LOAD DATA` 用 `@var` 赋值只更新 1 行** —— MySQL 5.7 对 `LOAD DATA` 用户变量处理有坑，**必须用「临时表中转 + `UPDATE JOIN`」**，实测 44,703 行正常
6. **拼音手工字表不可靠** —— 手写341 字表导致 16,406 行拼音残缺（"市"漏收录→`shi`变`治`），**必须用 pypinyin 专业库**。且 pip 默认源不通，须 `-i https://mirrors.aliyun.com/pypi/simple/`
7. **拼音源残留空行** —— 导致库里出现 `id=0, name=NULL` 的脏记录（level=0 变32条），已 DELETE 清理
8. **园区类名称含括号** —— 如"大安经济开发区（省级）"，须先 `re.sub(r"[^\w\u4e00-\u9fff]", "", name)` 剔除括号/连字符再转拼音

## 〇之三、坐标系统一：GCJ02 → WGS84（22:40-22:50，已完成）

### 为什么要转

排查后发现两个事实：

1. **项目约定统一存 WGS84** —— 《全局定案与待确认项清单》D-13 明确「`LocationRecord` 加 `coordSystem` 字段，上报校验坐标系合法」，北斗/GNSS 原始坐标即 WGS84。
2. **项目已有地图工具用的是百度** —— `pd-auth-server`的 `LocationUtil.getLatitude(address)` 调`api.map.baidu.com`（返回 **BD09**），且该工具已在 `OrgServiceImpl:227` 用于机构坐标回填。

若直接把高德 GCJ02 存进库，与项目既有约定冲突，且与百度 BD09 相差可达 **500m+**。

### 已执行的转换

| 项 | 内容 |
|---|---|
| 转换算法 | 逆向单步迭代逼近（3 次收敛），精度 **< 1m** |
| 往返自检 | GCJ02 → WGS84 → GCJ02 误差 **0.0000 米** |
| 北京位移 | 116.407387 → **116.401144**（712m，符合北京实际偏移量） |
| 转换条数 | **3,207 条**（省31 / 市 333 / 县 2,843） |
| 备份 | `pd_area_coord_bak_gcj02_20261007`（三库各 3,207 条，可回滚） |
| 列注释 | 三库 `lng`/`lat` 均加注释 `经度(WGS84)` / `纬度(WGS84)` |

工具已归档：`docs/sql/区划数据/坐标转换_GCJ02转WGS84.py`（含正反双向函数，可复用）

### 后续使用注意

前端/后端若需在**百度地图**上展示区划坐标，**仍需再转 BD09**（三库互转脚本已具备，改调用方向即可）：
```python
# WGS84 -> BD09：先 wgs2gcj，再 gcj2bd09（百度额外加密）
# GCJ02 -> BD09：gcj2bd09
```
三库坐标若要与北斗终端上报坐标（`pd_truck` GPS）比对，**现在已是同坐标系，可直接算距离**。
> ⚠️ **坐标系统一落点（P1-12，2026-10-08 三轮审查回写：BA-19）**：机构/网点 `scope` 多边形另有经百度 `LocationUtil` 回填的 BD-09 坐标（见上第 2 条），与本文件三库 WGS84 不一致；电子围栏（OPS 卡 §3.7）/就近匹配等空间计算在 pd-work 关联层统一转换前，不得直接拿 BD-09 多边形与 WGS84 轨迹点求交——转换层随 P1-12 实施。

## 〇之四、连带发现：机构坐标回填功能一直未生效（22:50）

排查坐标系时顺带发现一个**已存在的功能缺陷**（与本次导入无关，但需记录）：

### 现象

`pd_auth.pd_core_org` 表有 `longitude` / `latitude` 两个字段，但**14 个机构全部为空**。

### 根因

`OrgServiceImpl:218-233` 在新增/更新机构时，会用「省+市+县+详细地址」拼成完整地址，调 `LocationUtil.getLatitude(address)` 查坐标回填。而：

```java
// common.yml（Nacos）
location:
  ak: ""          // ← 空字符串
```

```java
// LocationUtil.java:36-39
if (ak == null || ak.trim().isEmpty()) {
    log.error("location.ak未配置，无法调用百度地图API");
    return null;          // ← 直接返回，坐标不回填
}
```

且该工具用的是**百度地图**（`api.map.baidu.com`，返回 BD09）。

### 影响

| 项 | 影响 |
|---|---|
| 机构坐标回填 | ❌ **完全未生效**（14/14 为空） |
| 影响范围 | 机构地图选点、站点分布图、就近派单半径计算等**依赖机构坐标的功能均不可用** |
| 隐蔽性 | 代码有完整逻辑 + 日志会报错，但**不阻断业务流程**，属静默失效，容易被忽略 |

### 建议处理（待决策，本期未做）

| 方案 | 说明 |
|---|---|
| **A. 配置百度 ak** | 到百度地图开放平台申请服务端 ak，填入 Nacos `common.yml` 的 `location.ak`。**注意返回 BD09，与本项目 WGS84 约定不符**，回填后需加 `gcj2bd09` 转换 |
| **B. 改用高德+ 改代码** | 换高德 API（GCJ02，与本项目 WGS84 差一次转换），并给 `LocationUtil` 加 WGS84 转换输出 |
| **C. 暂不处理** | 若机构坐标功能本期不用，保持现状即可 |

**共性教训**：本项目存在多个「有代码无配置」的静默失效点（地图 ak、三端 base_url 等）。**建议上线前做一轮「配置项齐全度」自查**（见《联调就绪检查清单》§2 前置条件）。

## 二、本项目的现有设计（已预留 5 级）

`pd-auth-entity/.../entity/common/Area.java` 注释明确：

```java
@ApiModelProperty(value = "行政区域等级（0: 省级 1:市级 2:县级 3:镇级 4:乡村级）")
@TableField("level")
private Integer level;
```

**表结构已完整支持 5 级树**（`pd_auth.pd_area`，17 列），且接口是**按 parentId 懒加载**：

```java
// AreaServiceImpl#findAll
if (parentId != null) {
    queryWrapper.eq(Area::getParentId, parentId);  // 逐级下钻
} else {
    queryWrapper.last("limit 100");// 只查第一级
}
```

即：**层级数由数据决定，不由代码限制**。导入四级就是四级树，将来加村级无需改代码。

## 三、为什么不做村级（决策依据）

### 3.1 数据量级对比

| 层级 | 2024 年数量 | 累计 | 查询影响 |
|---|---|---|---|
| 1 级 省/直辖市/自治区 | 31 | 31 | — |
| 2 级 地级市 | 343 | 374 | — |
| 3 级 县/区/县级市 | 3,255 | 3,629 | — |
| 4 级 镇/乡/街道 | 41,351 | **44,980** | 无压力 |
| 5 级 村/居委会 | 620,572 | **665,552** | 需索引优化 +强制分页 |

### 3.2 当前业务无村级消费方

实测代码扫描结果（`grep` 全库 Java 实体）：

| 字段 | 出现次数 | 说明 |
|---|---|---|
| `provinceId` | 1 | `AddressBook` 地址簿 |
| `cityId` | 1 | 同上 |
| `countyId` | 1 | 同上 |
| `townId` / `streetId` / `villageId` | **0** | **无任何实体使用** |

`AddressBook` 的地址结构是「省 + 市 + 县 + 详细地址文本」，**没有街道/村庄字段**。

### 3.3 物流场景倒推

| 业务场景 | 所需粒度 | 四级够吗 |
|---|---|---|
| 运费分档/计费 | 区县（3 级） | ✅ 够 |
| 站点（网点）归属与覆盖分析 | 街道/乡镇（4 级） | ✅ 够，且正好匹配站点服务半径 |
| 末端派送网格化 | 街道（4 级） | ✅ 够 |
| 网格化精细运营、乡村直达 | 村（5 级） | ❌ 但**当前无此业务** |
| 地址簿详细地址 | 文本 + 经纬度 | 与层级无关 |

**结论**：村级的唯一潜在价值是「网格化精细运营」，但该功能在需求文档中属规划期，不在本期范围。**等真有村级业务需求时再补，只需追加导入，不影响已有数据。**

## 四、数据源推荐

### 4.1 首选：`adyliu/china_area`（五级齐全，最新 2024）

- 地址：https://github.com/adyliu/china_area
- 数据源：**国家统计局**《2023 年统计用区划代码和城乡划分代码》
- 层级：1 省 / 2 市 / 3 县 / 4 镇 / 5 村（**含 `category` 城乡分类字段**）
- 编码：12 位（省2+市2+县2+镇3+村3）
- 格式：CSV / SQL / Excel 均有
- 优点：数据权威、结构规整、自带城乡分类（可用于判断城/乡，运费分档用得上）

**本项目取 1~4 级即可**，`category` 字段建议保留入库（可用于运费城乡分档）。

### 4.2 备选：`modood/Administrative-divisions-of-China`

- 地址：https://github.com/modood/Administrative-divisions-of-China
- 层级：provinces / cities / areas / streets / villages 分文件
- 优点：按层级分文件，**只需下载 provinces/cities/areas/streets 四个文件**，省事
- 缺点：更新频率不如首选

### 4.3 不推荐

`airyland/china-area-data`（npm 包）：仅到县级，且不提供镇级。

## 五、字段映射方案（关键）

开源数据的字段与本项目 `pd_area` 的对应关系：

| 开源字段 | 本项目字段 | 处理方式 |
|---|---|---|
| `code`（12 位） | `id` | ⚠️ **不能直接用**（本项目 id 是 int 且为雪花 ID 风格），需生成新 ID |
| `pcode`（父级 code） | `parent_id` | 需通过 code→id 映射表转换 |
| `name` | `name` | 直接映射 |
| — | `area_code` | 用 `code` 填充（本项目已有该字段，用于 `getByCode`） |
| — | `city_code` | 用 2 级 code 填充 |
| — | `level` | 开源的 level（1~4）**减 1**，对齐本项目 0~3 定义 |
| — | `lng` / `lat` | 开源无坐标 → 留空或后续单独补 |
| — | `merger_name` / `short_name` / `zip_code` / `pinyin` / `first` | 开源无 → 留空（拼音首字母可在应用层算） |
| `category` | —（无对应列） | 建议**加一列** `category varchar(10)` 存城乡分类 |

**注意本项目 `id` 是 `int(11)`**，而区划有 4.5 万条，int 够用；但建议统一用规则生成（如 `level*100000 + 序号`）保持可读，不要用随机数。

### 步骤 3：生成正式数据（ID 规则化）

> ⚠️ **2026-10-08 二轮审查回写（BA-15 / D-19）**：下方示例 SQL 用了 `ROW_NUMBER() OVER (...)` 窗口函数，**MySQL 5.7.44 不支持，勿在 5.7 直接执行**。本次实际导入已改用随附 Python 脚本（LOAD DATA 入 `pd_area_import_tmp` 后按 code 序生成 new_id，见 §七）绕过；年度重跑（RK-02）请走 Python 脚本，或把窗口函数改写为用户变量/自增变量写法。下方 SQL 仅为规则示意。

```sql
-- 生成 id：level 左移 + 序号，规则化便于排查
-- ⚠️ 本 SQL 含 ROW_NUMBER()，MySQL 5.7.44 不可执行（D-19），仅示意；实际用 §七 Python 脚本
INSERT INTO pd_area (id, parent_id, name, area_code, city_code, level, category, create_time, update_time)
SELECT
  (t.level - 1) * 1000000 + ROW_NUMBER() OVER (PARTITION BY t.level ORDER BY t.code) AS new_id,
  p.id AS parent_id,
  t.name,
  t.code AS area_code,
  t.city_code,
  t.level - 1 AS lvl,
  t.category,
  NOW(), NOW()
FROM pd_area_import_tmp t
LEFT JOIN pd_area_import_tmp p ON t.pcode = p.code
LEFT JOIN pd_area p ON p.area_code = t.pcode
WHERE t.level <= 4;      -- 只要 1~4 级
```
