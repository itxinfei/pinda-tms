## 决策① 客户是否看到 ETA（预计送达时间）

### ① 行业主流做法

| 产品 | ETA 展示做法 | 来源 |
|---|---|---|
| 顺丰速运 App/小程序 | 物流详情页展示"预计送达时间"，结合历史路由与时效模型预估 | 顺丰物流查询服务说明；woshipm 实测文章 |
| 京东物流 | 下单即展示预计送达时段（如"211 次日达"承诺），配送中 AI 动态更新 | woshipm《订单履约：商品配送时效如何展示？》 |
| 菜鸟裹裹 | 为四通一达包裹计算并展示"预计到达时间"，推送至手机负一屏 | 菜鸟物流科技官网地图轨迹服务页；woshipm 实测 |
| oTMS（中大型 TMS） | 国际版 TMS 内置 ETA 计算模块，订单详情地图上方显示总里程+预计送达时间，并随在途位置动态更新 | oTMS 官网产品特性页 |

**关键行业事实**：据 woshipm 作者实测，**四通一达（中通/圆通/韵达/申通）官网及官方 App 本身并不展示预计送达时间**，用户在淘宝看到的 ETA 实际是菜鸟裹裹计算后叠加的；顺丰与京东则为自行计算全程 ETA。也就是说——**全网直营/快递龙头已把 ETA 当标配，但加盟制快递官网长期没有 ETA**。

### ② 中小客户（10-50 辆车）通常怎么定

面向中小专线/三方物流的 SaaS TMS 产品普遍已把"客户微信查货"作为卖点，并在查货页附带"预计到达时间"：

- **快货运 TMS**（中小物流 SaaS）："客户在微信上自助查单——运单状态、实时轨迹、**预计到达时间**、签收照片，全部自己看"，宣称催货电话减少 70%+。
- **傲蓝物流软件**（零担专线 TMS）：提供网页+微信物流查询，客户输单号查运输进度。
- **和物流**（专线 TMS）：发货方/收货方微信扫码查货、查位置。
- **易物流**（专线轨迹系统）：客户输姓名/手机号自助查轨迹。

即：中小 TMS 厂商已把"客户自助查轨迹"作为标配功能在卖，但 ETA 的精度普遍是"日期级"（预计 X 月 X 日到），而非顺丰/京东的"时段级"（上午/下午几点前到）。

### ③ 推荐默认值/默认做法

- **默认展示 ETA，但只展示日期级区间**（如"预计 10 月 10 日到达【XX 网点】"），不承诺精确时段。
- **ETA 触发时机**：货物完成揽收/发车节点后才开始展示；开单后未发车前不展示 ETA（因揽收时间不可控，参考菜鸟"揽收后才计算"的做法）。
- **数据源**：初期用"线路固定时效表"（发车日期 + 线路标准运输天数）推算，不依赖 GPS/路径优化；后续有 GPS 数据再迭代为动态 ETA。
- **加盟网点场景**：分拨到网点后，ETA 可写"预计今日/明日派送"，由派送网点到站时间驱动。

## 决策② 货物到网点中间状态的客户端文案

### ① 行业主流做法

各快递/物流开放平台已将轨迹状态标准化为枚举节点，客户端文案由系统状态码映射而来：

| 产品/平台 | 状态枚举与客户端文案惯例 | 来源 |
|---|---|---|
| 圆通开放平台 | GOT=已揽收；ARRIVAL=已收入（到达网点/分拨）；DEPARTURE=已发出；SENT_SCAN=派件；INBOUND=自提柜入柜；SIGNED=签收成功；FAILED=签收失败；FORWARDING=转寄；TMS_RETURN=退回 | 圆通开放平台物流查询接口文档 |
| 快递鸟（第三方聚合 API） | StateEx：201=到达派件城市；202=派件中；211=已放入快递柜或驿站；3=已签收；404=拒收（退件） | 快递鸟物流轨迹地图 API 文档 |
| 快递 100 / 百递云 | 10 个基础状态 + 37 个高级状态（待揽收/投柜或驿站/转递等），节点带时间+网点名 | 百递云物流追踪方案；CSDN 整理 |
| 中通（17TRACK 聚合展示） | "派送中"=包裹已分配给快递员或本地派送路线 | 17TRACK 中通 carrier 页 |
| 电商客服话术惯例 | "您的宝贝已经到达您的所在地了，快递人员会在近期为您安排派送，请保持通讯畅通" | 腾讯云开发者社区-售后客服用语 |

**文案惯例总结**：
- 到达分拨/网点："已到达【XX 分拨中心/XX 网点】"
- 离开网点："已从【XX 网点】发出"
- 到达派送城市/网点："已到达【XX 派送网点】"
- 派送员上门："派送中，派送员【姓名/电话】正在为您派送"
- 入柜/到驿站："已放入【XX 快递柜/XX 驿站】，取件码 XXX"

### ② 中小客户（10-50 辆车）通常怎么定

中小专线 TMS 的轨迹节点比头部快递简单得多，一般只录 4-6 个大节点：

- **易物流**（专线轨迹系统）：后台/司机端小程序批量更新物流动态，客户自助查询。
- **物牛帮 SaaS TMS**："从发到收，一张运单走天下，微信扫一扫实时知晓货物轨迹"。
- **飞扬 UTMS**：客户自主查货，运单信息同步推送。

中小专线一般不做"已收入/已发出"这种分拨级细颗粒度，而是：已开单 → 已发车 → 已到达目的网点 → 派送中 → 已签收。中间到网点节点的文案通常就是"已到达【XX 网点】"。

### ③ 推荐默认值/默认做法

客户端轨迹时间轴节点文案采用标准句式（带网点名+时间）：

| 节点 | 客户端文案模板 |
|---|---|
| 开单/揽收 | "已开单，等待司机提货" / "司机已提货" |
| 干线发车 | "【车牌/司机】已发车，运输途中" |
| 到达目的网点 | "已到达【XX 网点】" |
| 网点入库待派送 | "货物已到达【XX 网点】，待派送" |
| 派送中 | "派送员正在为您派送，请保持电话畅通" |
| 签收 | "已签收，签收人：XXX" |

- 每个节点必须带：**时间 + 网点/司机名称**。
- 文案风格：一句话、动宾结构、地点明确，避免内部术语（不用"已收入""已扫描"等运营黑话）。

## 决策③ 异常订单（拒收/取消）的客户端展示方式

### ① 行业主流做法

异常件在物流状态体系中是**独立的主状态**，而非普通在途状态的分支：

| 产品/平台 | 异常状态设计 | 来源 |
|---|---|---|
| 快递助手 API | 主状态 7=FAILED 包裹异常；子状态：RETENTION 滞留件、ISSUE 问题件、RETURN 退回件、DAMAGE 破损、CANCEL_ORDER 揽件取消 | 快递助手开放平台文档 |
| 快递鸟 | State=4 问题件；StateEx=404 拒收（退件）、401 发货无信息、402 超时未签收、403 超时未更新 | 快递鸟 API 文档 |
| 万维易源全球快递查询 | status=5 用户拒签；6 疑难件；7 无效单（完结）；9 签收失败 | 万维易源 API 文档 |
| TrackingMore（国际聚合） | exception 状态=退回发件人/收件人拒收/破损/其他异常；undelivered=派送失败 | TrackingMore API 文档 |
| Shopline Tracker | Canceled=因异常取消；Refused=收件人拒签；Exception=配送异常；Returning to sender=退回中 | Shopline 帮助中心 |
| 淘宝物流（商家侧） | 异常件有专门"消费者展示文案"（如"您的包裹因在运输途中破损，现商家与您沟通后给您补发"），并触发异常处理工单 | 淘宝开放服务文档 |

**UI 展示惯例**（综合上述状态体系与电商 App 通用设计）：
- 拒收/退回/取消 → 作为**独立状态标签**在订单列表/物流详情顶部显示（通常橙色/红色字样）。
- 轨迹时间轴保留最后一个正常节点 + 异常节点（如"收件人拒收，包裹退回中"），并附异常原因说明。
- 电商订单侧（淘宝/京东）：已取消订单在订单列表中通常**灰色置灰**展示，但物流详情页异常件本身是彩色提示+说明文案，不是全灰。
- 异常件不会"消失"，而是形成逆向轨迹（拒收→退回网点→退回发件人）。

### ② 中小客户（10-50 辆车）通常怎么定

- **oTMS**（中大型 TMS）：双方均可上报货物破损/丢失/拒收/延误/订单撤回等异常事件，可上传图片+选择原因码（Reason Code），异常实时同步给订单链条上所有用户。
- **众享驿站 App**：驿站端可做"包裹拒收"操作（拍照上传），拒收后包裹进入滞留件/异常退回流程。
- 中小专线 TMS 普遍把拒收/退回作为运单的独立状态字段（"已拒收""退回中""已退回"），并在客户查货页显示该状态。

### ③ 推荐默认值/默认做法

- **拒收/已取消订单：独立状态标签 + 说明文案，不做整体灰色置灰。**
  - 订单列表：状态列显示橙色"已拒收"/灰色"已取消"标签，可点击查看详情。
  - 物流详情：时间轴最后一条节点显示异常事件（如"收件人拒收，拒收时间 X 点 X 分"），下方附说明文案（"包裹将退回【XX 发货网点】，如有疑问请联系 XXX"）。
  - 已取消（开单后未发车取消）：订单列表灰色置灰，但详情仍可查看取消原因与取消时间。
- **拒收后**：系统自动生成逆向轨迹节点（"退回中""已退回发件网点"），客户可追踪逆向物流。
- 异常原因码建议内置：拒收、客户取消、地址不详、联系不上收件人、破损、超时未取。

## 决策④ 客户评价/评分功能是否为 TMS 标配

### ① 行业主流做法

| 产品 | 评价功能做法 | 来源 |
|---|---|---|
| oTMS oneTMS | 送达后"收货人可以对送货服务进行评价——包括对司机的评分"；终端用户 App"到哪了"支持时间轴查货+异常反馈+对运输服务评价 | oTMS 官网产品特性页；oTMS 标签页 |
| 菜鸟/淘宝物流评价 | 菜鸟官方推出"物流评价"产品：签收后用户可对快递公司/派送员星级评价，评价数据沉淀用于快递服务质量监控；淘宝订单物流详情页可单独评价快递派送员 | 菜鸟网络-快递服务平台页；太平洋 IT 百科教程 |
| 和物流（中小专线 TMS） | "发货方、收货方用微信扫描运单上的二维码，即可查看运单信息、货物位置，**还可对服务进行评价**" | 和物流官网 |
| 中通快递 | 官网/小程序设独立"投诉反馈"入口（投诉订单列表、在线客服） | 中通官网投诉页 |
| 京东物流 | 订单评价体系中含物流服务评分（京豆激励评价） | 澎湃新闻电商行业观察 |

**行业惯例总结**：
- 头部快递/电商平台：**签收后五星评分 + 差评标签（如"送货慢""态度差"）+ 投诉入口**已成熟。
- oTMS 等中大型 TMS：把"收货人评价司机/送货服务"作为标准功能模块。
- 面向中小专线的 TMS：和物流已内置扫码评价，但傲蓝、易物流、物牛帮等多数中小 TMS 官网主打"查货/对账/调度"，未明确把评价作为核心卖点。

### ② 中小客户（10-50 辆车）通常怎么定

- 中小专线物流的客户评价诉求弱于电商快递（B 端商贸客户更关注时效/到货准确/回单，而非 C 端五星好评文化）。
- 但**投诉入口**是必备的（异常件需要客户能找到人），而**主动五星评分**在中小专线场景使用率低。
- 中小 TMS 厂商做法分化：和物流等已内置轻量评价；多数则把评价作为可选模块或干脆不做。

### ③ 推荐默认值/默认做法

- **不做重评价体系，但默认内置轻量三件套**：
  1. **签收后 1-5 星评分入口**（微信/小程序内，签收完成页弹出"本次运输服务体验如何？"）；
  2. **可选文字评价 + 快捷标签**（"准时到达""货物完好""司机专业""送货延迟""态度差"）；
  3. **投诉/异常反馈入口**（一键联系网点客服电话 + 在线留言）。
- 评分结果仅在后台展示给物流企业管理者用于司机考核，不对公开展示（B 端客户不需要看到其他公司的评分）。
- 初期可先做"投诉入口 + 五星评分"，文字评价可后置迭代。
