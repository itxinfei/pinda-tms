## 严重度口径（重要 · 先读）

本报告 §1 问题表中的 **P0 / P1 / P2 是「问题严重度」**，与《优先级总览.md》里「需求优先级 P0/P1/P2」是**两套完全不同的口径**，请勿混淆：

- **P0（问题严重度）= 阻断级**：会导致大模型按错误前提编码、或交付方向错误/返工，**必须先修**。
- **P1（问题严重度）= 重要级**：明显影响一致性、排期可信度或编码效率，**应尽快修**。
- **P2（问题严重度）= 建议级**：口径过时、易误导、可在迭代中顺带修。

## §2 按维度汇总

**① 需求完整性（业务闭环）**：整体 5 角色 × 正向主链路（下单→调度→提货→在途→派送→签收）已闭环，但**逆向/异常流（拒收退款、部分签收、破损、丢件理赔）在 P0 几乎无规格**（BA-11）；上线必备的 E1 基础数据初始化、E3 试点 SOP 被排期漏掉（BA-05）；管理端字典模块悬空（BA-18）。

**② 可执行性（能否直接喂给大模型）**：三张主任务卡（客户 46KB、司机 29KB、FIN 64KB、OPS 54KB）字段/接口/状态/DoD 粒度很好，是可直接编码的。短板集中在：异常流无规格（BA-11）、Kafka 通知方案与红线关系不清（BA-09）、客户卡本地编号与总览撞车（BA-14）、坐标系空间关联未统一（BA-19）。

**③ 文档间一致性**：是本次问题最密集的维度。**最危险的是 BA-01**——D-03/总览让大模型去改一个源码实测「无人调用的死方法 depart()」，而真实状态桥早已由 pickUp/finish 打通；其次是 BA-02（P0-6a 与 P1-2 逐字重复）、BA-03（主文档 5 条 FR 优先级未随总览回写）、BA-04（FR-17 与 D-07 相反）、BA-06/BA-07（告警页/合规闸口口径打架）、BA-08（P0-4 已完成却仍排期待做）。

**④ 优先级合理性**：主体划分（三端/管理端/财务/外部渠道 P0，VRP/视频/外协 P1，智能深化 P2）合理；问题在**主文档 FR 级标注未随拍板回写**（BA-03）、**告警管理页 P0/P1 不一**（BA-06）、**P0-9 是否混入 P1 合规项**（BA-07）、**商业化把 P1 能力当 P0 卖点**（BA-16）。

**⑤ 估算可信度**：低限自洽，**高限普遍被压低约 10%–18%**（BA-10，总高限 577 vs 标注 520），W1–W8 排期实际工作量风险被掩盖；E1/E3 另漏 15–35 人日（BA-05）。

**⑥ 与定案 D-01~D-24 一致性**：发现 3 处直接冲突（详见 §4）：D-03、D-07、D-19。
