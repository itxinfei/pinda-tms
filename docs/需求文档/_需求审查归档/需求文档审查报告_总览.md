## 三、跨域热问题（P1 级，修复优先级高）

### 3.1 告警域口径三处打架（后端能力是 P0-5，但口径乱）
- **EC-02**：`alertType` 数据字典含 `ETA_DEVIATION`，链路测试 §8.2 造数写 `DEVIATE_ROUTE`（字典中不存在）。
- **EC-03**：告警 `status` 数据字典只定义 3 态（0/1/2），OPS 任务卡 DDL 与测试用例实现 5 态（0 未处理/1 已认领/2 已处理/3 已关闭/4 已忽略），且 1/2 含义完全不同——按字典对接会把"已认领"当"已忽略"。
- **EC-06/EC-07**：LocationEntity 的 `source/coordSystem` 字段 2026-10-07 已落地，但《后端接口文档》《联调清单》仍写"待开发"；告警接口数量三处 4/5/7 不一致。
- **BA-06**：告警管理页优先级三处打架（主文档 P0 共 6 页含告警 / 管理端卡 §六标 P1 / 总览 P0-3a 说 7 页含告警）。
- **BA-08**：OPS 卡 §2.6 通知设计用 Kafka 事件总线，与同卡硬约束"不引新中间件"及 P0-7d 估算（仅短信直连）冲突。

### 3.2 优先级口径不同步
- **BA-03**：主文档 v2.4 有 5 条 FR（FR-40 告警、FR-50 财务、FR-53 外协、FR-54 VRP、FR-58 视频）优先级标注仍为 P1/P2，未随总览拍板回写为 P0/P1。
- **BA-07**：P0-9"合规闸口 7 项"（25~35 人日）与全景/主文档"仅 3 项硬闸、FR-32~35 为 P1"冲突（与 EC-01 同源）。
- **BA-05**：上线差距清单把 **E1 基础数据初始化（5~15 人日）+ E3 试点 SOP 培训（10~20 人日）** 列为 P0 最小集，但优先级总览未收口，**约 15~35 人日上线必备工作悬空**。

### 3.3 逆向/异常流无规格（大模型只能自己发明）
- **BA-11**：拒收、部分签收、破损、丢件定责、理赔、订单级退款在 P0 几乎无落地接口与页面规格；FR-55/56 仅标 P2；快递员端 delivered 接口只支持签收/拒收两态，破损无入口。**建议在 P1 补一份逆向/异常流规格（状态枚举+接口+页面）。**

### 3.4 估算不自治
- **BA-10**：按子项加总，P0 高限实算 304（标注 280）、P1 高限 173（标注 150）、P2 高限 100（标注 90）、总计高限 577（标注 520）——**低限自洽，高限普遍被压低约 57 人日**。

### 3.5 与定案/红线的次要冲突（P2）
- **BA-15**：行政区划 §六 示例 SQL 用 `ROW_NUMBER()`，违反 D-19（MySQL 5.7.44 禁窗口函数）——实际导入已绕过，但年度重跑会踩。
- **BA-16**：差异化场景把"北斗+GPS 双模"当 P0 卖点，D-13 定案 P0 仅加坐标系字段、双模终端是 P1——销售口径超前。
- **EC-09**：管理端 OAuth2 例外（`Authorization: bearer`+refresh_token）已在一致性报告/定案 D-16 承认，但红线正文未写豁免，新人可能误改。
- **EC-15/EC-16/EC-20**：章节号重复（数据字典两个"十二"、一致性报告两个"五"、合规清单跳 §7）、CSV 引入 SRS 未定义的 P0b/P0c、任务 ID "P0-4" 跨卡重载。
- **BA-12**：定案数量三处不一致（21/18/实际 D-01~D-24 共 24 项）。
