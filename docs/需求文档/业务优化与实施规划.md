## 一、现有核心业务流程梳理

| 环节 | 现状（实测） | 关键代码 |
|------|------|------|
| **订单** | 下单 → 同步调百度地图 3 次（2 地理编码+1 距离）→ Drools 算费 → 落库；12 级订单状态机 | `pd-oms/.../OrderServiceImpl`、`BaiduMapUtils` |
| **仓储** | **无独立仓储模块**。"入库/出库"仅 `OrderStatus` 的两个状态节点（23003/23006），无库容/在库量/出入库流水概念 | grep 全库 `warehouse/stock/库存` 0 匹配 |
| **运输（调度）** | Quartz 周期触发 → 订单分类 → DFS 递归路径规划 → 建运输任务 → 车次/车/司机匹配 → 司机作业单 | `pd-dispatch/.../DispatchTask`、`TaskRoutePlanningServiceImpl` |
| **配送** | 运单 → 运输任务状态机 `depart/arrive/deliver` → 司机作业单 → 妥投后回调 oms 改订单为已签收 | `pd-work/.../TaskTransportServiceImpl` |
| **轨迹** | Netty TCP+HTTP 双通道收 GPS → Kafka `tms_order_location` → 消费批量落库 | `pd-netty/.../GpsTraceConsumer` |

## 二、瓶颈与冗余（证据化）

### P0 · 一致性 / 可用性（高风险）
1. **跨服务状态回调吞异常、无重试** — `pd-work/.../TaskTransportServiceImpl.syncStatusOnComplete`：对每运单循环串行 Feign 回调，失败仅 `log.warn`，订单与运单状态**永久不一致**；且回调在 `@Transactional` 内做远程调用。
2. **妥投三连 Feign 无事务无重试** — `pd-work/.../CourierController.delivered`：任一步失败即部分提交。
3. **Seata 全局事务实际未生效** — 仅引入 `seata-spring-boot-starter` 依赖 + `@GlobalTransactional` 注解，**无任何 yml 配置、无 DataSourceProxy/GlobalTransactionScanner**（`DispatchTask`、`CourierController` 上的注解不会真正回滚）。
4. **百度地图 HTTP 无超时** — `BaiduMapUtils.loadJSON`、`pd-common/.../EntCoordSyncJob.loadJSON` 仅 `openConnection()`，外部抖动即阻塞请求线程直至耗尽。（**已修复**）

### P0 · 正确性 Bug
5. **`isInScope` 修改入参** — `pd-common/.../EntCoordSyncJob.java:209` `polygon.remove(0)` 篡改调用方集合，同一多边形被重复判定时顶点逐步丢失，后续调用 `get(0)` 可能抛异常，影响调度分类的区域匹配。（**已修复**）

### P1 · 时效 / 成本
6. **调度分类在 `@Transactional` 内对每笔订单串行调百度+Feign，且订单全量拉取无分页** — `pd-dispatch/.../TaskOrderClassifyServiceImpl`：单机构一次调度 = 订单数 ×(~4 百度 + ~4 Feign)，长事务占 DB 连接。
7. **线路规划递归 DFS，每节点 2 次 Feign** — `TaskRoutePlanningServiceImpl.findLine`：机构网络大时远程调用随分支膨胀，无深度剪枝。
8. **车次匹配重复拉取同一批车次** — `TaskTripsSchedulingServiceImpl`：先 `findAll(lineId)` 后又 `findAll(null, ids)` 再分组查车/司机。
9. **运费/距离计算无缓存** — 同地址重复下单重复调百度 3 次。（**已加本地缓存**）
10. **GPS 落库失败丢数据** — `GpsTraceConsumer.doFlushPendingRecords` 先 `clear()` 再 `saveBatch`，DB 抖动即丢点仅记日志。

### P2 · 可维护性 / 扩展性
11. **订单状态机双份定义** — `pd-oms/.../OrderServiceImpl.ORDER_STATUS_TRANSITIONS` 与 `pd-work/.../StateTransitionValidator` 各一份，易漂移。
    > ❗**2026-10-06 复核修正（阻断级）**：早期结论"pd-work 副本仅为死代码"**是错的**。实测 `StateTransitionValidator` **在主链路被实际调用**：
    > `TaskTransportServiceImpl.java:243/287/331`（depart/arrive/deliver）、`TransportOrderServiceImpl.java:74/84`。
    > **严禁删除、严禁重写**。真实问题只是"双份定义"，收敛方向=让 pd-oms 那份**委托/对齐** pd-work 的校验器（或原样下沉 pd-common 但**保持调用点不变**），**不是新建第三套**。
12. **调度策略 if-else 堆砌** — `TaskRoutePlanningServiceImpl.defaultLine` 对距离/成本/时效/中转堆分支，新增模式需改代码。
13. **业务范围多边形以 JSON 字符串存储、客户端遍历判定** — 无空间索引，面积大时慢。

## 三、优化目标（量化 KPI）

| 维度 | 目标 | 衡量 |
|------|------|------|
| **时效** | 下单 RT 去同步算费/百度 3 连；调度耗时按订单数线性下降；轨迹零丢失 | P99 下单耗时、单轮调度耗时、丢点率 |
| **成本** | 百度 API 调用次数、跨服务 RPC 次数显著下降 | 单次下单外部调用数、单轮调度 RPC 数 |
| **差错率** | 跨服务状态最终一致；非法状态跳转被拦截；消除 `remove(0)` 类副作用 | 状态不一致工单数、算费失败率 |

  **❗已作废（2026-10-06）**：`StateTransitionValidator` 是**在用代码**（`TaskTransportServiceImpl:243/287/331`、`TransportOrderServiceImpl:74/84` 实际调用），删除会导致编译失败并丢失全部状态校验。

### 阶段二：一致性与可用性（需少量中间件/小改造）

## 五、代码模块改造 / 新增建议（落地清单）

| 方案 | 改动文件 | 新增/扩展点 | 可维护性设计 |
|------|------|------|------|
| 状态机收敛 | `pd-oms`、`pd-work` | **不新建**状态机：以 pd-work `StateTransitionValidator` 为唯一来源，pd-oms `ORDER_STATUS_TRANSITIONS` 委托对齐它（跨模块则原样下沉 pd-common，**调用点不变**） | 状态语义与校验规则单一来源，全模块引用；**禁止新增 `OrderStatusMachine` 之类的第三套**（与《多端数据打通》§3.3.1 红线一致） |
| 跨端状态同步桥 | `pd-work` | **新增同步组件**（非状态机）：depart→Order 23005、deliver→Order 23009 等联动集中在此，禁止散落 Feign 回写 | 解决"司机发车后客户看不到运输中" |
| 坐标缓存/超时 | `pd-oms/BaiduMapUtils`、`pd-common/EntCoordSyncJob` | `CacheValue` TTL 缓存（已完成） | 零依赖、可替换为 Redis 二级缓存 |
| 跨服务一致 | `pd-work` 回调处 | 新增 `StatusSyncEvent` + 本地消息表 + MQ 消费者重试 | 事件驱动，新增业务方只需订阅事件 |
| 调度策略 | `pd-dispatch/TaskRoutePlanningServiceImpl` | 新增 `ScheduleStrategy` 接口与 4 个实现，`ScheduleParams` 注入 | 新增物流模式零改分支 |
| 线路规划 | `pd-dispatch` | 新增 `TransportGraph`（启动时预加载线路为图） | 图结构可换权重策略 |
| 仓储领域 | `pd-base` + 新模块 | `Warehouse/StockMovement/Inventory` 实体 + 出入库服务 | 与订单状态机解耦、可独立扩展 |

**扩展性原则**：状态/策略/枚举下沉 `pd-common`；跨服务交互走**领域事件（MQ）**而非同步 Feign；新增物流模式（快递/快运/专线/三方）通过策略接口与枚举扩展，不堆 if-else。
