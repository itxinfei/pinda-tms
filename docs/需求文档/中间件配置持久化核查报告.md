## 二、你的问题①：Nacos 配置类型是 `text`，应该是 `yaml` 吗？

### 结论：**功能上没问题，不需要改。但建议统一。**

### 2.1 实测数据（`pinda-tms` 命名空间，17 条）

| 格式 | 数量 | 配置 |
|---|---|---|
| `yaml` | 11 | `common.yml` `redis.yml` `mysql.yml` `pd-auth-server-test.yml` `pd-base-prod.yml` `pd-work-dev.yml` `pd-druid-prod.yml` `pd-web-manager-dev.yml` `pd-web-driver-prod.yml` `pd-web-courier-prod.yml` |
| **`text`** | **6** | **`pd-gateway-test.yml`** `pd-oms-prod.yml` `pd-user-prod.yml` `pd-aggregation-prod.yml` `pd-dispatch-prod.yml` `pd-netty-prod.yml` `pd-web-customer-prod.yml` |

### 2.2 为什么 `text` 不影响功能

- **Nacos 的 `type` 字段只决定控制台编辑器的语法高亮**，不参与任何解析逻辑。
- **客户端解析由 `dataId` 后缀决定**：`pd-gateway-test.yml` 后缀是 `.yml` → Spring Cloud Alibaba 用 **SnakeYAML** 解析，与 `type` 无关。
- **实证**：`pd-gateway-test.yml` 虽为 `text`，但其中配置的 `server.port: 8760` 与 `context-path: /api` **已实际生效**（实测网关跑在 8760、context-path 为 `/api`）。
- **内容核查**：7 个 `text` 配置的首行有效内容分别是 `server:` / `spring:`，**全部是合法 YAML 结构**，没有任何格式损坏。

### 2.3 那为什么有些是 yaml、有些是 text？

创建时用的方式不同：Nacos 控制台**新建配置**时若没手动选类型、或通过 OpenAPI/脚本推送（`type` 未显式指定），会默认落成 `text`。历史上这两种方式混用，就留下了 11 yaml + 6 text 的混杂状态。

### 2.4 建议（可选，低优先级）

统一成 `yaml` 的**唯一好处是控制台编辑时有语法高亮、不易写错缩进**，对运行**零影响**。若要改，用控制台"编辑 → 编辑配置"里改类型，或 OpenAPI `PUT` 时带 `type=yaml`。**不要为了改这个而重启任何服务。**

## 三、你的问题②：容器重启配置会不会丢？（这才是真风险）

### 3.1 好消息：编排文件已经写对了

`deploy/middleware/docker-compose.infra.yml` **已经为所有中间件配置了数据卷挂载**：

| 服务 | 挂载 | 说明 |
|---|---|---|
| mysql57 | `/data/mysql:/var/lib/mysql` | ✅ |
| redis | `/data/redis:/data` + `--appendonly yes` | ✅ AOF 持久化 |
| **nacos** | `/data/nacos:/home/nacos/logs` **+ `/data/nacos-data:/home/nacos/data`** | ✅ **配置库已挂出** |
| zookeeper | `/data/zookeeper/data` + `datalog` | ✅ |
| kafka | `/data/kafka:/bitnami/kafka` | ✅ |
| rabbitmq | `/data/rabbitmq:/var/lib/rabbitmq`（整个目录，含 `.erlang.cookie`） | ✅ |

编排文件头部还专门写了注释说明这段历史：

> "原本只有 logs 被挂出，35 条微服务配置存在容器可写层的内嵌 Derby 里，`docker rm nacos` 即永久消失。"

### 3.2 ⚠️ 坏消息：这些挂载很可能**还没生效**

`deploy/middleware/` 目录下有 `migrate-data.sh`，其 `status` 函数用于查看现状。**文件里的这段话是关键**：

> "首次启用必须先迁移数据，否则容器内已有状态会随重建丢失"

**这说明：截至编排文件写成时，中间件还是裸 `docker run` 创建的，尚未迁移到 compose。** 编排文件顶部的注释也印证了这点：

> "此前这些容器由零散 docker run 创建、仓库中无可复现编排"

### 3.3 两种情况的后果（**这是你最需要确认的**）

| 现状 | 容器重启 | `docker rm` + 重建 | 结论 |
|---|---|---|---|
| **A. 容器仍带 compose label**（已迁移） | ✅ 配置保留 | ✅ 保留（从 /data 卷恢复） | 安全 |
| **B. 容器是裸 `docker run`**（未迁移） | ⚠️ 数据在容器可写层，**stop/start 保留、rm 丢失** | 💥 **配置全丢** | 高危 |

> Nacos 1.4.1 standalone 默认用**内嵌 Derby**，配置存在容器内 `/home/nacos/data/derby-data`。**若情况 B 成立，一次 `docker rm nacos` 就会丢掉全部 35 条配置。**

### 3.4 🔴 必须在服务器上执行的确认命令

本机无 `docker` CLI，无法代查。请在 **192.168.20.130** 上执行：

```bash
cd /path/to/deploy/middleware      # 即 docker-compose.infra.yml 所在目录

# 方式一（推荐，脚本自带只读状态检查）
sudo bash migrate-data.sh status
```

它会输出每个容器的 `project=` 字段：**有值 = 已被 compose 接管（安全）**；`project=无` = 仍是裸 run（高危）。

或手工逐个确认：

```bash
# 1) 是否已被 compose 接管（看 project 是否为空）
for c in nacos redis mysql57 zookeeper kafka rabbitmq; do
  echo -n "$c: "
  docker inspect -f '{{if index .Config.Labels "com.docker.compose.project"}}{{index .Config.Labels "com.docker.compose.project"}}{{else}}无(裸run){{end}}' $c
done

# 2) Nacos 数据是否已在挂载卷（关键！看 derby-data 是否在 /data/nacos-data）
ls -la /data/nacos-data/ 2>/dev/null          # 期望能看到 derby-data 或 config-data
docker exec nacos ls /home/nacos/data/        # 容器内对应目录

# 3) 三个路径的内容是否一致（判断数据到底在卷上还是容器层）
docker exec nacos du -sh /home/nacos/data
sudo du -sh /data/nacos-data
```

### 3.5 若确认是情况 B（裸 run），修复步骤

`migrate-data.sh` 已写好迁移逻辑，**逐个服务执行，每步可独立验证**：

```bash
cd deploy/middleware
sudo bash migrate-data.sh nacos        # 复制 derby-data 到 /data/nacos-data
docker compose -f docker-compose.infra.yml up -d nacos   # 让 compose 接管

# 迁移后务必复核配置数没变
curl "http://192.168.20.130:8848/nacos/v1/cs/configs?search=accurate&dataId=&group=pinda-tms&tenant=1cb93ce4-dc0e-4730-b759-d35fd7ed93c3&pageNo=1&pageSize=50"
# 期望仍为 17 条
```

> 脚本设计已考虑安全：目标目录非空会**直接拒绝**，避免覆盖已有数据。
> **zookeeper / kafka / rabbitmq 同理**，都需要单独迁移。

### 3.6 无论哪种情况，都建议做这件事

**把 Nacos 配置导出为文件，纳入版本管理。** 这样即使容器全毁，也能一条命令恢复：

```bash
# 导出全部 35 条（含所有命名空间与组）
mkdir -p .workbuddy/nacos-backup/$(date +%Y%m%d-%H%M)
# 按 dataId 逐条拉取并保存
for d in $(curl -s "http://192.168.20.130:8848/nacos/v1/cs/configs?search=accurate&dataId=&group=pinda-tms&tenant=1cb93ce4-dc0e-4730-b759-d35fd7ed93c3&pageNo=1&pageSize=50" | jq -r '.pageItems[].dataId'); do
  curl -s "http://192.168.20.130:8848/nacos/v1/cs/configs?dataId=$d&group=pinda-tms&tenant=1cb93ce4-dc0e-4730-b759-d35fd7ed93c3" \
    -o ".workbuddy/nacos-backup/$(date +%Y%m%d)/$d"
done
```

> 当前已有 2026-10-06 的 17 份备份（含网关路由与 Redis 配置的 `.new` 修改版），**配置内容本身不会丢**，风险只在于"下一次改动没有同步进备份"。

## 四、🔴 新发现：`DEFAULT_GROUP` 下有 17 个重复配置

### 4.1 现象

Nacos 命名空间 `1cb93ce4-dc0e-4730-b759-d35fd7ed93c3` 下，**两个 group 各有 17 条同名 dataId**：

| group | 条数 | 格式 |
|---|---|---|
| `pinda-tms` | 17 | 11 yaml + 6 text |
| `DEFAULT_GROUP` | 17 | 1 yaml + 16 text |

内容抽样对比确认**两者相同**（如 `common.yml` 首行都是 `spring:` → `jackson:` → `time-zone: GMT+8`）。

### 4.2 风险

- 各服务 `bootstrap.yml` 里配的是 `group: pinda-tms`，**实际只读 `pinda-tms` 组**，`DEFAULT_GROUP` 那 17 条是**永不生效的废弃副本**。
- 危险点：**将来有人看到 `DEFAULT_GROUP` 里也有 `pd-gateway-test.yml`，可能误改那一份** → 改了不起作用，排查时极难察觉。
- 若有人用不带 `group` 参数的 OpenAPI 拉取/推送，可能**误操作到 `DEFAULT_GROUP`**，造成配置分裂。

### 4.3 建议

确认无用后删除 `DEFAULT_GROUP` 下 17 条（**建议先备份**，或先逐一确认内容与 `pinda-tms` 组完全一致）。清理后配置只剩一处来源，排查问题不再困惑。

> ⚠️ 本次**未执行任何删除操作**（超出"只分析"范围，且需你确认）。

## 五、顺带澄清：网关 500 与持久化无关

你可能会怀疑网关 500 是配置丢失导致，**不是**：

- 实测**直连** auth-server `9000/menu/router` → **200**（auth-server 健康、Redis 通）
- 实测**经网关** `/api/authority/menu/router` → **500 pre:AccessFilter`

网关 500 的原因是**进程启动时没加载到新 Redis 配置**（连接池启动时装配，Nacos 后推不会重建），**重启网关进程即恢复**。详见《联调就绪检查清单》§2 前置①。
