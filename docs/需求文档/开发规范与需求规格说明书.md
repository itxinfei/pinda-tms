## 第 1 章 项目约束与红线（宪法级，必须最先读）

> **本章是最高优先级约束。任何开发任务都必须先满足本章，违反本章的改动一律视为不合格、必须回退。**

### 1.1 技术栈硬约束（不可变更）
1. **JDK 固定 1.8**，不得升级到 9/11/17/21/25。**任何 `pom.xml` 不得出现 Java 9+ 语法或模块系统（module-info）**。
2. **后端依赖版本锁定**（见 §2），**未经人工显式同意，禁止升级任何依赖**（含 Spring Boot、Cloud、Alibaba、MyBatis Plus、Druid、Shiro、Drools、Lombok、FastJSON 等）。
3. **安全问题不考虑**：不对 FastJSON 1.2.47/1.2.62、Shiro 1.4.0 等已知 CVE 主动发起升级或修复，除非用户明确指示。
4. **业务代码不降级/不重写**：保持现有分层（controller / service / service.impl / mapper / entity）与 MyBatis Plus 用法；不引入 Jakarta、不迁移到 jakarta 命名空间。

### 1.2 架构与边界红线
5. **新增功能优先复用现有能力**：三端 REST API（`pd-web-customer/driver/courier`）已存在，移动端直接调用，**后端能不改则不改**。
6. **后端"未实现的中间件"是用户路线图，不是缺失 bug**：MongoDB/HBase/Spark/Hive/ES/RocketMQ/MapStruct/Sentinel/SkyWalking/XXL-JOB 等，当前未落地是"计划内"，**不得把它们当成问题去补齐或"顺手"引入**。
7. **网关现状 = Zuul 1.x**（在 `pd-authority/pd-apps/pd-gateway`），**不是 Spring Cloud Gateway、无 Sentinel**。移动端生产走该 Zuul 网关；不得改写网关选型。
8. **模块职责严格不越界**：订单只在 `pd-oms`、调度只在 `pd-dispatch`、作业只在 `pd-work`、基础数据只在 `pd-base`、轨迹只在 `pd-netty`。新增实体/接口放到对应模块，不跨模块写业务。

### 1.3 开发行为红线（AI 编码代理最易犯的错误）
9. **禁止过度设计（YAGNI）**：不引入当前需求用不到的抽象层、设计模式、配置中心、消息队列、缓存框架。能用现有 Drools/Kafka/RabbitMQ/Quartz 解决的，不换方案。
10. **禁止"顺手"重构**：不重命名既有类/方法、不改既有接口签名、不动 `pd-admin-ui`（管理端 Vue2）源码，除非任务明确要求。
11. **禁止重复造轮子**：轨迹、鉴权、坐标/距离计算、状态机、运费等已有实现，新增功能必须调用既有实现；不得另写一套。
12. **禁止硬编码**：cron、阈值、地图 Key、坐标等配置必须外部化到 `bootstrap.yml` / Nacos / 配置文件；不写死在 Java/JS 中。
13. **禁止破坏编译/契约**：每次改动后必须保证受影响的模块 `mvn -o -q compile` 通过（本地用 JDK 1.8）；对外接口字段变更须同步更新本文档 §5、§6。
14. **先读后写**：改动任何文件前，必须先用 Read/搜索确认其现状与调用关系；禁止凭记忆或猜测写代码。

### 1.4 明确不做的"花架子"（本期一律不启动）
- 不盲目上 MongoDB / HBase / Spark / Hive / Elasticsearch / RocketMQ / XXL-JOB / Sentinel（路线图里有，但当前无对应痛点）。
- 不把管理端 `pd-admin-ui` 重写为 Vue3（纯迁移 2–4 周、零业务收益）。
- 不建重型 WMS（波次/上架策略/AGV）、不建多租户 SaaS、不建复杂 BI。
- 不对接外部厂商 / 三方物流 API（EDI/ERP/顺丰·三通一达/多式联运/国家合规）—— 本项目为自营 / 加盟运输管理，业务模式不涉及（详见 §6.9）。
- 不引入 GraphQL、不引入微服务网格、不做容器编排改造（除非用户单独指令）。

### 1.5 需求优先级定义
| 优先级 | 含义 | 退出标准 |
|---|---|---|
| **P0** | 首期必做，业务闭环必需 / 最大缺口 | 功能可用 + 走通端到端链路 |
| **P1** | 重要补齐，明显提升时效/成本/差错 | 功能可用 + 数据正确 |
| **P2** | 增强/按需，出现真实痛点再做 | 单点验证通过 |
| **路线图** | 仅规划，本期不做 | — |

## 第 3 章 架构规范

### 3.1 模块边界（改动前先确认归属）
| 模块 | 职责 | 新增内容归口 |
|---|---|---|
| pd-oms | 订单、12 级订单状态机、Drools 运费、百度地图 | 订单/运费相关 |
| pd-dispatch | Quartz 5 阶段调度、DFS 路径规划 | 调度/配载/可视化 |
| pd-work | 运输任务状态机、运单、司机作业、取派 | 作业执行 |
| pd-base | 车队/车辆/司机/线路/车次/货物/业务范围 | 基础数据/承运商 |
| pd-netty | Netty+Kafka 轨迹、HTTP 轨迹接口 | 轨迹上报/查询 |
| pd-web-customer/driver/courier | 三端 REST API | 仅当确须后端配合时小改 |
| pd-aggregation | 聚合查询 | 看板/大屏数据 |
| pd-authority（内嵌） | RBAC + Zuul 网关 | 不改动（独立脚手架） |

### 3.2 前后端职责
- **前端（uni-app / 管理端）**：页面、交互、表单校验、本地缓存、离线队列、坐标转换、轮询。
- **后端**：业务规则、状态机、数据持久化、鉴权、计费、轨迹接入。
- **禁止**：把业务规则（运费、状态流转、计费）放到前端硬编码；前端只调用、不计算核心规则。

### 3.3 统一响应与错误处理（沿用既有）
- 沿用项目既有 `R` / `Result` 包装类（以源码实际为准）。新增接口返回结构须与既有接口一致。
- 错误码沿用既有枚举；新增错误码须追加到既有枚举，不新建一套。

### 3.4 鉴权契约（移动端必须遵守）
- 鉴权 = **JWT**。移动端登录后持 JWT，请求经拦截器自动附加 **`token` 头**（配置 `authentication.user.header-name: token`，**不是 `Authorization`**）。
- 拦截器处理 401（**清 token 重登**，后端 `Token{token,expire}` 不返回 refreshToken，不要实现刷新流程）。
- **登录端点已实测确认（2026-10-05）**：`pd-auth-server` 提供 `POST /anno/login`（`{account,password,key,code}`）+ `GET /anno/captcha?key={uuid}` + `/anno/check` + `/anno/verify`；**不存在"需要新建登录"的情况**。
- **请求入口（实测修正）**：生产与开发**统一走 Zuul 网关** `http://<host>:8760/api`（前缀 `/api`）。
  ❗ **开发期不可直连 `pd-web-*` 8161~8164** —— `TokenAuthInterceptor` 已全部注册，缺 `userid` 头返回 401。仅 `/swagger`、`/error`、`/actuator` 放行。
- 各 `pd-web-*` 服务的 Zuul 路由前缀在 Nacos `pd-gateway-test.yml`（仓库内无该文件），需运行时读取确认。
- 详见《文档与代码一致性核查报告.md》。

## 第 4 章 编码规范

1. **命名**：类 PascalCase、方法/变量 camelCase；接口名以 `XxxService`、实现 `XxxServiceImpl`；Mapper 沿用 `XxxMapper`；实体在 `entity`。
2. **分层**：controller（入参/出参/鉴权）→ service（业务）→ mapper（持久化）；不在 controller 写业务，不在 mapper 写业务。
3. **事务**：写操作加 `@Transactional`（沿用既有）；跨服务用既有 Seata 注解（见 §6.12），不新造分布式事务方案。
4. **日志**：用项目既有日志门面（slf4j）；禁止 `System.out.println`；敏感信息（手机号/证件）脱敏。
5. **异常**：业务异常抛 `RuntimeException` 子类或既有业务异常；全局异常处理器沿用既有，不新建。
6. **配置外部化**：cron、阈值、地图 Key、坐标类型、上报间隔等一律进配置文件/配置中心；不硬编码。
7. **SQL/MyBatis**：复杂查询用 MyBatis Plus 或 XML；禁止在循环内逐条查库（N+1），批量用 `in` 或批量接口。
8. **前端**：页面放 `pages/<角色>/`；公共能力放 `common/`；API 调用放 `api/`；状态放 `store/`；禁止在页面里写裸 `uni.request`（必须过拦截器）。

## 第 6 章 功能需求详细规格

> 每条需求格式：**编号 / 名称 / 优先级 / 用户故事 / 功能点 / 界面/接口 / 数据 / 验收标准**。编号前缀：ORD=订单, DSP=调度, CAP=运力, TRK=在途, POD=回单计费, DIS=配送, DRV=司机, CST=客户, EXC=异常, PER=绩效, WMS=仓储。

### 6.1 订单与运单（ORD）
- **ORD-01 客户极简下单** ｜ P0
  - 故事：客户在小程序填写寄/收件人与货物，即时看到运费并下单。
  - 功能：地址簿复用、货物选择、调用 `mailing/totalPrice` 试算、`mailing` 提交、`pay/{id}` 支付。
  - 验收：3 步内完成；运费与后端 Drools 一致；下单后状态进入 12 级状态机首态。
- **ORD-02 订单全程可视化** ｜ P0
  - 功能：状态时间轴（`mailing/detail`）+ 轨迹（`/trace/*`）+ 预计送达（前端估算/后期 ETA）。
  - 验收：每个状态节点有时间；轨迹可在地图渲染。
- **ORD-03 运费明细透明** ｜ P1
  - 功能：展示首重/续重/距离/优惠明细（基于 Drools 规则）。
  - 验收：明细与总价一致，可解释。
- **ORD-04 异常订单处理流** ｜ P1
  - 功能：滞留/退回/破损专用状态 + 管理端处理界面（沿用 12 级状态机扩展）。
  - 验收：可人工干预流转并记录原因。
- **ORD-05 运单拆分/合并** ｜ P1
  - 功能：按线路/时效/货物属性合单、拆大单（**后端新建**：`pd-oms` 新增合单/拆单服务）。
  - 验收：合单后生成主运单+子运单，状态联动。
- **ORD-06 在线报价（客户门户）** ｜ P1
  - 功能：客户自助试算（复用 `mailing/totalPrice`）。
  - 验收：无需电话询价。

### 6.2 智能调度（DSP）
- **DSP-01 运输闭环看板（管理端）** ｜ P0
  - 功能：调度→分配→发车→在途→到达→交付全链路可视化（数据来自 `pd-aggregation`/既有聚合）。
  - 验收：看板实时反映状态；可下钻到运输任务。
- **DSP-02 在途监控** ｜ P0
  - 功能：实时位置（轮询 `/trace/latest`）+ 轨迹回放（`/trace/replay`）。
  - 验收：地图显示车辆实时点；回放可拖动。
- **DSP-03 调度过程可解释** ｜ P1
  - 功能：把 5 阶段调度结果（路线/成本/策略）可视化，支持人工干预覆盖。
  - 验收：调度结果可查看与人工调整。
- **DSP-04 智能配载** ｜ P1

### 7.1 工程结构（单工程三端分包）
```
pinda-uni-app/
├── common/        # request 拦截器、api/ 层、utils（坐标转换/日期）、store(Pinia)
├── components/     # 地图轨迹、扫码、POD 签名、异常上报、离线队列

└── pages.json      # 三端分包 + 条件编译入口
```
- 三端通过**分包 + 条件编译（`#ifdef MP-WEIXIN` 等）**共享登录/地图/扫码/POD。

- `common/store/user.js`（Pinia）：登录态、token、角色。
- `common/utils/offline.js`：离线队列（基于 `uni.setStorageSync`）。

### 7.3 页面清单（首期 P0）

| 客户 | 登录、地址簿、寄件（运费试算）、运单列表、运单详情、轨迹地图、电子回单 | §5.1 |

## 第 12 章 UI 设计规范（强制引用）

> 移动端页面样式与结构受《UI 设计规范与页面模板.md》约束，与本章同等强制力。核心红线摘录：

1. **只用组件库，不写裸样式**：100% 使用 uview-plus 组件，禁止用 `<div>`+`<style>` 替代布局/按钮/卡片。
2. **Token 全集中**：颜色/间距/字号/圆角/阴影只允许引用 §6 的 CSS 变量或 `uni.scss` 主题变量，禁止页面内写死 hex/px。
3. **三端同视觉**：客户/快递员/司机共用同一套 Token 与组件，仅做角色化强调（司机端按钮更大、对比更强），禁止三端各一套。
4. **结构走模板**：列表/详情/表单/地图/任务大厅/POD 六类页面套用标准骨架（见 UI 规范 §4），禁止自由布局。
5. **三态必做**：加载中/空/错误统一用组件库，禁止缺失其一。
6. **统一反馈**：加载/空/错/提示/确认/刷新分页全部走 uview-plus 组件，禁止自造。
7. **禁止清单**（详见 UI 规范 §7）：禁裸 HTML 布局、禁硬编码色值、禁第二套 UI/图标库、禁 emoji 图标、禁缺三态、禁绕过 `u-navbar`、`uni.request` 必须过拦截器。
8. **主题一处改全端生效**：`uni.scss`（覆盖 uview-plus 主题）+ `common/styles/variables.scss`（业务 Token）为唯一真源。
