## 1. 行业公认的 TMS 需求版图

### 1.1 标准 7 模块（物牛帮）
基础信息管理 → 订单管理 → 运输调度 → 在途跟踪 → 费用结算 → 签收与回单 → 数据分析报表

### 1.2 行业 10 模块（世纪新成，更贴近商业产品）
1. 订单管理（ERP/WMS/电商接入、自动归集去重、拆合单）
2. **智能调度**（AI 引擎：位置/载重/时间窗/车型/司机偏好，效率提升 8×）
3. **承运商管理**（入驻→资质审核→KPI 考核→淘汰，黑名单自动过滤）
4. GPS 轨迹追踪（异常停留/到货预测/电子围栏，兼容 120+ 设备）
5. **运费结算**（20+ 计费方式，自动对账单，对账效率 +90%）
6. 财务报表（按线路/客户/承运商/车型/时段多维成本）
7. **客户自助服务**（WEB/APP 查运单、下对账单、发起异常申诉，减 80% 客服）
8. 移动端 APP（司机接单→导航→到达确认→回单上传；调度实时地图）
9. 系统对接（SAP/Oracle/用友 ERP、WMS、GPS、保险标准 API）
10. **增值服务**（供应链金融/运费垫付、ETC/油卡、保险集成）

### 1.3 商业产品的共性能力（跨通天晓/唯智/oTMS/科箭/G7/纷享链）
- **多角色协同门户**：货主 / 承运商 / 司机 / 客户 / 调度 / 财务 各有入口（oTMS 的 SaaS 协同、科箭的仓配一体、G7 的车队经营视角）。
- **计费引擎 + 在线对账 + 发票**：普遍把"运费核算"当成核心而非附属（科箭"在线结算与对账"、BCKFreight 进出发票+日记账）。
- **控制塔 Control Tower**：在途可视化大屏（通天晓 SCV、物牛帮"运输控制塔"），而非仅列表。
- **异常全生命周期**：识别→分类→处理→归因（通天晓把异常当作管理提升抓手）。
- **电子围栏 + ETA 预测 + 温层监控**：在途预警的标配三件套。
- **合规强绑定**：Load Logistics 把 ELD/HOS/IFTA/OBD/电子文档做成产品底座；这和我们"合规硬闸口"思路一致，且更重车载合规。

## 2. 别人是怎么"写需求"的（需求工程实践，最值得借鉴）

我方 v2.1 强在"现状实测 + FR 编号 + RTM"，但**需求组织颗粒度**上，开源项目给出了更成熟的范式：

| 实践 | 代表项目 | 具体做法 | 我方现状 | 建议 |
|---|---|---|---|---|
| **状态生命周期 + 就绪门禁** | Open TMS | 明确 `draft→ready→in_progress→complete`，离 draft 前必须过 readiness gate（客户/线路/承运商/日期等齐全），否则不可前进 | 有 12 级状态机 + `StateTransitionValidator`，但**无"就绪门禁"概念**，仅做状态守卫 | 在 §6.1 补充"下单/建运输任务前的必填门禁" |
| **状态变更审计日志** | Open TMS / EvolveTMS | 每次状态流转记录 acting user + 时间 + 前后态 | 仅有状态机校验，**无流转审计表** | 新增 `pd_status_audit` 或复用操作日志 |
| **异常作为正交维度** | Open TMS | 异常是独立于状态机的 flag，可挂任意节点 | 异常当"告警"处理（FR-40/P1），无统一异常模型 | 抽象 `ExceptionFlag` 概念，FR-55 升级为 P1 |
| **RBAC 角色矩阵** | EvolveTMS | Admin/Carrier/Shipper/Viewer 四角色 + 权限表 | 有角色但**无"角色×功能"权限矩阵文档** | 新增"权限矩阵"小节 |
| **软删除 / 归档** | Open TMS / EvolveTMS | 运单可归档（可恢复）、软删 | 未提及 | 数据模型补 `deleted/archive` 约定 |
| **自助门户作为独立需求类** | 世纪新成 / oTMS | 客户自助、承运商协同门户单列模块 | 客户端算"三端"之一，但**无"承运商门户"** | 增补承运商协同门户 FR |
| **财务 AR/AP 分离** | EvolveTMS / BCKFreight | 应收（客户）+ 应付（承运商）+ 对账 + 日记账分开建模 | 仅"结算单+对账"（FR-50~52，P2） | 结算域细化时引入应收/应付双账 |
| **需求分层（功能/非功能/集成/数据）** | 行业通用 | 明确区分功能需求、NFR、集成需求、数据需求 | 混在一处，NFR 极薄（见体检报告） | §4 后补"非功能需求"独立章节 |

## 3. 功能覆盖对标表（我方 v2.1 vs 行业）

| 能力维度 | 我方 v2.1 | 行业标配 | 差距判定 |
|---|---|---|---|
| 订单状态机 | ✅ 12 级 | ✅ | 无差距（我方更深） |
| 运输调度 / 配载 | ✅ DFS 路径规划 | ✅ AI/VRP + 时间窗 | 🟡 算法深度差（P2 升级） |
| 在途跟踪 | ✅ Netty+Kafka | ✅ GPS/北斗 + 电子围栏 + ETA | 🟡 缺电子围栏/ETA 显式（ETA 在 P1） |
| 基础数据 | ✅ 20 表 | ✅ | 无差距 |
| **承运商全生命周期** | ❌ 仅外协运力池(P2) | ✅ 入驻/资质/KPI/竞价/黑名单 | 🔴 **重大缺口** |
| **运费结算深度** | ❌ 结算单+对账(P2) | ✅ 自动计费+在线对账+发票+多维度 | 🔴 **重大缺口** |
| **客户/承运商自助门户** | ⚠️ 仅客户小程序 | ✅ 客户自助 + 承运商协同门户 | 🔴 缺承运商门户 |
| **控制塔 / 数据大屏** | ⚠️ 在途监控(FR-06) | ✅ 控制塔可视化 | 🟡 偏列表，缺大屏 |
| **异常全生命周期** | ⚠️ 告警中心(P1) | ✅ 识别→定责→理赔闭环 | 🟡 需升 P1 并建模 |
| 电子回单 / POD | ⚠️ POD 拍照+签名(P0) | ✅ 回单影像 + 状态追踪 + 归档 | 🟡 缺回单归档/状态机 |
| 多式联运 | ❌ 不做（自营） | ✅ 公铁水空组合 | 🟢 合理不做 |
| 供应链金融 / ETC / 油卡 | ❌ 不做 | ✅ 增值标配 | 🟢 三期再议 |
| 合规（车载/数据） | ✅ 7 项硬闸口 | ✅ ELD/HOS/IFTA/等保 | 🟢 我方更严（差异化优势） |

**核心结论（与 v2.1 §3.3 一致但更具体）**：
1. 我方**骨架 + 状态机 + 调度 + 在途**已达行业水平；
2. 真正的代际差距集中在三块：**① 承运商全生命周期管理**、**② 运费结算深度（AR/AP/对账/发票）**、**③ 客户/承运商自助协同门户**；
3. 需求**写法**上应补：就绪门禁、流转审计、异常正交模型、RBAC 矩阵、软删、NFR 分层。

## 4. 对 v2.1 的具体改进建议（可落地项）

### 4.1 增补"需求工程"章节（不改功能，只改写法）
- 新增 **§6.4 状态就绪门禁**：明确下单 / 建运输任务前的必填校验清单。
- 新增 **§9.4 权限矩阵（RBAC）**：角色 × 功能权限二维表（Admin/Manager/Dispatcher/Driver/Courier/Customer/Carrier）。
- 新增 **§4.3 非功能需求（NFR）**：并发（同时在线司机数）、轨迹上报 QPS、接口 SLA、数据保留策略（审计≥6月/业务≥3年）、可用性目标。
- 异常模型：将 FR-55（异常全生命周期）由 P2 升 P1，并抽象"异常为正交维度"概念。

### 4.2 增补功能 FR（补齐行业标配缺口）
| 新编号 | 功能 | 优先级 | 借鉴 |
|---|---|---|---|
| FR-61 | **承运商全生命周期**（入驻/资质审核/KPI 考核/竞价/黑名单） | P1 | 世纪新成模块3、行业标配 |
| FR-62 | **承运商协同门户**（接单/回单/对账自助） | P2 | oTMS、纷享链 |
| FR-63 | **结算域深化：应收(客户)+应付(承运商)双账 + 发票 + 日记账** | P2 | EvolveTMS、BCKFreight、科箭 |
| FR-64 | **控制塔大屏**（在途全景 + 异常热力 + KPI） | P1 | 通天晓 SCV、物牛帮 |
| FR-65 | **电子围栏 + ETA 预测**（强化在途预警） | P1 | 世纪新成模块4、行业标配 |
| FR-66 | **回单影像归档与状态机**（回单已传/已确认/异常） | P1 | 唯智回单影像、行业回单管理 |
| FR-67 | **软删除 / 归档**通用数据约定 | P1 | Open TMS、EvolveTMS |

### 4.3 验收标准模板（解决体检报告"可测性 3.0"短板）
每个 P0 FR 增加"验收标准"列，格式：
> 给定 [前置]，当 [操作]，则 [可观测结果] + [量化阈值]。
例：FR-01 订单列表"支持按状态+时间筛选，返回条数≤分页大小，响应 P95<800ms"。

## 5. 结论

- **功能广度**：我方当前覆盖 ≈ 行业 7 标准模块中的 5.5 个（缺承运商全生命周期、结算深度、自助门户），属"能跑通主干的执行型 TMS"，尚未达到"经营型/平台型 TMS"。
- **需求写法**：我方在"现状真实性、边界清晰、可追溯"上优于多数开源项目；但在"状态就绪门禁、流转审计、异常正交、RBAC 矩阵、NFR 分层、验收标准"上落后于 Open TMS / EvolveTMS 这类工程化更成熟的项目。
- **优先级建议**：把 FR-61（承运商）、FR-64（控制塔）、FR-65（围栏/ETA）、FR-67（软删）纳入一/二期；FR-62/63（门户+结算深化）放三期；多式联运/供应链金融明确不做。

> 本报告与《需求文档 v2.1》《产品差距与商业化升级路线图》互为补充：v2.1 是需求主文档，路线图是战略，本报告是"外部对标输入"。
