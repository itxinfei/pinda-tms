# 数据字典与枚举口径（跨端唯一真源）

> **日期**：2026-10-06
> **来源**：从源码 `pd-service-api` 的 17 个枚举类**逐条提取真实取值**（非推测）
> **用途**：三端 + 管理端 + 后端**共用同一套口径**，避免"同一个状态各端理解不同"导致的跨端 bug
> **价值**：状态值是本项目跨端 bug 的第一高发点（前端写死 23005、后端返回 23006、测试按 6 理解…），本表是唯一裁决依据

---

## 〇、使用规则（先读，否则本表会被用错）

| 规则 | 说明 |
|---|---|
| **① 禁止在前端硬编码数字状态** | 一律用后端返回的 `code`，中文名只用于**展示**。前端写 `status == 23005` 是 bug 源头 |
| **② 本表是唯一口径** | 文档、代码注释、数据库取值**冲突时以本表为准**（本表由源码提取） |
| **③ 新增枚举必须回写本表** | 后端加状态而本表未更新 → 视为未完成（DoD 卡点） |
| **④ 状态流转必须走校验器** | `StateTransitionValidator` 已实现且在用，**禁止绕过**（详见 §7） |
| **⑤ 中文名仅供展示** | 枚举第二个参数是**英文名**（如 `IN_TRANSIT`），中文对照取自 `OrderDTO` 注释，**两者都要以本表为准** |

## 一、订单状态 `Order.status`（12 级，核心中的核心）

> 源码：`pd-service-api/pd-service-oms-domain/.../enums/OrderStatus.java`
> ⚠️ 枚举类里只有英文名，**中文对照取自 `OrderDTO.java:144` 注释**（已交叉核对）

| code | 枚举名 | 中文含义 | 客户视图档位 | 阶段 |
|---|---|---|---|---|
| 23000 | `PENDING` | 待取件 | 待取件 | 下单后 |
| 23001 | `PICKED_UP` | 已取件 | 运输中 | 取件 |
| 23002 | `OUTLETS_SINCE_SENT` | 网点自寄 | 运输中 | 网点 |
| 23003 | `OUTLETS_WAREHOUSE` | 网点入库 | 运输中 | 网点 |
| 23004 | `FOR_LOADING` | 待装车 | 运输中 | 装车 |
| 23005 | `IN_TRANSIT` | **运输中** | 运输中 | 干线 |
| 23006 | `OUTLETS_EX_WAREHOUSE` | 网点出库 | 运输中 | 网点 |
| 23007 | `TO_BE_DISPATCHED` | 待派送 | 派送中 | 末端 |
| 23008 | `DISPATCHING` | **派送中** | 派送中 | 末端 |
| 23009 | `RECEIVED` | 已签收 | 已完成 | 终态 |
| 23010 | `REJECTION` | 拒收 | 异常 | 异常终态 |
| 23011 | `CANCELLED` | 已取消 | 已取消 | 异常终态 |

### 🚨 发现的代码注释笔误
`OrderDTO.java:144` 注释末尾写的是 **`230011`为已取消** —— **多了一个 0**。
✅ 正确值是 **`23011`**（见 `OrderStatus.CANCELLED`）。
**引用该注释时务必纠正**，否则会造出永不命中的状态判断。

### 客户视图 4 档映射（客户端展示用）
客户不关心 12 个细分状态，只看 4 档（与《多端数据打通与统一领域模型》§4.3 一致）：

| 客户档位 | 覆盖的 code |
|---|---|
| 待取件 | 23000 |
| 运输中 | 23001 ~ 23006 |
| 派送中 | 23007、23008 |
| 已完成 / 异常 | 23009（完成）、23010/23011（异常分支） |

> ⚠️ **映射必须查表实现，严禁区间判断**。写成 `status >= 23001 && status <= 23006` 是错的——一旦中间插入新状态就会漏。
> 建议后端在 DTO 里直接多返回一个 `customerStatus` 字段，由后端统一映射，前端不做区间判断。

## 七、状态机约束（枚举之外的强制规则）

### 7.1 校验器已实现，**禁止重写**

`StateTransitionValidator`（pd-work）已实现并在用：

| 调用方 | 行号 |
|---|---|
| `TaskTransportServiceImpl` | 243 / 287 / 331 |
| `TransportOrderServiceImpl` | 74 / 84 |

- 已覆盖：订单 12 级 + 运单双维度 + 运输任务 5 级。
- **真实缺口是"跨端同步桥"**（如司机发车未联动 `Order` 23005），**不是校验器本身**。
- ❌ 严禁新建/重写状态机；✅ 缺什么补什么。

### 7.2 状态更新必须带条件（防并发覆盖）

`TaskTransport.depart/arrive/deliver` 用 `LambdaUpdateWrapper + eq(status=期望值)` 做条件更新（**状态机守卫 / CAS**），全项目**无 `@Version` 乐观锁**。

> ⚠️ 新增状态变更接口时**必须沿用条件更新**，不要直接 `setStatus()`——否则并发下会状态错乱。

## 九、统一响应与错误码

### 9.1 业务服务响应（`Result extends HashMap`）

| 字段 | 含义 |
|---|---|
| `code` | **0 = 成功**，非 0 = 失败 |
| `msg` | 错误信息 |
| `data` | 业务数据 |

### 9.2 权限服务响应（`R<T>`）

| 字段 | 含义 |
|---|---|
| `code` | **0 = 成功**，-1/-2 = 失败 |
| `data` / `msg` | 数据 / 错误信息 |
| `isSuccess` / `isError` | 布尔便捷字段 |

> ⚠️ **两套响应结构并存**（业务 `Result` vs 权限 `R`），统一以 **`code === 0`** 判成功，不要只看 `isSuccess`。

### 9.3 常见错误码（联调实测）

| code | msg | 场景 | 处置 |
|---|---|---|---|
| 0 | ok | 成功 | — |
| 40003 | 缺少token参数 | 未带 `token` 头 | 前端拦截器问题 |
| 40005 | 解析token失败 | token 无效/过期 | 重新登录（有效期 7200s） |
| -1 | 系统繁忙~请稍后再试~ | 下游服务不可达 | 探活，见《环境故障排障手册》§1 |
| 500 | `pre:AccessFilter` | 网关鉴权层故障 | 见排障手册 §3 |

## 十、枚举使用规范（DoD 卡点）

开发/评审时逐条检查：

- [ ] 前端**未硬编码**任何状态数字（`status == 23005` ❌）
- [ ] 状态展示**中文名**来自统一映射表，非前端自造
- [ ] 客户视图 4 档由**查表**实现，非区间判断
- [ ] 新增状态时：改枚举 → **回写本表** → 更新状态机校验 → 通知三端
- [ ] 状态变更接口**带条件更新**（`eq(status=期望)`），非裸 `setStatus`
- [ ] 跨端对接时按**枚举类**区分 `CONFIRM`（司机作业=改派 / 运输任务=待确认）

## 十二、本次排查发现的 3 处口径陷阱（重点提醒）

| # | 陷阱 | 后果 | 规避 |
|---|---|---|---|
| 1 | `OrderDTO.java:144` 注释写 **`230011`**（多一个 0） | 造出永不命中的判断 | 以 `OrderStatus` 枚举为准 = **23011** |
| 2 | `DriverJobStatus.CONFIRM(3)`="**改派**" vs `TransportTaskStatus.CONFIRM(3)`="**待确认**" | 同 code 不同义，跨端必错 | 按**枚举类**区分，不只看 code |
| 3 | `*AssignedStatus.MANUAL_DISTRIBUTED` 英文="已人工分配" 但中文="**待**人工分配" | 语义相反，判断错乱 | 一律以**中文**为准 |

> 🎯 这三处都是**源码级陷阱**，文档不写出来后人必然踩。建议在 IDE 里给这三处也加个注释标记。
