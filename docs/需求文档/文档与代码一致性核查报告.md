## 一、阻断级错误（不改必踩坑）

### ❌ 错误 1：文档说"三端无登录接口，需 P0-0 新建" —— 实际登录接口**已存在**

**文档原话**（三张任务卡 §1 阶段 0）：

> | 登录接口 | 全仓搜索 `login` | **当前缺失** → 触发 P0-0 |

**代码真相**：`pd-authority/pd-apps/pd-auth/pd-auth-server/.../controller/auth/LoginController.java` 已完整实现：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/anno/login` | 账号密码登录，入参 `{account, password, key, code}`；**必须先过验证码** |
| POST | `/anno/loginTx` | 租户登录（同逻辑） |
| GET | `/anno/captcha?key={uuid}` | 获取验证码图片（image/png），`key` 由前端生成 UUID |
| GET | `/anno/check?key=&code=` | 校验验证码 |
| GET | `/anno/verify?token=` | 校验 token 有效性 |
| GET | `/anno/token?account=&password=` | **仅供测试**，代码内已判断 `prod` 环境直接拒绝 |

返回体 `R<LoginDTO>`：`{user: UserDTO, token: {token, expire}, permissionsList: []}`。

**处置**：
- 三张任务卡的 **P0-0「新增登录接口」应改为「对接既有 `/anno/login`」**，不是从零新建。
- 移动端真实工作量变成：① 渲染验证码（`GET /anno/captcha?key=uuid` → 前端生成 uuid，图片直显）；② 或新增一个**免验证码的移动端登录口**（如 `/anno/loginMobile`，走短信码/微信 `code2Session`，这才是真正要补的部分）；③ 登录成功后把 `token` 写入 `token` 请求头。
- 严禁再写一个平行登录服务。

### ❌ 错误 2：文档说"开发期直连 `pd-web-*` 端口" —— 实际**直连必被 401 拒绝**

**文档原话**（三张任务卡 §1）：

> | driver 服务直连端口 | 查 `bootstrap.yml` | 拿到端口/服务名 | **开发期直连用** |

**代码真相**：`pd-common/.../interceptor/TokenAuthInterceptor.java` 已在 **4 个 pd-web 模块全部注册**（`ConfigurationSupport.addInterceptors`，driver/courier/customer 各一份，manager 在 `SwaggerConfig`）：

```java
String userId = request.getHeader("userid");
if (StringUtils.isBlank(userId)) {
    response.setStatus(401);
    response.getWriter().write("{\"code\":401,\"msg\":\"未登录或身份信息缺失，请通过网关访问\"}");
    return false;   // 除 swagger/error/actuator 外全部拦截
}
```

**结论**：`userid` 头**只有网关才会注入**（`TokenContextFilter` 解析 JWT 后 `addZuulRequestHeader`）。直连 8162/8163/8164 调任何业务接口 → 一律 401。

**处置**：
- 任务卡中"开发期直连"**全部作废**，改为：**开发/生产统一走网关** `http://<host>:8760/api`。
- 端口 8161~8164 仅用于**健康检查/actuator**，不能用于业务联调。
- 若确需本地直连调试，只能临时用 `-D` 开关或放行 header，**不得改拦截器逻辑**（红线）。

### ❌ 错误 3：司机端任务卡写 `/trace/latest?orderId=` —— 实际**只接受 `businessId`**

**文档原话**（司机端任务卡 §6）：

> | GET | `/trace/latest?orderId=` | 最新位置（track 页轮询） |
> | GET | `/trace/replay?orderId=` | 轨迹回放点串 |

**代码真相**：`pd-netty/.../GpsTraceController.java`

```java
@GetMapping("/latest") public Result latest(@RequestParam("businessId") String businessId,
                                            @RequestParam(value="type", required=false) String type)
@GetMapping("/replay") public Result replay(@RequestParam("businessId") String businessId,
                                            @RequestParam(value="type", required=false) String type)
@PostMapping("/page")  public Result page(@RequestBody Map<String,Object> params)  // 支持 transportTaskId
```

**没有 `orderId` 参数**。`businessId` = 车辆ID 或快递员ID；`type` = `truck` / `courier`。

**处置**：
- 司机端轮询改为 `GET /trace/latest?businessId={truckId}&type=truck`（司机需先拿车牌/车辆 id，可从 `business/car/info` 取）。
- **客户按订单号查轨迹仍然无解** —— 这与《多端数据打通与统一领域模型》§4 的判断一致，属**待后端改造项**（`/trace` 增 `transportTaskId` 入参，或 `/trace/page` 开一个按 `orderId` 解析的口子）。任务卡不能再写 `orderId`。

## 二、重要偏差（影响实现细节）

### ⚠️ 偏差 4：JWT 请求头字段 —— 是 **`token`**，不是 `Authorization`

- 网关 `TokenContextFilter` 读 `authClientProperties.getUser().getHeaderName()`；
- 配置前缀 `authentication`，讲义与 Nacos 配置为 `authentication.user.header-name: token`、`expire: 43200`（12 小时）。
- 网关解析后向下游注入：`userid` / `name` / `stationid` / `account` / `orgid`。
- 移动端拦截器应写：`headers: { token: <token> }`。

> 附带风险：`pd-admin-ui/src/utils/request.js` 用的是 `Authorization: 'bearer ' + getToken()`，与网关配置的 `token` 头**不一致**（管理端可能另有 OAuth2 通道或历史遗留）。**移动端务必用 `token`**，管理端这一处列为"运行时实测确认项"，不要在移动端照抄管理端写法。

### ⚠️ 偏差 5：登录返回**没有 refreshToken**

`LoginDTO.token` → `Token{ token, expire }`，**只有两个字段**。而 `pd-admin-ui` 前端存在 `getRefreshToken()` / `queryRefreshToken()` 刷新逻辑 —— 后端从不返回该字段，前端刷新链路实际是空转。

**处置**：移动端**不要实现 refresh 流程**；策略为「12 小时有效期 + 401 拦截 → 清 token → 跳登录页重登」。若要做无感续期，需后端补 `refreshToken`（列为 P2 后端小改造）。

### ⚠️ 偏差 6：统一响应结构是**两套**，且成功/失败码不同

| 类 | 用于 | 结构 | 成功码 | 失败码 |
|---|---|---|---|---|
| `com.itheima.pinda.common.utils.Result` | pd-web-* / pd-netty / 业务服务 | `extends HashMap`，key 为 `code`/`msg`/`data` | **0** | **500**（`HttpStatus.SC_INTERNAL_SERVER_ERROR`） |
| `com.itheima.pinda.base.R` | pd-auth-server（权限体系） | 对象：`code`/`data`/`msg`/`path`/`timestamp` | **0** | **-1 / -2 / -9 / -10** |

**处置**：拦截器统一判定 `code === 0` 为成功即可（两套一致），**不要写 `code === 200` 判定**（此前文档有"0 或 200"的说法，代码中未见 200）。失败提示统一取 `msg`。

### ⚠️ 偏差 7：`CLAUDE.md` 项目概述与代码不符

`CLAUDE.md`（Claude Code 会自动读取）声称：

> 技术栈: Spring Cloud Alibaba + **Vue3**
> 已完成的优化：4. **订单-运单-任务状态联动**

实测：
- `pd-admin-ui` 是 **Vue 2.6 + Element UI 2.12 + ECharts 4.2**（已决策不迁移 Vue3）。
- "状态联动"**只做了一半**：`TaskTransportServiceImpl` 仅在**运输任务完成（交付）**时同步运单→"到达终端网点(4)"、订单→"网点出库(23006)"（第 408–444 行）；**司机发车（depart, status→2）不写订单 23005「运输中」**，客户看不到运输中。这正是《多端数据打通》§3 标记的断点 1，**未修复**。

**处置**：建议修正 `CLAUDE.md`，避免 Claude Code 误判"已完成"而跳过 P0 状态桥改造。

### ⚠️ 偏差 8：Seata 已在代码中使用，但部署侧是"可选"

- `pd-dispatch/task/DispatchTask.java:33` 与 `pd-web-courier/CourierController.java:271` 均已标注 `@GlobalTransactional`。
- 部署文档将 Seata Server 标为"可选"，未部署时需配置 `seata.enabled=false` / `seata.service.enable-degrade=true` 降级。

**处置**：列为环境风险项 —— 若 Nacos 未下发降级配置且 Seata 未启动，**调度定时任务与快递员接单会抛异常**。上线前必须二选一：部署 Seata 或显式降级。

## 五、给 Claude Code 的补充红线（在本报告基础上追加）

- **R-A**：严禁新建登录服务；登录必须复用 `pd-auth-server` 的 `/anno/login`（或在其上增移动端口）。
- **R-B**：严禁"开发期直连 pd-web-* 端口"的调试方案；所有请求走网关 `:8760/api`。
- **R-C**：轨迹查询参数只认 `businessId`；需要按订单查时，**改后端接口**，不许前端传 `orderId` 糊弄。
- **R-D**：JWT 头固定 `token`；不得照抄管理端的 `Authorization: bearer` 写法。

- **R-G**：`pd-web-*` 经网关目前**无路由**（见 §五），新增路由前不要假定 `/web-driver/**` 之类前缀存在；也不要假定能直连（401）。
- **R-H**：`pd-netty`（8192）**可直连**（无 `TokenAuthInterceptor`），轨迹联调走 8192；其余业务服务必须走网关。

### 5.1 🔴 阻断故障 A：网关**没有** pd-web-* 的路由（三端 API 全不可达）

实测 Nacos `pd-gateway-test.yml`（命名空间 `1cb93ce4-...`，分组 `pinda-tms`）的 `zuul.routes` **只有 8 条**：

|---|---|

| `/work/**` | pd-work |
| `/dispatch/**` | pd-dispatch |
| `/base/**` | pd-base |
| `/user/**` | pd-user |
| `/aggregation/**` | pd-aggregation |

**缺失**：`pd-web-manager`、`pd-web-driver`、`pd-web-courier`、`pd-web-customer`、`pd-netty`，且配置了 `ignored-services: '*'`（禁用"按服务名默认路由"）。

**后果**：三端要调的 `business/cargo/*`、`courier/*`、`mailing/*` 经网关 → **404**；直连 8162/8163/8164 → **401**。**当前两条路都走不通**。

```yaml
      path: /web-driver/**
      serviceId: pd-web-driver
    pd-web-courier:
      path: /web-courier/**
      serviceId: pd-web-courier

      path: /web-customer/**
      serviceId: pd-web-customer

```

### 5.2 🔴 阻断故障 B：Redis 配置**未生效**，登录链路中断

- `redis.yml` / `common.yml`（Nacos 共享配置）里 `spring.redis.host = 192.168.20.130`，**配置是对的**；
- 但实测打网关 `GET /api/auth/anno/captcha` 返回 **500**：
  `Unable to connect to 127.0.0.1:6379` → 服务实际用的是 Spring Boot **默认值 localhost**。
- 原因：各服务 `bootstrap.yml` 用的是旧属性 `shared-dataids` / `refreshable-dataids`，在 Spring Cloud Alibaba **2.2.1 已失效**（应改为 `shared-configs` / `extension-configs`），共享配置没被加载。

### 6.3 🔴 根因确认：网关 500 与验证码 500 是**同一个** Redis 问题

读 `pd-authority/pd-apps/pd-gateway/.../AccessFilter.java` 确认：

```java
CacheObject resourceNeed2AuthObject = cacheChannel.get(CacheKey.RESOURCE, ...);
```

网关前置过滤器用 **j2cache** 读"需鉴权资源"缓存，j2cache 的 L2 是 Redis。Redis 不可达 → `cacheChannel.get()` 抛异常 → Zuul 返回 `500 pre:AccessFilter`。

**所以网关不是"路由不通"，而是权限缓存读不了。** Redis 修好后这两处 500 应同时消失。

### 6.4 ⚠️ 需重启才生效（Nacos 改不了的部分）


### 6.5 🆕 新发现的阻断 C：三端接口**未注册到权限资源表**（下一个必然踩到的坑）

读 `AccessFilter.run()` 逻辑：

1. 取 `permission = method + requestURI`
2. 从缓存取 `resourceNeed2Auth`（**需鉴权的资源清单**，来自 `resourceApi.list()`）
3. `if (!permission.startsWith(任一资源)) → "未知请求" UNAUTHORIZED`
4. 再取 `userId`（网关注入），查用户资源权限，命中才放行

实测数据库：

```sql
-- pd_auth.pd_auth_resource 仅 48 条，全部是后台权限系统自身的接口
/org /role /resource /station /user /menu …（含 /user/page、/user 等）
-- 无任何 driver/courier/customer 业务接口
select count(*) from pd_auth.pd_auth_resource where url like '%cargo%' or url like '%courier%' or url like '%mailing%';  -- 0
```

且 `pd_auth_resource` **无 `app_id` 字段**、库里也没有应用注册表 → **没有自动扫描注册机制，需手工维护**。

**后果**：即使 Redis 修好、路由打通，三端业务接口（如 `GET /user/profile`、`POST /mailing/...`）仍会被判"未知请求"拒绝。

**处理建议**（属数据库操作，不在本次 Nacos 范围内，需另行确认）：
1. 把三端接口批量写入 `pd_auth.pd_auth_resource`（`code/method/url/name`）；
2. 绑定菜单并授予司机/快递员/客户角色；
3. 或将三端前缀加入网关忽略鉴权（**不推荐**——跳过 token 校验会导致下游 `TokenAuthInterceptor` 401）。
