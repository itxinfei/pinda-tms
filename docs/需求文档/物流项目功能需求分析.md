# 品达物流 TMS — 功能需求分析

> 编写依据：已核实的后端能力（pd-oms / pd-dispatch / pd-work / pd-base / pd-netty / pd-web-*）与已敲定的移动端技术栈（uni-app + Vue3）。
> 核心原则：**业务优先、不做花架子**——每条需求都要回答"解决什么实际问题 / 影响哪个 KPI（时效·成本·差错率）"。

---

## 0. 优先级约定
- **P0 必做（首期）**：直接补最大缺口 / 砍最高差错率 / 业务闭环必需。
- **P1 重要**：明显提升时效或成本可视、投入产出比高。
- **P2 增强/后期**：看真实业务是否需要，不盲目做。
- **不推荐**：属花架子，对齐用户原则明确不做。

---

## 1. 现有能力盘点（已核实）

| 域 | 已有后端能力 | 主要缺口 |
|---|---|---|
| 订单 (pd-oms) | 12 级订单状态机；Drools 运费；百度地图解析；客户下单/查单/轨迹 API（pd-web-customer：Mailing / Order / OrderLocus / AddressBook，7 个 Controller） | 运费规则不透明、下单无草稿/模板、无预计时效(ETA)、异常订单无专门处理流 |
| 仓储 | **无独立模块**；"入库/出库"仅为订单状态机节点(23003/23006) | 完全无库容/在库量/出入库流水概念 → 真实仓储管理缺失 |
| 运输 (pd-dispatch+pd-work+pd-netty) | Quartz 5 阶段调度 + DFS 路径规划；运输任务状态机(depart/arrive/deliver)；DriverJob；Netty+Kafka 轨迹（`POST /netty/push`、`GET /trace/replay|latest|page`） | 调度过程黑盒不可解释；在途无时效预警；跨服务回调不可靠（Seata 仅依赖未配置、状态回调吞异常）；外部调用原无超时（已修百度 HTTP 超时+缓存） |
| 配送 (pd-web-courier) | 取派任务/运单/快递员 API（PickupDispatchTask / TransportOrder / Courier，4 个 Controller） | 无 POD 电子签收、无异常上报、无末端时效统计 |
| 基础 (pd-base) | 车队/车辆/车型/司机/线路/车次/货物类型/业务范围(多边形覆盖) | 车辆/司机实时状态未与运输任务联动展示 |
| 移动端 | 三套 REST API 已就绪（driver 4 / courier 4 / customer 7 Controller） | **无任何前端界面**（最大缺口） |

## 2. 分域功能需求

### 2.1 订单域
- **[P0] 客户极简下单**：寄件人/收件人/货物信息 + 地址簿复用 + **运费即时试算**（对接 Drools）+ 下单草稿。
- **[P0] 订单全程可视化**：状态机节点时间轴 + 当前位置轨迹 + 预计送达。
- **[P1] 运费透明化**：展示计费明细（首重/续重/距离/优惠），减少客诉与差错。
- **[P1] 异常订单处理流**：滞留/退回/破损专用状态 + 管理端处理界面。
- **[P1] 预计时效 ETA**：基于调度结果与历史给出预计送达，设时效预警。
- **[P2] 批量/月结下单模板、电子合同**（看客户结构是否需要）。

### 2.2 仓储域（谨慎，P2）
- 原则：**当前系统无仓储**。是否做取决于你是否真有"仓"的业务。若只做运输+配送，可不做；若有中转仓/分拨中心，做**轻量 WMS**。
- **[P2] 轻量入库/出库登记 + 库容/在库量 + 出入库流水 + 盘点**，并接入订单状态机节点。
- **不做**：重型 WMS（波次/上架策略/AGV 对接）属花架子，除非真有仓运营。

### 2.3 运输域（核心）
- **[P0] 运输任务闭环看板（管理端）**：调度→分配→发车→在途→到达→交付全链路可视化。
- **[P0] 在途监控**：实时位置（轮询 `GET /trace/latest`）+ 轨迹回放（`/trace/replay`）。
- **[P1] 时效预警**：偏离预计时效自动告警（司机/调度）。
- **[P1] 调度过程可解释**：把当前黑盒的 5 阶段调度结果（路线/成本/策略）可视化，便于人工干预。
- **[P1] 成本控制**：里程/空驶率/任务量统计（基于轨迹与任务）。
- **[P2] 调度策略可配置**：距离/成本/时间/中转数策略支持后台配置，而非硬编码。

### 2.4 配送域（末端 + POD）
- **[P0] 取派任务列表（快递员端）**：今日任务、按距离/时间排序、导航入口。
- **[P0] POD 电子签收**：扫码 + 手写签名 + 拍照(GPS 水印)，回传后端（**纳入第一期**）。
- **[P0] 异常上报**：破损/拒收/地址错误一键拍照上报 + 处理流。
- **[P1] 末端时效统计**：准时率、签收时长（考核依据）。

### 2.5 跨域 / 公共
- **[P0] 统一登录鉴权**：Shiro+JWT，移动端拦截器自动续期。
- **[P0] 轨迹统一服务封装**（已具备，移动端调用）。
- **[P1] 电子围栏**：超范围/偏航告警（基于 pd-common 的 `isInScope`，bug 已修）。
- **[P1] 异常订单/任务 管理端红点 + KPI 大屏**。
- **[P2] 财务结算**（运费对账、司机工资单——友商 logistics-app 有，看是否需）。
- **[P2] 多维报表**：运输量/时效/成本分析。

## 3. 三端移动功能需求（即将用 uni-app+Vue3 搭建）

### 客户端（P0 首期）
登录 / 地址簿 / 极简寄件（运费试算）/ **支付闭环（在线支付+到付+余额）** / 运单查询 / 实时轨迹 / 电子回单查看 / **预约配送** / **服务评价**。

### 快递员端（P0，含 POD）
登录 / 取派任务大厅 / 扫码签收 / **POD（签名+拍照+水印）** / **部分签收·拒签** / **COD 当面收款** / 异常上报 / 任务统计。

### 司机端（P0，App 形态）
登录 / 运输任务大厅 / **后台持续定位上报**(App `plus` 原生) / TruckLocation / 到站交付 / 导航 / 离线队列 / **驾驶行为监控（联动视频/定位）**。

> 注：POD 与附件回传可能需要后端补一个轻量 POD/附件接口（pd-web-courier 现有 TransportOrder 接口需核对，搭建时确认）。

## 4. 优先级矩阵（按 KPI 与后端改动量）

| 需求 | 影响 KPI | 优先级 | 后端是否需改动 |
|---|---|---|---|
| 三端移动前端（客户/快递员/司机） | 时效+差错(可视化/签收) | **P0** | 否（纯前端） |
| POD 电子签收 | 差错率↓ | **P0** | 可能小补 POD/附件接口 |
| 运输任务闭环看板 | 时效/成本可视 | **P0** | 否（聚合查询） |
| 在途监控/轨迹 | 时效 | **P0** | 否 |
| 异常订单/任务处理流 | 差错率↓ | P1 | 小改状态 |
| 时效预警/ETA | 时效 | P1 | 新逻辑（可前端估算） |
| 调度可视化 | 成本/时效 | P1 | 否（展示已有结果） |
| 电子围栏 | 差错/安全 | P1 | 否（isInScope 已修） |
| 财务结算 | 成本 | P2 | 需新模块 |

| 大数据/重型WMS/多租户 SaaS | — | **不推荐** | 花架子 |

## 5. 明确不做的"花架子"（对齐用户原则）
- 不盲目上 MongoDB / HBase / Spark / Hive / ES / RocketMQ / XXL-JOB（路线图里有，但当前无对应痛点）。
- 不把管理端重写为 Vue3（核算 2–4 周纯改造、零业务收益）。
- 不建重型 WMS / 多租户 SaaS / 复杂 BI，除非真实业务需要。
- 不做与后端已有能力重复的"第二套"逻辑。
- 不对接外部厂商 / 三方物流 API（EDI / ERP / 顺丰·三通一达 / 多式联运 / 国家合规）—— 本项目为自营 / 加盟运输管理，业务模式不涉及，详见 §8.7。

---

## 6. 建议落地顺序
1. **搭三端移动骨架（客户小程序首跑通全链路）** → 直接补最大缺口（无前端）。
2. **POD + 异常上报** → 砍差错率（快递员端核心价值）。
3. **管理端补"运输任务闭环看板 + 在途监控 + 异常红点大屏"** → 时效/成本可视。
4. **后端侧把"没做完的"补完**（Seata 真配置 / 调度可视化 / 状态回调补偿）。
5. **P2 按需**（财务结算 / 轻量 WMS / 时效预警）。

## 7. 借鉴成熟 TMS 项目补充的功能模块（联网调研）

> 为使功能需求"做全、不漏"，参考以下真实项目的公开功能清单，提炼出成熟 TMS 的通用能力边界，再与本项目现状做差距分析。
> 参考项目：科箭 TMS、厦门远物 TMS、Odoo TMS 套件（tms_base 等 40+ 模块）、Trenova（美车载 TMS）、open_tms、logistics-app、物牛帮（专线物流）、FRD SCM（智慧运输）。

各项目贡献的关键能力：
- **科箭 / 厦门远物**：八大核心模块 = 订单 / 调度 / 路线规划 / 在途监控 / 回单 / 费用 / 绩效 / 承运商；与 ERP 双向接口；多渠道接入（EDI/API/手工）、智能拆合单、优先级（VIP/紧急）。
- **Odoo TMS 套件**：承运商竞价与记分卡、车队维护与轮胎管理、Hub 中转与越库(cross-dock)、last-mile 代收货款(COD)与重投、逆向物流(RTO)、SLA 时钟与违约惩罚、类型化异常(shortage/damage/breakdown/delay)+索赔、合同费率卡版本化、预约月台(dock scheduling)、装载优化(轴载合规)、拖车/托盘资产监管、各国合规(e-Way Bill/CMR)。
- **Trenova**：运单生命周期 + 停靠排序(stop sequencing)、公式化计费 + 附加费(燃油/等待/detention)、开票与司机结算、文档自动化(BOL/POD)、FMCSA 合规、EDI 204/210/214。
- **open_tms**：客户/位置(仓/中转/cross-dock/terminal)/承运商与线路/订单(handling unit、危险品、温控、海关)、运单只读 Share Link、生命周期状态机、异常处理。
- **logistics-app**：营收/财务/工资/维护/安全/IFTA、调度↔司机实时聊天、客户门户、7 种角色权限。
- **物牛帮（专线物流）**：开单货件台账/零担拼货、网点中转入库出库、干线调度在途、到站自提/上门派送、费用核算 + **代收货款**、运营统计。
- **FRD SCM**：提货任务电子围栏打卡+扫码核验交接、一键发车、卸货 ePOD、AI 路径优化、智能配载(三维装箱/重泡比)、偏航/超时/温度预警多端推送。

## 8. 差距分析与补充需求（合并优先级）

将成熟 TMS 能力与本项目现状对比，**新增**以下务实功能（原文档已覆盖的不重复）：

### 8.1 订单 / 运单域
- **[P1] 运单拆分 / 合并**：按线路/时效/货物属性合并同向订单、拆分大单 —— 智能调度与配载的基础（当前 pd-oms 订单→运单近似 1:1，缺合单/拆单能力）。
- **[P1] 优先级 + 批量开单**：VIP/紧急订单优先；订单池统一归集；支持手工 / Excel 批量开单（内部，不涉及外部厂商 API）。
- **[P1] 在线运费报价（客户门户）**：客户自助试算报价（复用 Drools），减少电话询价。
- **[P2] 货物精细化属性**：Handling Unit（托盘/箱/桶）、危险品(hazmat)、温控标志 —— 影响配载与计费（按需）。

### 8.2 调度 / 运力域
- **[P1] 承运商 / 外协运力管理**：资质、合同、评级、竞价、记分卡（carrier scorecard）。真实物流大量使用外协车/三方，pd-base 当前仅有"自有车辆/司机"，这是显著缺口。
- **[P1] 智能配载**：按重量/体积/轴载自动匹配车型、三维装箱/重泡比计算、提升装载率（当前 pd-dispatch 有 DFS 路径规划，但缺配载优化）。
- **[P1] 自动 + 人工双模式调度**：支持算法建议 + 人工干预覆盖（当前调度偏黑盒）。
- **[P2] 多式联运 / 零担 LTL vs 整车 FTL**：按业务形态支持（当前偏向整车干线）。

### 8.3 在途 / 监控域
- **[P1] 异常类型化 + 预警分级**：偏航 / 超时停留 / 超速 / 温度异常（冷链）多端推送；当前仅有基础电子围栏(isInScope，已修 bug)。
- **[P1] 节点自动通知**：装货/到达/签收关键节点推短信/微信模板给客户与司机（当前缺通知能力）。
- **[P2] 冷链温控（如需）**：温度遥测 + 超标告警 + 合规报告（按需）。

### 8.4 回单 / 计费 / 结算域（原文档偏弱，重点补）
- **[P1] 回单管理闭环**：ePOD 采集（签名+拍照+GPS水印，**第一期已纳入**） + **回单影像归档 + 回单核销 + 关联运费结算**（当前仅采集，无归档/核销/计费联动）。
- **[P1] 计费多样化 + 附加费**：按吨/按车/按里程/零担/整车；燃油附加费、等待费、返空费、detention 自动识别（当前 Drools 运费需扩展附加费规则）。
- **[P1] 多维对账**：按承运商 / 客户 / 时间快速对账；应收应付分离。
- **[P1] 司机结算 / 工资**：按里程/百分比/固定计算司机报酬（友商 logistics-app / Trenova 均有，是运输公司刚需）。
- **[P1] 合同费率卡版本化**：客户/承运商合同 + 生效日期 + 续约（计费依据）。
- **[P2] COD 代收货款**：专线/电商场景的代收与回款管控（物牛帮核心）。

### 8.5 客户 / 协同域
- **[P1] 客户自助门户增强**：运单只读 Share Link（发给收货人无需登录）、下载 POD、在线请求提货。
- **[P1] 调度 ↔ 司机 协同**：消息/指令送达回执（logistics-app 有，减少电话）。
- **[P2] 逆向物流（退货/RTO）**：退件、RTO 处理流（电商场景）。

### 8.6 绩效 / 合规域
- **[P1] 绩效考核**：司机 KPI（准点率/货损率）、承运商考核、服务质量评分、排名与奖惩。
- **[P2] 车队与司机证照/资质**：车辆年检、司机证照到期提醒、预防性维护（trucking 刚需，看是否自有车队）。
- **[P2] SLA 时效时钟 + 违约惩罚 + 审批流**：多级审批（费率/折扣/费用/异常）。

### 8.7 范围澄清：本项目不涉及对接外部厂商 / 三方物流 API

> **重要澄清（用户确认，2026-10-05）**：本项目的业务模式为**自营 / 加盟运输管理**，系统中**不存在、也不需要对接外部厂商 / 三方物流的 API**（如顺丰 / 三通一达 / EDI X12 / ERP SAP·金蝶·用友 / 多式联运 / 国家合规 e-Way Bill·CMR 等）。
> 上述项来自友商功能参考（§7），**对本项目不适用，已从需求范围中移除**，不列入本期、也不列入路线图。后续若业务形态变化（如对外承接三方订单），再单独评估。
> 保留"按需"项：需求预测与 BI、预约月台（仅当真实业务需要时启动）。

### 8.8 北斗定位（BDS）支持 ｜ P1

背景：当前 `pd-netty` 接收的 `LocationRecord` 仅存 `lng/lat`（字符串），**无坐标系标识字段**，内部隐含百度 BD-09（源于 `pd-oms` 的 BaiduMapUtils）。要支持北斗，需补齐：

- **[P0·最小改造] 坐标系统一与转换（合规 R2-1 闸口前置，2026-10-06 审查定案）**：`LocationRecord` 增加 `coordSystem`（枚举：WGS-84 / GCJ-02 / BD-09 / CGCS2000）与 `source`（北斗车载终端 / 手机 GPS / 网络）字段；提供统一坐标转换工具（WGS-84 ↔ GCJ-02 ↔ BD-09 ↔ CGCS2000），所有对外展示（地图标点、轨迹）统一转到展示目标系。**随合规阶段 0 落地**，支撑 R2-2（车辆监控在线状态标记）与 R2-3（轨迹真实性校验），不阻塞上线闸口；完整北斗接入见下（P1）。
- **[P1] 北斗车载终端接入（规划，依赖 P0 最小改造）**：支持北斗 + GPS 双模车载终端通过 **JT/T 808**（道路运输车辆卫星定位系统车载终端通讯协议）上报位置；新增轻量接入服务（复用现有 Netty，不引新中间件），解析 808 报文写入 `LocationRecord`。
- **[P1] 移动端定位优先北斗 / GPS 双模**：uni-app `uni.getLocation` 在支持北斗的终端自动使用北斗；**禁用纯网络定位**（`type` 不取仅网络定位），保证定位源真实为卫星定位。
- 影响 KPI：定位精度↑（差错率↓）、在途可视（时效↑）。

### 8.9 司机视频接入 ｜ P1（随时查询司机情况）

背景：用户明确需求——**将视频对接进系统，运营 / 调度中心可随时查看司机实时情况**。当前系统无任何视频能力。

- **[P1] 司机端实时视频采集**：司机 App 调用摄像头向平台推流（司机主动开启 / 调度中心发起请求后开启）；可查看司机面部 / 车厢画面。
- **[P1] 平台侧实时查看**：管理端 / 调度端按 `businessId`（车辆 / 司机）拉起实时视频流，随时查询司机当前状况。
- **[P1] 按需录制与回看**：关键事件（异常 / 签收）触发录制，事后可回看。
- **技术约束（红线）**：
  - 不自建 RTMP 流媒体集群（重中间件，违反"不引新中间件"原则）。
  - 优先采用**云厂商实时音视频 SDK**（如腾讯云 TRTC / 声网 / 阿里 RTC）做司机端 ↔ 平台 1v1 视频；若司机配备专业车载监控设备，则按 **GB/T 28181 / JT/T 1078** 国标接入。
  - 选型需"轻量、按需、可替换"，不绑定重架构。
- 影响 KPI：司机监管可视（差错率↓）、异常取证（差错率↓）、客户信任（服务↑）。

> **原则重申**：北斗与视频均为**真实业务需求，纳入本期 P1**；而"对接外部厂商 API（EDI/ERP/快递API/多式联运）"不适用已移除。本期仍聚焦 P0+P1 主线，避免花架子。

## 10. 第二轮联网补充需求（2026-10-05 第二轮调研）

> 依据：对 TMS 全链路（订单→调度→在途→签收→回单→结算→绩效）及三端（客户/快递员/司机）公开功能清单的二次调研。聚焦**首轮遗漏、但对业务闭环真正有用**的能力。仍遵循"实用优先、不花架子"。每条都标注优先级与影响 KPI。

### 10.1 客户闭环补全（首轮缺支付 / 预约 / 评价）
- **[P0/P1] 支付闭环**：寄件支持**在线支付（微信支付 SDK，属常规业务 SDK、非重中间件）+ 到付 + 余额**三选一。首期可先用"到付 + 线下"兜底，**在线支付列为 P1 必做**（不完成则客户下单=空单，转化与坏账都受影响）。影响 KPI：下单转化率↑、坏账↓。
- **[P1] 预约配送**：用户可预约未来时段（如 2 小时内 / 指定日期）下单，系统排期后进入调度。影响：体验↑、调度可预规划。
- **[P1] 服务评价**：订单完成后客户对时效/服务评分 + 文字评价，沉淀为快递员/司机服务质量分（喂给绩效模块）。影响：服务质量↑。
- **[P2] 保价/保险**：高价值货物保价，按申报价值计费，降低纠纷与赔偿风险。影响：信任↑（按需）。

### 10.2 签收 / 回单闭环深化（POD 不止"采集"）
- **[P0] 部分签收 / 拒签流程**：记录实际签收数量、拒签原因、剩余货物处理方案（退回/转运/销毁），状态联动订单与库存。影响：差错/纠纷↓。
- **[P1] 回单状态机**：已签收未回传 / 已回传未确认 / 已确认三态 + 催收提醒（承运商凭回单结算）。影响：结算准确率↑。
- **[P1] COD 当面收款**：快递员/司机端收代收款 → 计入骑手现金余额 → 后台对账核销（证据四件套：照片+时间+定位+原因码）。影响：资金安全↑。

### 10.3 异常全生命周期（首轮只有"上报"，缺闭环）
- **[P1] 投递失败→重投→退回 标准路径**：`Delivery Unsuccessful → Re-attempt → Shipper Advice → Return In Process → Returned to Shipper`，每步状态对客可查。影响：差错↓、客诉↓。
- **[P1] 异常自动识别 + 分级**：超时（>预计 30min）/ 偏航 / 停留超时 / 签收争议自动标记 + 多端推送（短信/微信/APP）。影响：时效↑。
- **[P1] 投诉管理闭环**：客户投诉 → 指派 → 处理 → 满意度回访，全程留痕。影响：服务↑。
- **[P2] 理赔自动化（定责+赔付）**：破损/丢失定责规则库 → 自动生成赔付方案 + 凭证 PDF；先人工审批后固化，逐步半自动。影响：纠纷处理时效↑（流程重，先半自动）。

### 10.4 财务结算深化（首轮偏弱）
- **[P1] 账期 / 回款 / 坏账预警**：客户账期、到期应收、逾期提醒、欠款台账自动生成。影响：资金周转↑、坏账↓。
- **[P1] 价格体系固化防暗箱**：运价写入系统不可私改，开单员/业务员无改价权限，从根源减少利润流失。影响：利润↑。
- **[P1] 多维对账增强**：应收应付分离、异常费用标记、批量核销、在线对账（货主/司机/承运商手机端可看待结与运单明细）。影响：对账效率↑（友商实测可降 80%+）。
- **[P2] 利润驾驶舱 / 资金账**：按线路/客户/车辆毛利、预付款/油卡余额/往来结算统一呈现（老板视角）。影响：经营可视。

### 10.5 人 / 车 / 调度深化
- **[P1] 证照 / 预防维护预警**：车辆年检/保险/驾照/从业资格证到期提醒；保养计划 + 维修记录。影响：合规/安全风险↓。
- **[P1] 抢单 / 派单双模式**：系统自动派单（按距离/评分/负载）或司机抢单，运力均衡。影响：调度效率↑。
- **[P0] 可视化调度看板（细化）**：全部在途车辆/任务状态一张图、智能推荐车辆司机、一键派单、异常预警推送。影响：时效/成本可视。
- **[P2] 排班 / 考勤**：司机排班、工时、双人轮班、疲劳驾驶管控（联动视频/定位）。影响：安全/合规。
- **[P1] 驾驶行为监控**：超速/急刹/疲劳/分心（联动车载摄像头/视频）实时提醒 + 纳入绩效。影响：安全/货损↓。

### 10.7 跨端硬约束：多端数据打通（用户强要求，优先于单端功能）

用户原话："几个用户端数据必须是通的"。客户下单 → 快递员取派 → 司机运输，**三端共享同一份主记录**，不是各端各建一套。详细契约见独立文档 **[《多端数据打通与统一领域模型》](多端数据打通与统一领域模型.md)**，关键红线：

- **单一数据源**：`Order`(pd_order) / `TransportOrder` / `TaskTransport` / `DriverJob` / `LocationRecord` 为主记录；链路主键已通（`Order.id → TransportOrder.orderId → TransportOrderTask → TaskTransport.id → DriverJob.taskTransportId → LocationRecord.transportTaskId`）。任何端不得私存状态副本。
- **统一状态机（双向同步）**：`Order.status`(12 级: 23000~23011) 与 `TaskTransport.status`(5 级: 1~5) 必须靠集中状态机互相推导——司机 depart 同步 `Order`→23005 运输中、deliver 同步→23006 网点出库、快递员 delivered 同步→23009 已签收。现状仅在交付时散落 Feign 回写，且"运输中"未同步，**属反模式，需收口**（见该文档 §3）。
- **客户轨迹只凭订单号查**：`/trace/latest|replay` 现状仅接受 `businessId`（车辆/快递员 id），客户无 truckId 无法查自己包裹轨迹；需支持按 `transportTaskId`（表已有字段）查询并新增"凭 `Order.id` 解析"的客户端入口（见该文档 §4）。
- **不引新中间件**：实时同步只用 Kafka/RabbitMQ/Netty/轮询/Spring WebSocket，不引 MQTT 等栈外组件。

> 优先级标注：**多端数据打通 = P0 架构前置**，三端任务卡任何页面都不得违反其 §6 六条红线，否则单端功能跑通也视为 bug。

## 11. 合规与监管要求（2026-10-06 新增，源自最新法规）

> 依据：2024–2026 年交通运输部 / 税务总局 / 国家邮政局 / 网信办 / 人社部公开规章与政策解读。完整法规清单、边界声明、逐项映射见独立文档 **[《物流行业合规与监管要求》](物流行业合规与监管要求.md)**。本项目为**自营/加盟运输管理**，非网络货运撮合平台；凡仅适用于平台撮合/税务套利的条款已在该文档 §2 明确标注"不适用边界"，不列入本需求。

### 11.1 上线前必须满足（P0，否则面临处罚风险）
- **[P0] 快递投递确认（R1）**：未经用户同意不得擅自投柜/驿站，最高罚 3 万。派件前确定投递方式（上门默认、改投需二次确认），客户地址簿加"投递偏好"，投递结果回写备查。→ 快递员端派件页 + 客户小程序。
- **[P0] 北斗车辆在线 + 离线禁排班（R2）**：12 吨以上货车强制北斗实时在线，故障车辆**不得排班/派单**；轨迹真实性校验（防伪造/跳变告警）。→ 复用 BDS 需求 + 调度排班校验。
- **[P0] 数据安全分类分级 + 单独同意（R6/R7/R8）**：货运定位集、司机信息、客户信息属重要/敏感数据；位置/行程等敏感信息**移动端单独授权**、最小必要采集；操作审计日志留存 ≥6 个月；境内存储 + 高等级加密 + 接口防越权遍历。
- **[P0] 轨迹/运单真实可核验（R5 通用）**：杜绝"空转走单/虚假轨迹"，业务数据真实（呼应税务"五流合一"精神）。

### 11.2 应建（P1）
- **[P1] 车辆技术等级/新能源字段（R3）**：车辆档案加能源类型、技术等级（二级以上）、检车周期（5 年以上半年检）、电池检测；扩展新能源预警。
- **[P1] 车证/人证一致校验（R5）**：派车派司机校验营运证、从业资格证/驾照有效，否则禁派。
- **[P1] 数据留存策略（R5）**：运单/轨迹/结算数据留存 ≥3 年（涉税 10 年）。
- **[P1] 前端脱敏展示（R6）**：面单/轨迹/司机信息脱敏（手机号掩码等）。
- **[P1] 运价透明 + 运费保障（R10）**：运费规则可查、结算/垫付保障（呼应 §10.4 价格固化）。
- **[P1] 电子运单强制填报（R4，条件）**：仅当开展危货业务时升级 P0；每趟次真实填报、随车备查。

### 11.3 远景（P2）
- **[P2] 绿色物流（R9）**：车辆能源类型字段 + 能耗/碳排放统计（并入 OPS-4）。
- **[P2] 司机参保/健康记录（R10）**：司机档案加参保状态，便于关怀与合规备查。

> 说明：P0 合规项应进入第一批开发；R2/R4/R5 通用项与既有 BDS、视频、运单、调度任务卡融合（在对应任务卡加"合规约束"子节即可），不另起炉灶。边界条款（网络货运撮合/税务、危货）写入"不做清单"，仅业务拓展时启用。
