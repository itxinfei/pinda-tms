# 品达 TMS 移动端（uni-app）技术栈与业务逻辑敲定方案

> 目的：在写任何代码之前，把**技术选型**与**三端业务范围**逐项敲定并留档。
> 前提约束：后端 JDK 1.8 / Spring Boot 2.2.5 栈**不动**；移动端为纯前端新增工程，只调现有 REST API。
> 文中所有后端接口均已核实到源码（Controller + 路径），非猜测。

> ## ⚠️ 版本修订（2026-10-05 拍板，本节为最终依据，覆盖下表旧选型）
>
> 下表为**初稿选型**（Vue2 路线），**已被推翻**。最终敲定（见三张任务卡与 MEMORY）：
>
> | 项 | 最终结论 | 旧稿（作废） |
> |---|---|---|
> | 框架 | **uni-app + Vue3 + Vite** | uni-app（Vue2 语法） |
> | UI 库 | **uview-plus**（Vue3 版 uView） | uView UI 1.8.x |
> | 状态管理 | **Pinia** | Vuex 3 |
> | 网络层 | `uni.request` 封装，JWT 头字段 = **`token`** | `Authorization: Bearer <token>` ❌（网关不认） |
> | 请求入口 | **开发+生产均走网关** `http://<host>:8760/api` | 开发直连 8161~8164 ❌（会被 401） |
> | 登录 | 复用 **`POST /anno/login`**（pd-auth-server 已存在） | 需新建登录 ❌ |
>

## 一、总体结论

- **一个 uni-app 工程，三端（司机/快递员/客户）分包**，编译到 微信小程序 + H5 + iOS/Android App。
- **实时轨迹对接方式已定死**：pd-netty 走 **HTTP REST**（`POST /netty/push` 上报、`/trace/*` 查询），**不是 WebSocket**——uni-app 侧不需要 `connectSocket`，按 HTTP 轮询/定时上报即可，实现更简单。
- 两个必须提前定的技术点：**地图坐标系**（后端是百度 BD-09，小程序内置腾讯 GCJ-02）与**司机端后台定位**（小程序受限，以 App 为主）。

## 二、技术栈敲定（逐项：建议 + 理由 + 备选）

| # | 项 | 建议 | 理由 | 备选 |
|---|-----|------|------|------|
| 1 | 跨端框架 | ~~uni-app（Vue2 语法）~~ → **uni-app + Vue3 + Vite**（2026-10-05 拍板，见文首修订） | Vue2 已于 2023-12 EOL；新工程避开停更底座 | — |
| 2 | UI 组件库 | **uView UI 1.8.x** | Vue2 生态最全的移动端库（表单/日历/签名板/骨架屏都有），适合中大型物流 App | uni-ui（官方，组件少）；ColorUI（纯样式） |
| 3 | 状态管理 | **Vuex 3** | Vue2 配套；存 token/角色/用户信息 | Pinia（需 Vue3） |
| 4 | 网络层 | **uni.request 统一封装** | JWT 拦截器：请求头字段 **`token: <token>`**（网关 `authentication.user.header-name: token`，**不是 Authorization**）；401 清 token 跳登录；统一错误提示；BASE_URL = `http://<host>:8760/api` | — |
| 5 | 请求入口 | ~~开发直连~~ → **开发+生产统一走 Zuul 网关 `http://<host>:8760/api`** | 实测 `TokenAuthInterceptor` 在 4 个 pd-web 模块全注册，缺 `userid` 头即 401，**直连不可用**；端口 8161~8164 仅供健康检查 | 见决策点③（已实测推翻） |
| 6 | 登录鉴权 | **复用 pd-auth-server `POST /anno/login` + `/anno/captcha`**（已存在），JWT 由 `AuthManager` 签发，有效期 7200s（2h，实测 Nacos pd-auth-server-test.yml）；token 存 `uni.setStorageSync`（或 Pinia 持久化） | 后端**不需新建登录服务**；微信小程序如需免密，另增 `code2Session` 入口（P0-0） | — |
| 7 | 地图 | **App 端：百度地图 SDK（与后端一致）；小程序端：内置 map + 坐标转换** | 后端 pd-oms 存的是百度 BD-09 坐标；App 端用百度可零转换；微信小程序 map 固定腾讯(GCJ-02)，必须做 BD-09→GCJ-02 转换（有公开公式） | 见决策点② |
| 8 | 定位 | `uni.getLocation`（wgs84/gcj02 按端适配） | 客户/快递员前台定位够用 | — |
| 9 | **司机持续定位** | **App 端：plus 原生后台定位（Android 后台服务）** | 小程序后台 GPS 受限，无法满足运输途中持续上报 | 小程序仅做轻量场景 |
| 10 | 轨迹上报 | `POST /netty/push`（LocationEntity：businessId/type/lng/lat/currentTime…） | 已核实 pd-netty 的 `NettyController`，入队 Kafka 落库 | — |
| 11 | 轨迹查询 | `GET /trace/replay`（回放）、`GET /trace/latest`（最新位置）、`POST /trace/page`（分页） | 已核实 `GpsTraceController`，按 businessId+type(truck/courier) 查询 | — |
| 12 | 上报节奏 | 司机 App：**10s 一次**（可配）；快递员：操作触发时上报 | 平衡流量与轨迹精度（后端 Kafka 无压力） | 30s（更省电） |
| 13 | 扫码 | `uni.scanCode`（运单条码/取派码） | 全端支持 | App 端可换原生扫码插件（连续扫） |
| 14 | 电子签收 POD | canvas 手写签名 + `uni.chooseImage` 拍照 + GPS/时间水印 | 对齐友商标杆做法；附件走现有 AttachmentController | 见决策点④（是否第一期） |
| 15 | 离线容灾 | `uni.setStorageSync` 本地队列：失败上报先入队，网络恢复重传 | 司机在地库/郊区丢信号不丢数据 | App 端 SQLite（数据量大时） |
| 16 | 发布形态 | **客户=微信小程序+H5；快递员=小程序(+App)；司机=Android App（iOS 后续）** | 按各端使用场景定（见下） | — |

## 三、三端业务功能范围敲定

### 3.1 客户端（C 端，微信小程序 + H5）
| 页面 | 核心交互 | 后端对接（已核实） |
|------|---------|------------------|
| 登录 | 手机号+验证码/密码 | `pd-web-customer` UserController/UserCenterController |
| 首页 | 寄件入口、我的订单、轨迹速查 | — |
| 寄件下单 | 地址簿选择/手输、货物类型/重量、**运费试算**（输入即算） | MailingController + OrderController |
| 运单列表/详情 | 状态流转（对齐 12 级订单状态） | OrderController |
| **轨迹地图** | 地图 polyline + 起终点标记 + 定时刷新 | `GET /trace/replay`（type 按快递员/车辆） |
| 地址簿 | 增删改查、默认地址 | AddressBookController |
| 个人中心 | 资料、退出 | UserCenterController |

**不做（本期）**：在线支付（后端为模拟）、催单/投诉工单、会员积分。

### 3.2 快递员端（小程序 + App）
| 页面 | 核心交互 | 后端对接 |
|------|---------|---------|
| 登录 | 工号+密码 | `pd-web-courier` UserCenterController |
| 任务列表 | 待取件/待派件/已完成 三 tab，突出**时间窗+地址距离** | PickupDispatchTaskController |
| 取件操作 | 扫码核运单 → 拍照 → 确认取件 | PickupDispatchTaskController |
| **派件签收 POD** | 扫码 → 手写签名 → 拍照（水印）→ 妥投/异常 | TransportOrderController + AttachmentController |
| 异常上报 | 拒收/地址不明/破损，**带时间水印拍照**，醒目入口 | PickupDispatchTaskController |
| 位置上报 | 前台操作时顺带上报（轻量） | `POST /netty/push`（type=courier） |
| 我的 | 今日完成量/准时率统计 | — |

### 3.3 司机端（Android App 为主）
| 页面 | 核心交互 | 后端对接 |
|------|---------|---------|
| 登录 | 工号+密码 | `pd-web-driver` UserCenterController |
| 运输任务列表 | 待发车/在途/已完成，突出车牌+线路+时间窗 | TransportTaskController |
| 任务详情 | 车次/路线地图 + 携带运单列表 | TransportTaskController |
| **发车/到达/交付** | 三按钮对应状态机 depart/arrive/deliver，防误触二次确认 | TransportTaskController（CAS 状态守卫已核实） |
| 作业单 | 司机作业任务明细 | DriverJobController |
| **持续位置上报** | App 后台 GPS → 10s 定时 `POST /netty/push`（type=truck，businessId=车辆ID）+ 离线队列 | `POST /netty/push` |
| 导航 | 一键跳百度/高德导航 App | 端能力 |
| 轨迹自查 | 查看本车今日轨迹 | `GET /trace/replay` |

**不做（本期）**：司机抢单（当前为调度分配制）、油耗/车检（后期）。

## 五、两个必须提前定的技术点

1. **坐标系**：后端百度 BD-09 ↔ 小程序腾讯 GCJ-02。
   - 方案 A（推荐）：App 端集成百度地图 SDK（零转换）；小程序端写一个 `bd09ToGcj02()` 转换工具（约 30 行公开公式）。
   - 方案 B：后端改存 GCJ-02（**违反"后端不动"约束，不推荐**）。
2. **司机后台定位**：微信小程序切后台 30s 后停止定位 → 司机端**必须以 App 形态交付**（Android 原生后台服务），小程序只做应急查询。
