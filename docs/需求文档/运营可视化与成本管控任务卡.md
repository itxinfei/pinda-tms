## 0. 硬约束（不可违反）

- JDK 1.8 锁死、**不升级任何依赖**、安全 CVE 不处理。
- **不引新中间件**：不使用 MongoDB/Redis Stream/MQTT/XXL-JOB/ES。
- 周期任务用 **Spring `@Scheduled`**（Spring Boot 原生，非新中间件）；**不要**为告警新建 Quartz 表驱动任务（现有 Quartz 走反射调 `run(...)`，过重）。
- **新建 MySQL 表允许**（不是中间件）；能靠关联查询算出的**一律不建表、不改表**。
- 管理端维持 **Vue2 + Element UI**，不迁移 Vue3。
- 接口风格与现有保持一致：类上 `@RequestMapping("xxx")`（无前导斜杠），方法 `@PostMapping("/page")` 等。

## 1. 现状核对小结（已核实，决定实现方式）

| 能力 | 现状 | 结论 |
|---|---|---|
| 时效告警 | ❌ 无。但 `TaskTransport` 已有 `plan/actualDepartureTime`、`plan/actualArrivalTime`、`plan/actualPickUpGoodsTime`、`plan/actualDeliveryTime` | **可纯基于现有字段计算**，只需新建告警表落库 |
| GPS 告警 | ⚠️ `pd-netty` 已有 `GpsAlertService`（超速 `SPEED_OVER`、长时间停留 `STAY_TOO_LONG`），通道=日志 + `gps.alert.webhook-url` 推 Webhook | **已有但只发不存、无闭环** → 收口到统一告警中心表 |
| ETA | ⚠️ `Order.estimatedArrivalTime` 字段**已存在**但无写入逻辑 | 先落"计划到达时间即 ETA"，再做历史偏差修正 |
| 车辆看板 | ⚠️ `PdTruck` 有 `truckTypeId/fleetId/licensePlate/allowableLoad/allowableVolume/status(0禁用/1正常)`，**无"运营状态"字段** | **零表改动**：状态由 `TaskTransport.truckId+status` 关联推出；装载率用 `allowableLoad/allowableVolume` 算 |
| 司机看板 | ⚠️ `PdTruckDriver` 有 `userId/fleetId/age/drivingAge`，**无状态字段** | **零表改动**：由 `DriverJob.driverId+status` 关联推出 |
| 趟次成本 | ❌ 完全空白 | **必须建表** |
| 油耗 | ❌ 完全空白（`PdTruck` 也无里程字段） | **必须建表**（里程由人工录里程表读数） |

**关键判断**：5 项里 **OPS-3（看板）几乎零表改动**，OPS-1/OPS-2 靠现有字段，只有 **OPS-4 必须建表**。所以先看板后成本，成本最高、看板最省。

## 2. OPS-0 公共基础设施：统一告警中心（OPS-1/OPS-5 依赖）

### 2.1 为什么先做这个
现在 `GpsAlertService` 只打日志 + 推 Webhook，**告警不落库 → 无法查看、无法处理、无法闭环**（G7 的告警是"推送给司机/稽查员/管理者 + 处置结果反向沉淀为管理规则"）。所以先建告警中心表。

### 2.2 新建表 `pd_transport_alert`（放 **pd-work** 库）

```sql
CREATE TABLE pd_transport_alert (
  id              VARCHAR(64)  NOT NULL COMMENT '主键',
  biz_type        VARCHAR(32)  NOT NULL COMMENT '业务类型: TRANSPORT_TASK-运输任务 ORDER-订单 DRIVER-司机 TRUCK-车辆',
  biz_id          VARCHAR(64)  NOT NULL COMMENT '业务id(任务id/订单id/司机id/车辆id)',
  alert_type      VARCHAR(32)  NOT NULL COMMENT '告警类型(见枚举)',
  level           INT          NOT NULL DEFAULT 2 COMMENT '级别 1提示 2预警 3严重',
  message         VARCHAR(512) NOT NULL COMMENT '告警内容',
  delay_minutes   INT          NULL     COMMENT '延误分钟数(时效类告警)',
  status          INT          NOT NULL DEFAULT 0 COMMENT '处理状态 0未处理 1已处理 2已忽略',
  handler         VARCHAR(64)  NULL     COMMENT '处理人',
  handle_time     DATETIME     NULL     COMMENT '处理时间',
  handle_remark   VARCHAR(512) NULL     COMMENT '处理备注',
  create_time     DATETIME     NOT NULL COMMENT '创建时间',
  PRIMARY KEY (id),
  KEY idx_biz (biz_type, biz_id),
  KEY idx_status_level (status, level),
  KEY idx_create_time (create_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='运输告警记录(统一告警中心)';
```

**告警类型枚举 `alertType`**

| 枚举 | 含义 | 来源 | 级别建议 |
|---|---|---|---|
| `DEPART_DELAY` | 发车延误（超 `planDepartureTime` 未发车） | OPS-1 时效 | 2 |
| `ARRIVE_DELAY` | 到达延误（超 `planArrivalTime` 未到达） | OPS-1 时效 | 2~3 |
| `DELIVERY_DELAY` | 交付延误 | OPS-1 时效 | 3 |
| `PICKUP_DELAY` | 提货延误 | OPS-1 时效 | 2 |
| `ETA_DEVIATION` | ETA 偏差超阈值 | OPS-2 | 2 |
| `NO_GPS` | 长时间无定位上报 | OPS-1/OPS-5 | 2 |
| `STAY_TOO_LONG` | 长时间停留 | 已有 GpsAlertService | 2 |
| `SPEED_OVER` | 超速 | 已有 GpsAlertService | 3 |
| `DRIVE_FATIGUE` | 疲劳驾驶（连续行驶超阈值） | OPS-5 | 3 |

### 2.3 接口（pd-work，类上 `@RequestMapping("alert")`）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/alert/page` | 告警分页（按 bizType/bizId/alertType/level/status 筛选） |
| GET | `/alert/{id}` | 告警详情 |
| POST | `/alert/handle` | 处理/忽略告警（入参 id、status、handler、handleRemark） |
| POST | `/alert/report` | **上报告警**（供 pd-netty 的 GpsAlertService 通过 Feign 调用落库） |
| GET | `/alert/count` | 未处理告警数（管理端红点） |

### 2.4 实现要点
- `GpsAlertService.alert(...)` 增加"落库"分支：优先调 pd-work 的 `/alert/report`（Feign）；**Feign 不可用则降级保留原日志+Webhook**，不得阻断主流程（沿用现有 try-catch 兜底风格）。
- 告警**幂等**：同一 `bizId + alertType` 在未处理状态下不重复插入（查 `status=0` 存在则跳过或更新）。

### 2.5 DoD
- [ ] 表已建、枚举已定义；`/alert/report` 可被 pd-netty 调通并有降级。
- [ ] 超速/停留告警能落库并可在管理端查看、处理。
- [ ] 未处理告警数接口返回正确（红点）。

## 3. OPS-1 时效预警与异常告警

### 3.1 目标（对标）
G7："在途数据实时在线、异常自动告警"；顺丰："及时预警、路由动态调整"。
**解决**：现在调度过程黑盒、超时无人知 → 延误只能靠客户投诉发现。

### 3.2 数据来源（全部已有，无需改表）
`TaskTransport`：`planDepartureTime/actualDepartureTime`、`planArrivalTime/actualArrivalTime`、`planPickUpGoodsTime/actualPickUpGoodsTime`、`planDeliveryTime/actualDeliveryTime`、`status`。

### 3.3 规则（可配置，写进 yml，不硬编码）

```yaml
pinda:
  alert:
    depart-delay-minutes: 30     # 超计划发车时间 N 分钟仍未发车
    arrive-delay-minutes: 30     # 超计划到达时间 N 分钟仍未到达
    pickup-delay-minutes: 30
    delivery-delay-minutes: 60
    no-gps-minutes: 30           # 在途任务 N 分钟无定位上报
```

**判定逻辑**（`@Scheduled` 每 5 分钟扫一次 `status IN (1,2,3)` 的 `TaskTransport`）：
- `status=1 待执行` 且 `now > planDepartureTime + N` 且 `actualDepartureTime is null` → `DEPART_DELAY`
- `status=2 进行中` 且 `now > planArrivalTime + N` 且 `actualArrivalTime is null` → `ARRIVE_DELAY`
- `status=2` 且该任务关联的 `LocationRecord` 最新上报时间距今 > `no-gps-minutes` → `NO_GPS`
- 交付节点同理 → `DELIVERY_DELAY`

### 3.4 接口
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/transport-task/alert/scan` | 手动触发一次扫描（便于验收，定时任务外暴露） |
| GET | `/transport-task/{id}/timeline` | 任务时间轴（计划 vs 实际各节点 + 是否延误） |

### 3.5 前端
- 管理端（Vue2）：**告警中心页**（列表+筛选+处理）+ 运输任务详情加**时间轴**（计划/实际对比，延误红色）。
- 移动端：司机端任务卡显示"剩余时间/已延误"提示。

### 3.6 DoD / 红线
- [ ] 阈值进 yml，**禁止硬编码**。
- [ ] 扫描任务幂等、不重复造告警。
- [ ] 延误任务能在管理端被筛选出来并处理。
- [ ] 不引新中间件（用 `@Scheduled`）。

## 5. OPS-3 车辆 / 司机看板（利用率·状态·装载率）

### 5.1 目标（对标 G7 车辆 Dashboard）
G7："车辆利用率、调度、效率可见"；"一个平台管理多地业务"。
**解决**：现在 pd-base 只有静态档案，**车辆/司机实时状态未与运输任务联动展示**。

### 5.2 关键：**零表改动**，全部关联查询
| 指标 | 算法（不建表） |
|---|---|
| 车辆当前状态 | 查 `TaskTransport` where `truckId=?` 取最新任务：`status=2`→在途，`status=1`→待执行，`status=4`→已完成；无任务→空闲 |
| 车辆利用率 | 统计周期内：有任务时长 ÷ 总时长（用 `actualDepartureTime~actualArrivalTime` 或计划时间） |
| 装载率 | 任务关联货物总重/总体积 ÷ `PdTruck.allowableLoad / allowableVolume`（经 `OrderCargo.totalWeight/totalVolume`） |
| 司机当前状态 | 查 `DriverJob` where `driverId=?` 最新记录 `status`（1待执行/2进行中/4已完成） |
| 司机在途任务 | `DriverJob.driverId + taskTransportId` → `TaskTransport` |

### 5.3 接口（pd-work / pd-base，类上 `@RequestMapping("dashboard")`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/dashboard/truck/board` | 车辆看板：车牌、车型、车队、当前状态、当前任务、装载率 |
| GET | `/dashboard/driver/board` | 司机看板：姓名、车队、驾龄、当前状态、当前任务 |
| GET | `/dashboard/fleet/summary` | 车队汇总：车辆总数/在途/空闲、司机总数/在途、今日趟次 |
| GET | `/dashboard/truck/{id}/utilization` | 单车利用率（按时间范围统计） |

### 5.4 前端
- 管理端：**车辆看板页**（卡片/表格 + 状态色：在途绿/空闲灰/待执行蓝）、**司机看板页**、车队汇总卡片。
- 状态色**必须用 UI 规范的 Token**，禁止硬编码。

### 5.5 DoD / 红线
- [ ] **禁止为"运营状态"给 `PdTruck`/`PdTruckDriver` 加字段**（状态由关联查询推出，保持单一数据源）。
- [ ] 车辆/司机状态与 `TaskTransport`/`DriverJob` 实时一致。
- [ ] 装载率能算出来并展示。

## 6. OPS-4 趟次成本与油耗（唯一必须建表的项）

### 6.1 目标（对标 G7 财运通核心）
G7："在途成本精细到每趟""每发生一笔业务，利润当时就能看到""水印相机实时报销""油耗管理在线审批"。
**解决**：品达**成本侧完全空白** → 不算账就不知道哪条线路/哪趟赚钱。

### 6.2 新建表

```sql
-- 趟次成本（各类成本统一在此，按趟归集）
CREATE TABLE pd_task_cost (
  id                VARCHAR(64) NOT NULL COMMENT '主键',
  task_transport_id VARCHAR(64) NOT NULL COMMENT '运输任务id(趟次)',
  truck_id          VARCHAR(64) NULL COMMENT '车辆id',
  driver_id         VARCHAR(64) NULL COMMENT '司机id',
  cost_type         VARCHAR(32) NOT NULL COMMENT 'FUEL油费 TOLL路桥费 REPAIR维修 FINE罚款 LABOR司机工资 OTHER其他',
  amount            DECIMAL(12,2) NOT NULL COMMENT '金额',
  occur_time        DATETIME    NOT NULL COMMENT '发生时间',
  voucher           VARCHAR(255) NULL COMMENT '凭证图片(水印相机/拍照上传)',
  operator          VARCHAR(64) NULL COMMENT '录入人',
  remark            VARCHAR(255) NULL,
  create_time       DATETIME    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_task (task_transport_id),
  KEY idx_truck_time (truck_id, occur_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='趟次成本';

-- 加油/油耗记录（用于百公里油耗，需里程表读数）
CREATE TABLE pd_truck_fuel (
  id            VARCHAR(64) NOT NULL COMMENT '主键',
  truck_id      VARCHAR(64) NOT NULL COMMENT '车辆id',
  fuel_amount   DECIMAL(10,2) NOT NULL COMMENT '加油量(L)',
  unit_price    DECIMAL(10,2) NULL COMMENT '单价(元/L)',
  total_amount  DECIMAL(12,2) NULL COMMENT '金额',
  mileage       DECIMAL(12,2) NULL COMMENT '本次里程表读数(km,人工录入)',
  occur_time    DATETIME    NOT NULL COMMENT '加油时间',
  voucher       VARCHAR(255) NULL COMMENT '凭证图片',
  operator      VARCHAR(64) NULL,
  create_time   DATETIME    NOT NULL,
  PRIMARY KEY (id),
  KEY idx_truck_time (truck_id, occur_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='车辆加油/油耗记录';
```

> 里程说明：`PdTruck` **无里程字段**，因此百公里油耗 = `本次加油量 ÷ (本次mileage − 上次mileage) × 100`，里程由人工录里程表读数。**不为此改 `PdTruck` 表、不引 IoT 硬件**。

### 6.3 接口（类上 `@RequestMapping("cost")`）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/cost` | 新增成本（趟次成本录入，含凭证上传） |
| POST | `/cost/page` | 成本分页（按任务/车辆/司机/类型/时间筛选） |
| GET | `/cost/task/{taskId}` | **某趟成本明细 + 合计**（趟次利润的输入） |
| POST | `/cost/fuel` | 新增加油记录 |
| GET | `/cost/fuel/truck/{truckId}` | 车辆油耗记录 + **百公里油耗** |
| GET | `/cost/summary` | 成本汇总（按车队/车辆/月份/类型聚合） |

### 6.4 趟次利润（G7"每趟盈亏实时可见"）
趟次利润 = 该趟运费收入 − 该趟成本合计。
- 收入：来自 `Order.amount`（经 `TransportOrder.orderId` → `Order`）。
- **本期只做"成本归集 + 收入关联展示"**，真正的结算/对账属第三梯队（P1 财务），不在本卡。

### 6.5 前端
- 管理端：**趟次成本录入页**、**车辆油耗页**、成本汇总报表。
- 移动端司机端：**在途费用上报**（拍照/水印上传走已有 `attachment/upload`）→ 对应 G7"水印相机实时报销"。

### 6.6 DoD / 红线
- [ ] 成本能按趟归集并算出合计。
- [ ] 油耗能算百公里油耗（里程缺失时给出明确提示，不报错）。
- [ ] 司机端上报的费用能落到对应趟次。
- [ ] 凭证上传复用现有 `attachment/upload`，**不新建文件服务**。

## 7. OPS-5 司机趟次绩效与驾驶行为

### 7.1 目标（对标 G7 安全管家 / ADAS·DSM）
G7：驾驶行为监控、事故率下降 51%。
**解决**：司机绩效无量化、驾驶行为无管控。

### 7.2 绩效：零表改动，统计查询
| 指标 | 算法 |
|---|---|
| 完成趟次 | `DriverJob` where `driverId` and `status=4` 计数（按周期） |
| 准点率 | `actualArrivalTime <= planArrivalTime` 的趟次 ÷ 总趟次 |
| 异常/告警次数 | `pd_transport_alert` where `bizType=DRIVER` and `bizId=driverId` 计数 |
| 平均延误 | `delay_minutes` 均值 |

### 7.3 驾驶行为：复用已有 + 扩展告警类型
- 已有：`GpsAlertService` 的 `SPEED_OVER`（超速）、`STAY_TOO_LONG`（长时间停留）。
- 本期新增：`DRIVE_FATIGUE`（连续行驶超阈值）、`NO_GPS`。
- **数据来源**：现有 `LocationRecord` 轨迹 + 已规划的**北斗定位**（见司机端任务卡 D-P0-1）与**司机视频**（VID）。
- **明确**：用手机 GPS / 北斗车载终端（JT/T 808）替代 G7 的专业 ADAS/DSM 硬件 —— **不采购新硬件、不引新中间件**。

### 7.4 接口（类上 `@RequestMapping("driver-performance")`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/driver-performance/{driverId}` | 司机绩效：趟次、准点率、告警次数、平均延误 |
| POST | `/driver-performance/page` | 司机绩效列表（可排序，用于排名） |
| GET | `/driver-performance/{driverId}/alerts` | 该司机告警明细 |

### 7.5 DoD / 红线
- [ ] 绩效指标由查询算出，**不加冗余统计字段、不建中间表**（样本量小，实时算即可）。
- [ ] 驾驶行为告警复用 `GpsAlertService` + 告警中心，**不另起一套告警机制**。
- [ ] 疲劳驾驶阈值进 yml，禁止硬编码。
