# 品达物流 TMS —— 项目分析、同类项目对比与可借鉴设计要点

> 本文基于**本仓库真实代码**（非 README 宣传）逐项核对，并联网检索 8 个同类开源/商业 TMS 项目做对比。
> 约束前提（来自历史约定）：**JDK 固定 1.8、技术栈不升级、安全问题不处理、未实现的中间件属后期路线图**。

---

## 一、项目解决了什么核心问题

品达物流 TMS 是一套面向**运输公司 / 企业运输队**的运输管理全流程系统，核心价值是把"下单 → 调度 → 运单 → 运输 → GPS → 签收"这条链路从人工作业（电话、Excel、纸质回单）搬到线上，实现：

- **降本增效**：智能调度引擎（Drools 算费 + DFS 路径规划）自动派单、配车、配司机，降低空驶率。
- **全程可视化**：Netty 双通道收 GPS 轨迹，订单状态机（12 级）全程可控、可追溯。
- **多端协同**：管理端、司机端、快递员端、客户端四类角色联动，状态自动闭环。
- **行业适配**：设计上支持快递 / 快运 / 专线 / 三方物流四类模式。

本质 = **用微服务 + 规则引擎 + 实时通信，把"运输资源（车/人/线路）与运输任务（订单/运单）做最优匹配与全链路追踪"**。

## 三、覆盖了哪些"端"（实测）

| 端 | 仓库内现状 | 技术形态 |
|----|-----------|---------|
| **后台管理端** | ✅ 有完整前端 + 后端 API | `pd-admin-ui`（Vue2/Element）对接 `pd-web-manager`（13 个 Controller）+ `pd-authority` |
| **司机端后端 API** | ✅ 有（`pd-web-driver`，4 Controller：User/Car/Cargo/Attachment） | REST API，**但无对应前端 App** |
| **快递员端后端 API** | ✅ 有（`pd-web-courier`，4 Controller：Courier/User/Common/GoodsType） | REST API，**无对应前端** |
| **客户端（C 端）后端 API** | ✅ 有（`pd-web-customer`，7 Controller：Mailing/User/Agency/AddressBook/Attachment/Common/GoodsType） | REST API，**无对应前端** |

> ⚠️ 历史上曾误将 `DriverJob/TruckLocation/TransportTask/PickupDispatchTask/TransportOrder` 写成 `pd-web-driver/courier` 的控制器——**实测它们属内部 Feign 服务 `pd-work`（及 `pd-dispatch` 的 OrderLocus），并非 pd-web 端点，不可经网关直连**。完整接口清单见《后端接口文档.md》。
| **移动端 App / 小程序 / H5 / PDA** | ❌ 仓库内**无**任何移动端前端工程 | 属路线图（README 设想 Weex/MQTT/高德SDK） |

**关键澄清**：`pd-web` 的 4 个模块是**四个角色的后端 API 服务**，管理端已有 Vue 控制台；而司机/快递员/客户三个"端"目前**只有后台接口、没有前端界面**——这正是后续要补的"多端"缺口。

Controller 清单印证业务覆盖：`pd-web-driver/courier/customer` 暴露下单(Mailing)、运费(totalPrice)、取派(Courier/PickupDispatch)、车辆(Car)、货物(Cargo/GoodsType)、用户(User)、机构(BusinessHall/Agency)、附件(Attachment) 等；而运输任务(TransportTask)、司机作业(DriverJob)、运单(TransportOrder)、轨迹(OrderLocus/TruckLocation) 由**内部 Feign 服务 `pd-work`/`pd-dispatch` 提供**，仅能被 `pd-web-*` 聚合层调用、不可经网关直连。完整接口清单见《后端接口文档.md》。

## 六、可借鉴的功能与界面设计要点（落地建议）

以下按"**对本项目有价值 + 符合 JDK1.8/不升栈约束**"筛选，分功能与 UI 两类。

### 6.1 功能增强要点（优先级排序）
1. ~~**补"仓储 WMS"短板（最大空白）**~~
   **❗2026-10-06 定位复核后降级**：经《友商定位对比与优化完善清单》§4 判定，品达是 **Carrier TMS**（自营/加盟运输管理），
   **不做重型仓配一体 WMS**（那是京东模式、重投入）。本期仅保留**轻量中转/分拨节点管理**（P2 可选），
   原建议的 `Warehouse / Stock / Inventory / InOutRecord` 完整领域建模**不在本期范围**。
2. **移动端三件套（司机/快递员/客户）**：参考 logistics-app 三端架构与 InstaDispatch 司机 App 功能——把已存在的 `pd-web-driver/courier/customer` 三个 API 配上前端。

3. **电子签收 POD（Proof of Delivery）**：拍照 + 手写签名 + 条码扫描 + GPS 时间水印，参考 InstaDispatch/DataCapture。当前 `deliver()` 仅有状态回写，缺凭证采集（前端 + 附件 API 已具备，需打通）。
4. **财务结算模块**：运费挂账、应收应付、司机工资——当前完全缺失（海泰/JeecgBoot 均有）。可先用 `pd-aggregation` 聚合做账单视图。
5. **数据大屏升级**：当前仅基础 ECharts；参考海泰仓运统计报表 + Codazz 的 KPI 看板（OTIF 准时率、单 route 成本、异常率），把调度/运输关键指标可视化。
6. ~~**开放 API / 对接**：为后期对接 WMS/ERP/三方物流留标准接口~~
   **❗已移出范围（用户明确约束）**：本项目为自营/加盟运输管理，**不对接任何外部厂商 API**
   （顺丰/三通一达/EDI/ERP/多式联运/海外合规全部不做）。
   仅保留**内部能力**：客户 Share Link（凭单号查件的分享链接，属本系统自有功能，非 EDI）。

### 6.2 界面（UI/UX）设计要点
1. **管理后台（M 端）——数据驱动大盘**
   - 全量运单状态看板，**异常订单标红预警**（Codazz/站酷一致做法）。
   - 财务与运力分析：发件端与司机端账单自动匹配、差异可追溯；按区域/时段统计单量分布辅助调配。
   - 沿用现有 Element UI + ECharts，无需换框架即可做"异常红点 + KPI 卡片 + 地图轨迹"三件套。
2. **司机端（B 端）——效率优先、单手操作**
   - 任务大厅：运单列表**突出距离 / 时间窗 / 收入**，支持便捷筛选（站酷）。
   - 揽收派送：扫码识别运单设**快捷键**；醒目"异常上报"入口，支持**带时间水印拍照**减少电话沟通。
   - 个人看板：接单量/准时率/好评率图表化 + 提现快捷键（提升黏性）。
   - **离线优先**：路线与任务本地缓存，恢复网络自动同步（Codazz/DataCapture 强建议，农村地区必需）。
3. **客户端（C 端）——极简、透明**
   - 发件：简化表单；**运费试算用滑动选择器**实时按重量/体积算价（站酷）。
   - 追踪：实时位置 + ETA 预测 + 每个里程碑（揽收/在途/签收）通知。
   - 电子签收：大尺寸手写板 / 拍照上传组件，凭证云端留存。
4. **通用交互规范（从商业方案提炼）**
   - 司机 App"最少点击数"原则、大按钮、语音/地图引导（Codazz）。
   - OTP/扫码核验收件人身份、COD 代收、司机-调度双向消息（InstaDispatch）。
   - 统一色彩系统：沉稳主色（物流信任感）+ 前置化信息布局（站酷总结）。

### 7.3 给本项目的"优势融合"路线图
把上面所有友商优势，**按"不升级技术栈、契合 JDK1.8"原则**融合成一条路线：

- **近期（补齐最大缺口，纯前端/领域层）**
  1. 三端配 **uni-app(Vue3) + uview-plus** 跨端前端（借海泰仓运"多端协同"+ 商业 App"单手大按钮/离线"经验），对接现有 `pd-web-driver/courier/customer` API。
  2. 管理端大屏升级（借 Codazz/海泰"异常标红 + KPI 卡片 + 轨迹地图"），现成 Element+ECharts 即可做。
  3. **电子签收 POD**：前端采集签名/拍照/扫码/GPS 水印 → 复用现有附件 API（借商业 App 范式）。
- **中期（业务纵深）**
  4. ~~**WMS 仓储领域建模**~~ ❗**不做**（品达 = Carrier TMS，不做重型仓配一体）。改为：中转/分拨节点管理（轻量，P2 可选）。
  5. **财务结算视图**（借 logistics-app/JeecgBoot）：运费挂账、应收应付、司机工资，先用 `pd-aggregation` 聚合。
  6. **电子围栏 + 实时重排**（借 logistics-app/Codazz）：在现有 Netty+Kafka 轨迹上加 GeoHash 围栏与异常预警。
- **后期（你的既定路线图，技术栈允许时）**
  7. 调度升级为多约束 VRP；接入 Kafka/RocketMQ、MongoDB/HBase、XXL-JOB、SkyWalking；~~开放 API/EDI 对接 WMS/ERP~~ ❗**不做**（不对接外部厂商 API）。

> **融合结论**：不必每个友商都抄——取**海泰仓运的"WMS+TMS 一体+三端"**打底，**商业司机 App 的"POD+离线+单手交互"**做移动端体验，**logistics-app 的"财务+多端"**补经营闭环，**JeecgBoot 的低代码思路**留作提效参考。其余（多租户/低代码/现代前端框架）按自身需要取舍，不强行升级。

## 八、一句话总结

**品达 TMS 当前是一个"后端链路完整、管理端有 Vue 控制台、但三个业务角色缺前端、且完全没有仓储 WMS"的运输管理骨架。** 把友商优势集中后，最该优先融合的是：海泰仓运的"WEB+小程序+PDA 协同 + WMS/TMS 一体"、商业司机 App 的"离线优先 + POD 电子签收 + 单手大按钮"、logistics-app 的"财务结算 + 多端"、以及 Codazz/海泰的"异常标红 KPI 大屏"。UI 上继续用 Element UI（**管理端 Vue2，不迁移**）与 **uview-plus（移动端 uni-app + Vue3）** 即可对齐行业主流，**无需升级现有技术栈**。
